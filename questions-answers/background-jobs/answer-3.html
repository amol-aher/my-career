Overview

Detailed explanation of SNS and SQS: what they are, when to use each, common patterns (fanout, pub/sub, queueing), security, and operational tips.

What are SNS and SQS?

  • SNS (Simple Notification Service): Pub/Sub messaging for fan-out to multiple endpoints (SQS, HTTP, Lambda, email, SMS). Good for broadcasting events.
  • SQS (Simple Queue Service): Durable queue service for decoupling producers from consumers. Two types: Standard (high throughput, at-least-once, best-effort ordering) and FIFO (exactly-once processing within a 5-minute dedupe window, ordered).

Common patterns

Fan-out

Publisher -> SNS topic -> multiple SQS subscriptions (or Lambdas). Useful for sending the same event to many consumers.

Event bus

SNS as an event bus for microservices; integrate with EventBridge for richer routing.

Queueing

SQS as a durable buffer for jobs processed by consumers (Shoryuken, Lambda, consumers).

Security and reliability best practices

  • Use IAM roles with least privilege for producers and consumers.
  • Enable server-side encryption (SSE) on SQS and encrypt SNS messages if sensitive.
  • Use VPC endpoints (AWS PrivateLink) for SQS/SNS to avoid public internet traffic.
  • Monitor CloudWatch metrics (ApproximateNumberOfMessagesVisible, NumberOfMessagesSent, NumberOfMessagesDeleted, ApproximateAgeOfOldestMessage).

Operational tips & costs

  • Use long polling on SQS to reduce empty responses and lower costs (wait time up to 20s).
  • Tune visibility timeout based on consumer processing time.
  • Use DLQs to catch poison messages and metrics/alarms to detect anomalous redrive counts.
  • Watch costs for very high message volumes; standard queues are cheaper but FIFO adds cost and throughput limits.

Subquestions and answers

  1. When to use SNS vs SQS?
    Use SNS for pub/sub and fanout; SQS for durable queues and buffering. Often they are used together: SNS publishes events, SQS stores them for consumers.
  2. How to ensure messages are processed exactly once?
    Use SQS FIFO + deduplication where applicable and design idempotent consumers. For large scale, rely on idempotency because distributed systems rarely guarantee perfect once-only semantics.
