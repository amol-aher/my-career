Dead Letter Queues in SQS — What They Are and How To Use Them

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Detailed explanation of SQS Dead Letter Queues (DLQs): how messages get there, redrive policy, monitoring, troubleshooting, and best practices for handling poison messages.

What is a Dead Letter Queue (DLQ)?

A DLQ is a secondary SQS queue where messages are moved after failing processing repeatedly. It isolates poison messages so they don't block normal processing and helps you debug problematic payloads.

How messages end up in a DLQ

  • Configure a redrive policy on the primary queue that references a DLQ and a maxReceiveCount (e.g., 5).
  • Each time a message is received but not deleted (consumer fails), its receive count increments.
  • When receive count > maxReceiveCount, SQS moves the message to the DLQ automatically.

Important configuration parameters

  • maxReceiveCount: How many times a message can be received before being moved to DLQ.
  • VisibilityTimeout: Must be long enough for your consumer to process the message.
  • RetentionPeriod: How long messages are kept in DLQ (default 4 days, max 14 days).

How to handle DLQ messages

  • Inspect & diagnose: Pull messages from DLQ and examine payload, headers, and processing errors.
  • Fix & redrive: After fixing the root cause, you can redrive messages back to the source queue with the AWS Console, CLI, or programmatically.
  • Automate alerts: Create CloudWatch alarms on ApproximateNumberOfMessagesVisible for the DLQ to notify the team when messages appear.
  • Store metadata: Log failure reasons and stack traces in a structured store (S3, DynamoDB) with correlation IDs to trace upstream producers.

Best practices and patterns

  • Set conservative maxReceiveCount (3–10) depending on transient error expectations.
  • Avoid automatic redrive until you have telemetry and a human-in-the-loop for critical flows.
  • Keep DLQ messages immutable — record original metadata and failure context for debugging.
  • Consider archiving DLQ messages in S3 for long-term analysis.

Subquestions and answers

  1. What if DLQ fills up quickly?
    Investigate the root cause — common causes are schema changes, consumer code bugs, permission issues, or malformed messages. Use CloudWatch logs and the DLQ payloads to triage.
  2. Can Sidekiq use SQS DLQ?
    Sidekiq doesn't consume SQS directly. If using an SQS->Sidekiq bridge, DLQs are managed by SQS and the bridge should surface failures to application logs and monitoring. Alternatively, use Shoryuken which works with SQS and DLQs directly.
