Sidekiq and SNS — Integration Patterns and Practical Approach

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Overview

Explains whether Sidekiq can be used directly with SNS, common patterns for integrating SNS/SQS with Sidekiq, and recommended architectures for reliable event processing.

Can Sidekiq consume SNS or SQS directly?

Short answer: No — Sidekiq natively consumes jobs from Redis, not SQS/SNS.

However, you can integrate SNS/SQS with Sidekiq using bridging patterns. The right approach depends on requirements (throughput, latency, FIFO, deduplication, AWS-native features).

Common integration patterns

1) SNS -> SQS -> Shoryuken (or custom consumer) -> Sidekiq

Subscribe an SQS queue to an SNS topic. Run a lightweight SQS consumer (Shoryuken or a tiny Ruby process) that reads messages from SQS and enqueues Sidekiq jobs:

# pseudo-code inside SQS consumer
sqs_msg = receive_message(...)
Sidekiq::Client.push('class' => MyWorker, 'args' => [sqs_msg.body])
sqs.delete_message(receipt_handle)

2) SNS -> Lambda -> Enqueue Sidekiq (or call API)

Use an AWS Lambda triggered by SNS that either:

  • Calls your Rails API endpoint to create a Sidekiq job (HTTP POST)
  • Directly enqueues a job by calling Redis/Sidekiq client if network/security allows

3) Use SQS-native consumers (Shoryuken) instead of Sidekiq

If you want a simpler architecture with SQS as the only queue, use shoryuken which can process SQS messages directly and supports threads and AWS integrations.

4) Event-driven — make consumers idempotent

Because SQS is at-least-once delivery, ensure the Sidekiq job or the downstream processing is idempotent or uses deduplication.

Why use SNS + Sidekiq hybrid?

  • Durability & fanout: SNS can fan-out events to multiple SQS queues or Lambda consumers simultaneously.
  • Leverage AWS features: Use SQS DLQs, FIFO queues, and SNS filtering without coupling all consumers to Redis.
  • Separation of concerns: Use SNS/SQS for inter-service messaging and Sidekiq for internal asynchronous processing.

Example: SQS consumer enqueuing Sidekiq job (Ruby, Shoryuken or custom)

# Example using shoryuken (simplified)
class MySqsWorker
  include Shoryuken::Worker
  shoryuken_options queue: 'my-queue', auto_delete: true

  def perform(sqs_msg, body)
    payload = JSON.parse(body)
    # Enqueue to Sidekiq for internal processing
    SendWelcomeEmailWorker.perform_async(payload['user_id'])
  end
end

This keeps SQS as the durable transport and Sidekiq for CPU-bound/IO-bound work inside your app.

Subquestions and answers

  1. Is latency worse with bridging?
    Some added latency exists (SQS poll + enqueue step), but it's usually small and the benefit of durability and decoupling outweighs it for many systems.
  2. How to handle visibility timeouts and reprocessing?
    Ensure the consumer deletes SQS messages only after successful enqueue, and set visibility timeout long enough for the enqueue operation plus a safety margin.
  3. Why not push directly to Sidekiq from producers?
    If producers are external services, they may not have access to your Redis or you may want to decouple with durable messaging so producers don't fail when your app is down.
