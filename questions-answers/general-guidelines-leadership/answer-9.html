Feature Flags — Usage & Use Cases

Experience Summary

I have used feature flags extensively (Flipper, LaunchDarkly, custom-built toggles) to decouple deployment from release, perform A/B tests, enable gradual rollouts, and run dark launches.

Common Use Cases

  • Gradual rollouts: Enable a feature for 1% → 10% → 100% of users while monitoring metrics.
  • Dark launches: Deploy backend changes without enabling UI, to warm caches or run background jobs.
  • Kill switches: Rapidly disable a problematic feature in production.
  • A/B testing & experiments: Serve different logic to cohorts and measure conversion.
  • Permissioning & tiers: Expose features to paid tiers only.

Implementation — Example with Flipper

# Gemfile
gem 'flipper'
gem 'flipper-active_record'

# in an initializer
Flipper.configure do |config|
  config.default do
    adapter = Flipper::Adapters::ActiveRecord.new
    Flipper.new(adapter)
  end
end

# usage in controller
if Flipper.enabled?(:new_checkout, current_user)
  render :new_checkout
else
  render :legacy_checkout
end

Best Practices

  • Use descriptive flag names and a flag lifecycle: create → roll out → remove.
  • Store flag state in a durable store and avoid spread throughout many code paths — centralize the decision if possible.
  • Document flags and tie to tickets so old flags can be deleted.
  • Monitor metrics and create automated rollback triggers for anomalies.

Subquestions & Answers

When to remove a flag?

Once the feature is stable and fully rolled out, remove the flag and related branching code to reduce technical debt — typically within 2–4 sprints after full rollout.

How do you avoid flag sprawl?

Enforce a lifecycle policy, regular audits, and a small owner team responsible for flag hygiene.
