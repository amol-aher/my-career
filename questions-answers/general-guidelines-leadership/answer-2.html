Ruby & Rails Versions — Experience

Summary

I have worked across multiple Ruby and Rails versions from Ruby 1.9/2.0 era up to Ruby 3.x and Rails 3.x through Rails 7.x. I have experience upgrading apps, managing deprecations, and leveraging new features for performance and developer productivity.

Specific Versions & Notable Work

  • Ruby: 1.9.3, 2.0.x, 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 3.0, 3.1, 3.2. Experience includes: performance tuning with MJIT/YJIT, leveraging pattern matching in Ruby 2.7/3.x, and using frozen string literals.
  • Rails: Rails 3.2, 4.2, 5.0–5.2, 6.0–6.1, and Rails 7.0. Worked on upgrades: Rails 4→5, 5→6 (introduced Zeitwerk, parallel testing, Webpacker adoption), and 6→7 (hotwire integration, esbuild, and removing Webpacker in many cases).

Upgrade Experience — Example Checklist

1. Run test-suite and fix failing tests
2. Audit Gemfile for incompatible gems
3. Replace deprecated APIs (e.g., before_filter -> before_action)
4. Upgrade Ruby minor versions first (2.6 -> 2.7 -> 3.0)
5. Address keyword arguments changes in Ruby 3.0
6. Migrate autoloaders (classic -> Zeitwerk)
7. Run security scanners (brakeman, bundler-audit)

Common Pitfalls & How I Address Them

  • Gem incompatibilities: Fork or replace unmaintained gems; vendor small patches if necessary.
  • Performance regressions: Benchmark before/after; optimize SQL, add indexes, or fix N+1 queries.
  • Runtime changes: Run in staging with representative traffic and feature flags for safe rollouts.

Code Example — Rails 6 initializer for Zeitwerk compat

# config/initializers/zeitwerk_compat.rb
if Rails.autoloaders.zeitwerk_enabled?
  Rails.autoloaders.each do |autoloader|
    autoloader.push_dir(Rails.root.join('lib'))
  end
end
