How to decide: Service Object vs Concern vs Callback

Choosing among these patterns is about responsibilities, coupling and testability. Below is a practical decision guide with code examples.

Definitions (brief)

  • Service Object — a PORO that encapsulates a single business operation or workflow (testable, injectable).
  • Concern — shared module (mixin) for behaviour reused across models/controllers; usually small and composable.
  • Callback — lifecycle hook on models (before_save, after_commit) used for model-intrinsic behaviors (defaults, simple side-effects).

Decision checklist

  1. Is this business orchestration spanning multiple models or external services?
    • Yes → Service Object
  2. Is this purely a small reusable behavior (scopes, small helper) used by many models/controllers?
    • Yes → Concern (keep it tiny)
  3. Is this tightly coupled to model lifecycle (normalize attributes, set defaults) and simple?
    • Yes → Callback (prefer small; avoid heavy work in callbacks)
  4. Does it cause side effects like sending emails/charging cards?
    • Avoid doing this in callbacks — instead, emit an event or enqueue a Service Object through a job.

Examples

Service Object (good for orchestration)

class PlaceOrder
  def initialize(user:, cart:, payment_gateway:)
    @user = user; @cart = cart; @gateway = payment_gateway
  end

  def call
    ActiveRecord::Base.transaction do
      order = Order.create!(user: @user, total: @cart.total)
      @gateway.charge(order)
      NotifyUserJob.perform_later(order.id)
      order
    end
  end
end

Concern (small, reusable behaviour)

module Archivable
  extend ActiveSupport::Concern

  included do
    scope :archived, -> { where.not(archived_at: nil) }
  end

  def archive!
    update!(archived_at: Time.current)
  end
end

Callback (for intrinsic lifecycle logic only)

class User < ApplicationRecord
  before_validation :sanitize_email

  private
  def sanitize_email
    self.email = email&.strip&.downcase
  end
end

Testing and maintainability

  • Service Objects — easy to unit-test (no DB) and to mock when used in controllers.
  • Concerns — test via small spec on a dummy class to keep behavior correct.
  • Callbacks — test the effect, but prefer explicit service use for complex side effects to avoid hidden behavior.

Common mistakes

  • Putting heavy orchestration in callbacks -> hard-to-test code and surprising behavior during object lifecycle.
  • Creating God concerns that mix many unrelated behaviours — split concerns by responsibility.
  • Overusing Service Objects for trivial getters/setters — don't add indirection where simple methods suffice.

Interview tip

Show an example where you refactored a callback into a service (and job) and explain why it improved testability and debuggability.
