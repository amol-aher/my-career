Applying the Observer pattern using ActiveSupport callbacks

Rails provides lifecycle callbacks on ActiveRecord models (e.g., after_create, after_commit) which can be used to implement observer-like behavior. For more decoupled instrumentation, ActiveSupport::Notifications or background jobs are preferred.

Simple callback-based observer

class Order < ApplicationRecord
  after_create :publish_order_created_event

  private

  def publish_order_created_event
    OrderNotifier.publish(self.id)
  end
end

class OrderNotifier
  def self.publish(order_id)
    # push to queue or call subscribers
    EventBus.publish('order.created', order_id: order_id)
  end
end

Using ActiveSupport::Notifications (recommended for decoupling)

# instrumenting
class Order < ApplicationRecord
  after_create_commit :announce

  def announce
    ActiveSupport::Notifications.instrument('order.created', order_id: id, user_id: user_id)
  end
end

# subscriber (e.g., in an initializer)
ActiveSupport::Notifications.subscribe('order.created') do |name, start, finish, id, payload|
  Analytics.track('order_created', payload)
  EmailWorker.perform_later(payload[:order_id])
end

Advantages

  • Callbacks are easy to add and good for short synchronous side effects.
  • ActiveSupport::Notifications provides a pub/sub mechanism without tight coupling to handlers and is helpful for metrics and asynchronous processing.

Caveats

  • Don't mix heavy business logic into callbacks — they can make transactions and error handling complex.
  • Prefer after_commit for publishing events that should run only once the DB transaction succeeds.
  • Use background jobs for IO-heavy observers to avoid blocking web requests.
