Handling API rate limits across integrations

Rate limiting is crucial when integrating with external APIs. Each provider has its own limits and policies. You must protect both your system and respect provider rules. Below are strategies for enforcement and recovery.

Types of rate limits

  • Per-second / per-minute / per-day limits
  • Concurrent request limits
  • Leaky-bucket or token-bucket enforced by provider
  • Per-API-key or per-account limits

Client-side strategies

  • Centralized rate limiter — a shared component that tracks allowance per provider/tenant and delays/queues requests when limits approach. Implement token-bucket or leaky-bucket algorithms in Redis for distributed processes.
  • Per-connector quotas — read provider docs for limits and configure the limiter per endpoint/connector manifest.
  • Adaptive throttling — lower concurrency when error rates increase; dynamic windows based on observed Retry-After headers.

When limits are exceeded

  1. Detect — provider typically returns 429 or specific error codes and may include Retry-After header.
  2. Respect Retry-After — delay retries according to header. For missing headers, use exponential backoff with jitter.
  3. Queue & prioritize — enqueue failed requests to a retry queue with backoff. Prioritize critical requests and deprioritize bulk syncs.
  4. Notify & expose status — surface rate limit hits in dashboards and inform tenants if their integrations are triggering excessive calls.

Architectural components

  • Rate limit store — Redis or in-memory with consistency layer to track tokens per provider/account.
  • Request queue — persistent queue for delayed retries (SQS/Kafka/Redis streams).
  • Circuit breaker — open the circuit for an endpoint under sustained 429s and avoid wasting resources.
  • Backoff & jitter — exponential backoff with randomized jitter to prevent thundering herds.

Sample algorithm (token bucket in Redis)

# pseudocode
def allow?(key)
  now = Time.now.to_i
  bucket = redis.get(key) || {tokens: capacity, last: now}
  # add tokens since last
  elapsed = now - bucket[:last]
  bucket[:tokens] = [capacity, bucket[:tokens] + elapsed * rate].min
  if bucket[:tokens] >= 1
    bucket[:tokens] -= 1
    bucket[:last] = now
    redis.set(key, bucket)
    true
  else
    false
  end
end

Operational considerations

  • Monitor rate limit rejections per provider and per tenant.
  • Provide dashboards and alerts for sustained rate limiting.
  • Offer tenant-level throttles and self-service limits to avoid noisy neighbors.
  • Log sample request payloads and provider responses to debug frequent 429s.

Interview follow-ups

  • Q: What if provider provides no Retry-After?
    Use exponential backoff with bounded retries and escalate to a dead-letter queue for manual inspection.
  • Q: How to prioritize requests?
    Classify requests (real-time, background sync, bulk import) and enforce different priority queues and rate buckets.
  • Q: How to handle token expiry and auth errors?
    Retain a refresh flow and renew tokens proactively; pause requests if auth fails repeatedly and alert owners.

In interviews give concrete examples: e.g., implemented Redis-based token-bucket limiter that reduced 429s by 80% and added per-tenant quotas to prevent abuse.
