AASM — an overview and usage patterns

What is AASM? AASM (also known as acts_as_state_machine historically) is a lightweight Ruby gem that adds state machine behavior to Ruby classes (commonly ActiveRecord models). It provides a DSL to declare states, transitions, events, guards, and callbacks in a readable way.

Why use AASM?

  • Clear state modeling — makes possible states and transitions explicit.
  • Centralizes state logic — avoids scattered status strings and `if` chains.
  • Integrates well with ActiveRecord — persists state to model column and supports scopes for each state.

Basic example

class Order < ApplicationRecord
  include AASM

  aasm column: 'status' do
    state :pending, initial: true
    state :paid
    state :shipped
    state :cancelled

    event :pay do
      transitions from: :pending, to: :paid, after: :send_payment_confirmation
    end

    event :ship do
      transitions from: :paid, to: :shipped, guards: [:inventory_available?]
    end

    event :cancel do
      transitions from: [:pending, :paid], to: :cancelled, after: :refund_if_paid
    end
  end
end

Key features

  • Events & transitions — declare allowed transitions and run actions in callbacks (before/after).
  • Guards — methods that return boolean to allow conditional transitions.
  • Persistence — specify the column used to persist states; works with ActiveRecord and Sequel.
  • Bang methods — AASM generates bang methods that raise errors if transition is invalid, and non-bang methods that return boolean for safe attempts.
  • Scopes — generate ActiveRecord scopes for states (e.g., Order.shipped).
  • Multiple state machines — you can define multiple machines on a single model using different columns.

Advanced usage

  • Transition hooks — use before_enter, after_exit, and similar hooks to trigger side effects.
  • Internationalization — integrate with I18n to present friendly state names in the UI.
  • Persistence strategies — store state as string, integer (with mapping), or serialized symbol depending on space/perf needs.
  • Testing — test valid transitions, guards, callbacks, and invalid transitions (expect exceptions or false returns).

Pros and cons

ProsCons / Caveats
Readable DSL; quick to add to models; good for straightforward workflows. Can encourage fat models if you put lots of side-effects in callbacks; not ideal for extremely complex long-running workflows (use a workflow/orchestrator).

When to prefer AASM

  • Model has a relatively small, well-defined set of states and transitions (orders, invoices, ticket lifecycle).
  • You want simple state validation and query helpers integrated alongside the model.

Alternatives

  • state_machines / state_machines-activerecord — another popular state machine gem with advanced features.
  • Temporal / Step Functions — for durable, long-running orchestrations rather than in-model state machines.
  • Custom service objects — model transitions using explicit service classes and event logs if you want clearer separation of side-effects.

Interview subquestions

  • How to avoid fat models with AASM? Keep side effects in service objects triggered by transition hooks. Use the state machine only to validate transitions and persist state.
  • How to test transitions? Unit-test state transitions and assert side effects are delegated to collaborators (mocks/stubs).

AASM is a pragmatic choice in Rails apps for modeling finite state domains. In interviews, emphasize separation of concerns: use AASM for state validation and small callbacks, and push heavier side-effects into services.
