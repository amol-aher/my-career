Designing a social feed system — architecture, storage, scaling

Scenario: Users can post content; other users see a personalized news feed (e.g., LinkedIn/Facebook/Instagram). We must design for high throughput writes, low read latency, and personalization.

High-level architecture

  1. Clients (mobile/web) -> CDN -> API Gateway
  2. API layer — stateless services for posts, feeds, profiles.
  3. Write pipeline — post service writes canonical post to DB and emits events (Kafka/SNS).
  4. Fan-out workers — subscribe to events to push post IDs into followers' timelines (push) or update indexes (pull-friendly stores).
  5. Storage — primary DB for posts (sharded), Redis/Elastic for timelines and search, object store (S3) for media.
  6. Read path — feed service reads precomputed timeline from Redis or composes via queries to fast stores; cache per-user timeline.

Data model (simplified)

posts table
- id (UUID)
- author_id
- content_text
- media_refs (S3 keys)
- created_at
- visibility (public/friends/private)
- metadata (likes_count, comment_count)

followers table
- user_id
- follower_id
- created_at

user_timeline (denormalized per user, in Redis or DB)
- user_id
- list of post_ids (sorted by score or timestamp)

How to store posts

Store canonical posts in a primary persistent store (relational DB like PostgreSQL or a wide-column store like Cassandra depending on scale). Media files go to S3 with presigned URLs. For fast reads, store denormalized timelines in Redis lists or in a dedicated timeline DB (Cassandra, Scylla) keyed by user_id.

How another user fetches friends' posts efficiently

Two broad approaches:

  1. Fan-out on write (push): When author posts, fan-out post ID to all followers' timelines (redis list or timeline table). Pros: fast reads, simple paging. Cons: expensive for users with millions of followers (celebrity problem). Mitigations: hybrid push for regular users, and pull for celebrities (store in a separate hot-post index).
  2. Fan-out on read (pull): At read time, fetch recent posts from followees (query their recent posts) and merge-sort. Pros: cheaper writes. Cons: higher read latency and heavy read amplification for many followees; requires optimized joins and caching.

Hybrid approach (commonly used)

Use push for users with small-to-medium follower counts and pull for celebrities/influencers. Also maintain a global hot-posts cache for widely-shared content and perform partial merge at read time.

Caching strategy

  • Cache per-user timeline in Redis with TTL and support for incremental updates.
  • Cache rendered feed pages (HTML/JSON fragments) at CDN edge where privacy allows (public posts).
  • Cache commonly accessed entities: user profiles, media metadata.
  • Use cache-aside pattern for Redis: check cache, on miss fetch from timeline store and repopulate cache.

Pagination

Prefer cursor-based (keyset) pagination: return a cursor token (e.g., last_post_timestamp + offset or encoded last post id) rather than offset-based pages. This avoids skipping/missing posts and scales well. Provide limits and a "load more" cursor. For infinite scroll, prefer stable cursors that encode read position.

Access Control (ACL) & Visibility

  • Store visibility on post level (public/friends/private/custom list). Enforce ACL at write time (filter audience) when fanning out to timelines to avoid expensive checks during reads.
  • For group or restricted posts, maintain per-audience timelines or membership checks during read with caching of membership data.
  • Use signed URLs for private media and short TTLs.

Scaling & sharding

  • Shard posts by author_id to distribute write load.
  • Partition timeline storage by user_id. Use consistent hashing for Redis clusters or use a distributed datastore like Cassandra that scales horizontally.
  • Use message queues (Kafka) to absorb write bursts and fan-out asynchronously with workers and backpressure.

Consistency and latency trade-offs

Feeds are usually eventually consistent. Aim for low read latency; tolerate slight delays in visibility. Use write-through or read-after-write guarantees for critical flows (e.g., show user's own new post immediately by reading from write DB or local buffer).

Metrics and observability

  • Track feed load latency, cache hit rates, fan-out lag, queue backlog, and worker failure rates.
  • Monitor heavy hitters (users causing high fan-out) and adapt strategies (rate limit or switch to pull).

Optimizations & pitfalls

  • Celebrity problem: hybrid push/pull and materialized views for hot users.
  • Backpressure: queue-based writes and graceful degradation when workers lag—serve partial feeds from cache.
  • Storage cost: prune old timeline entries, compress IDs, or store only pointers to posts in timelines.

Interview subquestions

  • How to handle notifications and real-time updates? Use websockets or push notifications with presence and incremental update events; update timelines in background and push deltas to clients.
  • How to support complex ranking? Compute scores via offline ML pipelines and apply realtime boosts (engagement, recency) at read time in the feed service.
  • How to handle deletions/privacy changes? Propagate delete events through the pipeline to remove from timeline stores and invalidate caches; for hard deletes remove in batches to avoid spikes.
  • How to test at scale? Load test producers and consumers, simulate celebrity fan-out, and measure queue lag and worker throughput.
