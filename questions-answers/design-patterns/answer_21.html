Implementing the Singleton pattern in Ruby

Goal: ensure only one instance of a class exists and provide a global access point to it.

When to use

  • Shared resource managers (connection pools, configuration, logger wrappers)
  • Cross-cutting single instances like a global cache adapter

Approach 1 — Ruby's standard Singleton module

require 'singleton'

class AppConfig
  include Singleton

  attr_accessor :settings

  def initialize
    @settings = load_defaults
  end

  def load_defaults
    {timeout: 5, retries: 3}
  end
end

# usage
cfg = AppConfig.instance
cfg.settings[:timeout] = 10

The singleton module provides instance and prevents direct .new calls. It is simple, thread-safe on MRI, but lacks flexibility (hard to subclass).

Approach 2 — Manual implementation (more control, easier to test)

class LoggerSingleton
  @instance_mutex = Mutex.new

  class << self
    def instance
      return @instance if @instance
      @instance_mutex.synchronize do
        @instance ||= new
      end
      @instance
    end

    private :new
  end

  def log(msg)
    puts "[LOG] #{msg}"
  end
end

# usage
LoggerSingleton.instance.log('started')

This gives thread-safe lazy initialization and hides new by making it private. It’s easy to mock in tests by stubbing .instance.

Approach 3 — Dependency injection preferred for testability

Singletons introduce global state which can make testing and reasoning harder. Prefer to inject shared instances into components, and use a composition root (an initializer) to wire the singleton in production:

# in initializer (e.g., config/initializers)
LOGGER = LoggerSingleton.instance

# in classes
class OrderService
  def initialize(logger: LOGGER)
    @logger = logger
  end
end

Trade-offs & best practices

  • Singletons provide convenience but create hidden dependencies—use DI where practical.
  • Prefer private new + .instance pattern if you need control over instantiation.
  • Keep singleton state minimal and immutable when possible to avoid surprising side-effects across tests.
  • When writing libraries, avoid global singletons to not pollute consumer apps' global state.

Interview tips

Explain why you might avoid globals in large systems, show both Singleton module and manual implementations, and mention dependency injection as a more testable alternative.
