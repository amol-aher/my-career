REST API design — principles, patterns and practical examples

Snapshot: Good REST API design blends clear resource modeling, consistent HTTP semantics, strong error handling, versioning, security, and operational concerns (pagination, caching, rate limiting). Below is a practical checklist, patterns, and interview-ready examples.

Core design principles

  • Model resources as nouns: Use URIs to represent resources: /users, /orders, /reports/123.
  • Use HTTP verbs correctly: GET (read), POST (create), PUT/PATCH (replace/partial update), DELETE (remove). Prefer PATCH for partial updates.
  • Statelessness: Each request contains the information needed (auth token, context). Externalize state if necessary (session store).
  • Proper status codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests, 500 Internal Server Error.
  • Consistent error format: Use RFC 7807 (Problem Details) or a company-standard error schema with code, message, details, and optionally a user-facing hint.
  • Idempotency: Design endpoints so retries are safe (PUT/DELETE are idempotent; use Idempotency-Key for POSTs that must not duplicate).
  • Pagination & filtering: Use cursor/keyset pagination for large sets; support flexible filtering and sorting through query parameters.
  • Versioning: Expose API versions via the URL (/v1/) or via content negotiation; make breaking changes explicit and sparse.

Design patterns & concrete practices

  • Resources & relationships: Represent relationships with sub-resources (/users/{id}/posts) or links in response body (HATEOAS) when helpful.
  • Filtering & search: Provide expressive query parameters (e.g., ?status=active&created_after=...). Use dedicated search endpoints when full-text search or complex filters required.
  • Pagination: Prefer cursor-based pagination: return next_cursor and prev_cursor. Avoid offset-based pagination for large/volatile datasets.
  • ETags & conditional GET: Implement ETag and If-None-Match to reduce bandwidth and support client-side caching.
  • Rate limiting: Provide response headers (e.g., X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset) and return 429 when exceeded.
  • Pagination + caching: Cache frequent list endpoints and use short TTLs with cache revalidation for freshness.
  • Batching & bulk operations: Provide bulk endpoints when it reduces chattiness (e.g., POST /v1/jobs/batch), but keep error semantics clear per item.

Example endpoints with semantics

POST /v1/reports                 # returns 202 Accepted + job id (async)
GET  /v1/reports/{id}              # 200 with status & metadata
GET  /v1/reports/{id}/download     # 200 + file stream or 302 to S3 signed url

GET  /v1/users?cursor=abc&limit=25 # cursor pagination
PATCH /v1/users/{id}               # partial update; idempotent semantics
DELETE /v1/users/{id}              # 204 No Content on success

Security & Authentication

  • Always enforce TLS and HSTS.
  • Use OAuth2 bearer tokens or mutual TLS for service-to-service auth. For internal microservices, mTLS and short-lived certificates are ideal.
  • Validate scopes/claims at the API gateway or service boundary; use least privilege for service accounts.
  • Sanitize and validate inputs; use whitelisting for sort/filter params.

Operational concerns

  • Expose health endpoints for orchestrators (/healthz, /readyz).
  • Support graceful shutdown and connection draining.
  • Instrument with structured logs, metrics, and distributed traces (OpenTelemetry).
  • Provide OpenAPI/Swagger specs and keep them in sync with code (contract-first or code-gen pipelines).

When to choose alternatives

  • GraphQL: When clients need flexible queries and want to reduce over/under-fetching — but consider complexity in caching, rate-limiting and server-side performance controls.
  • gRPC: For high-performance internal services that can accept binary protocols and require streaming; provide REST+JSON gateways for external clients.

Interview follow-ups & suggested answers

  • Backward compatibility: Make additive changes, deprecate fields gently, run consumer contract tests, and provide migration guides. Use API versioning where needed.
  • Idempotency for POST: Use Idempotency-Key header persisted for the operation's lifetime (common for payments/orders).
  • Partial response / field masking: Support a fields= parameter when clients need small payloads (document and limit complexity).
  • Caching strategy: Use cache-control, ETags, and CDNs for public endpoints; use Redis for server-side caches and be explicit about cache invalidation policies.
Interview tip: Give concrete examples from past systems (e.g., “I designed an orders API using cursor pagination and ETags, which reduced client traffic by 35%”) — numbers and trade-offs score well.
