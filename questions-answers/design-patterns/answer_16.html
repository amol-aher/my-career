Scheduling user jobs (e.g., daily at 3 p.m.)

Scheduling in multi-tenant distributed systems introduces challenges: timezone handling, reliability, idempotency, and scalability. Below are design options and recommended practices.

Common scheduling options

  • Central scheduler (single source) — a leader process (Kubernetes CronJob, scheduler service) scans scheduled tasks and enqueues jobs. Use leader election (Redis lock/etcd) to avoid duplication.
  • Distributed scheduling — store schedule metadata in DB and let multiple workers claim due jobs using atomic DB operations (select ... for update / row locks) or Redis sorted set pop by score (timestamp).
  • Managed schedulers — AWS EventBridge, CloudWatch Events, or GCP Cloud Scheduler to trigger API endpoints or push messages; good for low operational overhead.
  • Workflow engines — Temporal / Step Functions provide durable timers and long-running scheduled workflows with built-in retry & visibility.

Key design requirements and how to meet them

  • Timezone awareness — store schedule with timezone or normalize to UTC plus user's timezone offset; when computing next run, apply timezone/dst rules (IANA tz database).
  • Idempotency — scheduled actions must be safe to run multiple times; include run_id and use dedup keys or distributed locks.
  • Retry & backoff — configurable retry policy for failures with exponential backoff and a dead-letter queue for manual inspection.
  • Scalability — partition scheduled jobs by tenant or time window and process in parallel; use sharded queues for throughput.
  • Visibility & control — UI for users to see upcoming runs, last run status, and to pause/cancel schedules.

Implementation patterns

  1. DB-backed schedule + worker claim 
    # pseudo SQL
WITH due AS (
  SELECT id FROM schedules WHERE next_run_at <= now() AND enabled = true LIMIT 100 FOR UPDATE SKIP LOCKED
)
UPDATE schedules SET next_run_at = compute_next() WHERE id IN (SELECT id FROM due) RETURNING id;
-- enqueue jobs for returned ids
  2. Redis sorted set (ZSET) — add schedules with score=timestamp; workers atomic pop by score and run; use locks to avoid races.
  3. Use managed EventBridge — create per-tenant scheduled rules or publish a single rule that triggers a service which filters and enqueues tenant jobs (cost/scale trade-offs).
  4. Sidekiq + sidekiq-cron / whenever — good for Rails apps; for user-configurable schedules, store schedule definitions in DB and a scheduler process updates Sidekiq Cron or enqueues jobs dynamically.

User-facing scheduling model

  • Allow cron expressions for power users or human-friendly options like "daily at 15:00" with timezone selection.
  • Validate schedules at creation and provide preview of next N run times in user's timezone.
  • Quota scheduled jobs per tenant and provide throttling to protect system resources.

Edge cases & operational tips

  • Clock skew — synchronize clocks with NTP; prefer timestamp-based queues over relying on local clocks.
  • DST transitions — compute next_run using timezone libraries (tzinfo) to avoid running twice or skipping runs.
  • Backfill and missed runs — provide options to backfill missed runs for offline windows or grace periods.
  • Testability — simulate schedules in staging and support test hooks to fast-forward timers.

Example: Rails + Sidekiq approach

# Scheduler service runs periodically (once per minute) and claims due schedules
class Scheduler
  def run
    due = Schedule.due.limit(100)
    due.each do |s|
      next unless s.claim! # atomic claim: update status if still due
      PerformScheduledJobWorker.perform_async(s.id)
      s.update(next_run_at: s.compute_next)
    end
  end
end

Interview follow-ups

  • How to scale to millions of schedules? Partition by tenant, use sharded queues, and event-driven triggers. Consider a streaming scheduler (Kafka) and multiple consumer groups.
  • How to support user cancellation? Provide APIs to pause/cancel and ensure workers check cancellation before executing a job.
