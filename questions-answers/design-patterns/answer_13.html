Designing a workflow engine for user-defined automations

Goal: allow users to define automations like "When order ships → generate invoice → send email" via a UI or configuration, with robust execution, retries, observability and safe sandboxing.

High-level architecture

  1. Workflow Designer UI — drag-and-drop or form-based builder that produces a serialized workflow (JSON/YAML).
  2. Workflow Definition Store — persistent store for definitions and versions (Postgres/Cassandra).
  3. Workflow Compiler/Validator — validates the DSL, resolves references, type-checks inputs, and compiles to an executable plan.
  4. Orchestrator / Execution Engine — executes steps, tracks state, schedules retries, and persists execution history.
  5. Task Workers / Action Runners — pluggable workers that perform external actions (generate PDF, send email, call API).
  6. Event Bus — Kafka/SNS for event-driven triggers and for decoupling producers/consumers.
  7. Monitoring & Audit — execution logs, metrics, and a UI for inspecting runs and replays.

Key design choices

  • Representation — define workflows as a directed acyclic graph (DAG) or state machine. Use JSON-friendly schema to store nodes and edges plus metadata.
  • Idempotency & retries — runners should be idempotent, with configurable retry policies and exponential backoff. Track attempt counts in execution state.
  • Long-running tasks — support durable timers and sleep/wait for asynchronous callbacks (webhooks) by storing state and resuming later.
  • Security — sandbox user-provided expressions; restrict access to secrets, and use role-based access to workflow definitions.
  • Pluggability — actions implemented as plugins (Ruby gems or microservices). Provide a library of common actions and a way to install custom actions safely.

Example workflow JSON (simple)

{
  "id": "invoice-on-ship",
  "version": 3,
  "trigger": {"type": "event", "name": "order.shipped"},
  "nodes": [
    {"id": "gen_invoice", "type": "action", "action": "generate_invoice", "params": {"template": "standard"}},
    {"id": "email", "type": "action", "action": "send_email", "params": {"to": "{{order.customer.email}}", "template_id": "invoice_email"}}
  ],
  "edges": [["gen_invoice","email"]]
}

Execution semantics

  • Trigger: event consumed from the event bus starts a new workflow run (create run_id).
  • Execution: orchestrator schedules nodes whose dependencies are satisfied; workers pick up tasks from queues and report completion state.
  • Compensation & rollback: allow optional compensating actions for failure scenarios (e.g., cancel shipment if invoice fails).

Scaling & reliability

  • Stateless orchestrator instances with durable state in DB; use optimistic locking for state transitions.
  • Separate queues per action type or priority for worker scaling.
  • Use outbox pattern for reliable event publishing when workflow changes result in external calls.

Implementation options (fast path vs full-featured)

  • Use an existing workflow engine: Temporal, Cadence, or AWS Step Functions for durable execution, retries, timeouts, and visibility.
  • Custom lightweight engine: DB-backed orchestrator + Sidekiq workers + event bus — good when you need bespoke actions and want full control.

Common interview subquestions

  • How do you test workflows? Unit-test action implementations, use integration tests with a test bus and ephemeral DB, and provide replay capabilities for debugging.
  • How to handle schema changes? Version workflow definitions and support migration scripts or graceful version negotiation at runtime.
  • How to secure user-defined actions? Whitelist permitted actions, sandbox scripts, and enforce least privilege for secrets and external APIs.

This design balances flexibility (user-defined flows) with operational safety (idempotency, retries, auditing). For an interview, be ready to sketch the event flow and justify choices between a managed workflow (Temporal/Step Functions) and a custom implementation.
