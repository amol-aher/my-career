Single Responsibility Principle (SRP) and report generation

Question: Is the report generation example an example of a single responsibility class from SOLID? Short answer: Not by default — report generation is usually an orchestration of multiple responsibilities. To follow SRP, split the pipeline into focused classes: data fetcher, aggregator/presenter, builder, exporter, and persistence/queuing. Each should have one reason to change.

SRP recap

SRP: A class/module should have one, and only one, reason to change. In practice we aim to minimize reasons to change by separating concerns such that each class is responsible for a single part of the behavior.

Typical responsibilities in a report pipeline

  • Input/Querying — building and executing DB queries, applying filters.
  • Business aggregation — applying domain rules, calculations, roll-ups.
  • Layout & composition — sections, headers, totals, page breaks.
  • Serialization/export — CSV, XLSX, PDF, streaming logic.
  • Persistence/dispatch — save to S3, enqueue background job, or return HTTP stream.

How to refactor a monolithic ReportGenerator into SRP-compliant pieces

  1. Introduce a Query Object for all DB interactions (unit-testable with factories).
  2. Introduce an Aggregator/Presenter for domain logic (pure Ruby, no DB calls).
  3. Use a Builder to compose the report structure (PORO representing the rendered model).
  4. Use Exporter strategies for each output format.
  5. Keep a thin Coordinator / Service that wires components and orchestrates the workflow.

# Orchestrator
class OrdersReportService
  def initialize(query:, aggregator:, builder:, exporter:)
    @query = query
    @aggregator = aggregator
    @builder = builder
    @exporter = exporter
  end

  def run
    relation = @query.call
    aggregated = @aggregator.new(relation).aggregate
    report = @builder.build_from(aggregated)
    @exporter.export(report)
  end
end

How SRP helps

  • Each component is small and focused — easier to reason about and test.
  • Changing how data is fetched does not affect how PDFs are generated, reducing regression risk.
  • Parallelization: exporter can run in a background worker without touching the query object implementation.

Practical guidelines / interview talking points

  • Explain SRP with "one reason to change" and show the mapping of reasons to classes.
  • Show how you would test each component independently. For instance, the Aggregator should be tested with in-memory arrays or stubs, not the DB.
  • Discuss performance considerations: keep large dataset handling in streaming or batched processing.
  • Mention real-world constraints: deadlines sometimes require pragmatic merges of responsibilities (trade-offs), but show how you'd refactor for maintainability.

Overall: report generation is an orchestration; to adhere to SRP you should split responsibilities into small collaborating classes. This is a great chance in an interview to show design judgement — explain trade-offs and demonstrate sample tests and metrics you’d monitor.
