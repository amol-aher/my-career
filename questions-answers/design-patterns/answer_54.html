Using Event Sourcing & CQRS patterns in a Rails app

Overview: Event Sourcing stores state as an append-only sequence of domain events. CQRS (Command Query Responsibility Segregation) splits write models (commands/events) from read models (projections). In Rails, you can adopt these gradually for parts of the system where auditability, complex history, and scalable read models are required.

When to consider

  • Auditability and full history are mandatory.
  • Complex business rules that evolve and need reprocessing.
  • Need to scale read models independently of writes.

Key components

  • Event store — append-only store of domain events (RailsEventStore, Kafka, custom table).
  • Command handlers — validate and persist events to the event store.
  • Projectors / Read model builders — subscribe to events and update read-optimized views (Postgres tables, Elasticsearch, Redis).
  • Replayers — re-run events to build new projections if read model schema changes.

Example using rails_event_store (conceptual)

# command handler
class PlaceOrderHandler
  def call(cmd)
    # validate...
    event = OrderPlaced.new(data: {order_id: cmd.order_id, items: cmd.items})
    RailsEventStore::Client.new.publish(event)
  end
end

# projector
class OrderProjector
  def call(event)
    case event
    when OrderPlaced
      OrderReadModel.create!(id: event.data[:order_id], items: event.data[:items])
    when OrderCancelled
      OrderReadModel.find(event.data[:order_id]).update!(status: 'cancelled')
    end
  end
end

# wiring (initializer)
RailsEventStore::Client.new.subscribe(OrderProjector.new, to: [OrderPlaced, OrderCancelled])

Benefits

  • Perfect audit trail and ability to reconstruct state.
  • Decouples write logic from read performance tuning.
  • Enables flexible, denormalized read models tailored to use cases.

Costs & challenges

  • Increased complexity (mental model, testing, operational).
  • Event schema evolution must be handled carefully (versioning).
  • Eventual consistency between write and read sides—design for it.

Practical adoption strategy

  1. Start with a single bounded context (e.g., billing or orders) where audit matters.
  2. Implement an event store and projectors for that context.
  3. Build replayers & migrations for event versioning.
  4. Monitor projection lag and tune consumers/parallelism.

Interview tip

Explain when you’d adopt event sourcing: not for every table—only where the benefits outweigh the complexity. Give a concrete example: invoice lifecycle where exact history and ability to recompute balances were crucial.
