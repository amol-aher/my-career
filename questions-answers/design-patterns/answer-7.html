API Gateway — components and responsibilities

Short summary: An API Gateway is a single entrypoint for clients to interact with backend services. It centralizes cross-cutting concerns: authentication, authorization, rate limiting, request routing, protocol translation, request/response transformation, telemetry, and caching.

Key components

  • Authentication & Authorization — validate tokens (JWT/OAuth), integrate with identity providers, enforce ACLs and scopes.
  • Routing & Load Balancing — map incoming paths to backend services, support canary/blue-green routing, and weighted routes.
  • Rate Limiting & Throttling — per-client/quota limits, burst controls, and quota tracking.
  • Request/Response Transformation — modify headers, body, and protocol conversion (HTTP <-> gRPC), and composition of multiple backend responses.
  • Caching — edge caching for public endpoints, configurable TTLs and cache invalidation hooks.
  • Observability — structured logs, metrics, distributed tracing headers, and access logs.
  • Security & WAF — protect against injection, bad payloads, and provide WAF integration and input validation.
  • Rate plan / API monetization — API key management, usage plans, and billing hooks (for public APIs).
  • Monitoring & Health checks — upstream health checks, circuit breaking, and failover strategies.

Advanced features

  • Service composition / aggregation — combine multiple backend calls into a single response for clients.
  • Protocol translation — frontend clients speak REST while backends use gRPC; the gateway translates.
  • Edge A/B testing & canarying — route a portion of traffic to new service versions.
  • Dynamic configuration — push routing and policy changes without restarts.

Interview subquestions

  • Where to place the gateway? At the edge before internal network; often layered: external gateway for public clients and internal gateway for service-to-service communication.
  • Do you put business logic there? Keep gateway thin: avoid business rules. Use it for orchestration and composition only when it reduces chattiness and does not duplicate domain logic.
  • High availability? Run multiple gateway instances across AZs, use autoscaling, and externalize rate-limiter state to Redis or DB for consistency.

In an interview, be ready to discuss trade-offs: security centralization vs single point of failure, performance overhead vs developer productivity, and how you handle scaling and failover for the gateway itself.
