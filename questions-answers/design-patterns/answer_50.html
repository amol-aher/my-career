Refactoring a large Rails model — design patterns & techniques

If your model is growing too large, apply patterns that break responsibilities into testable, single-purpose components.

Patterns to apply

  • Service Objects — move complex operations and orchestration out of the model (e.g., CreateOrder, ProcessRefund).
  • Query Objects / Repositories — extract complex queries into dedicated classes.
  • Form Objects — handle multi-model form flow outside the model.
  • Decorator / Presenter — move presentation logic out of the model.
  • Policy objects — use Pundit for authorization logic instead of sprinkling checks in the model.
  • State pattern — extract state-specific behavior into state machines or state objects.
  • Events / Observers — move side effects to subscribers or background jobs.
  • Concerns (small) — extract reusable bits but avoid God modules.

Refactoring approach

  1. Identify responsibilities (validation, persistence, business rules, integrations, presentation).
  2. Prioritize easiest extractions (presenters, queries) and add tests before moving code.
  3. Extract one responsibility at a time and run full test suite; use feature flags for behavioral changes if necessary.
  4. Document new boundaries and update architecture diagrams.

Example refactor — order checkout

# before: large Order model with payment, shipment, notifications

# after: extract services
class CreateOrder
  def call(cart:, user:)
    order = Order.create!(...)
    ChargePayment.new(order).call
    ReserveInventory.new(order).call
    NotifyUserJob.perform_later(order.id)
    order
  end
end

Other techniques

  • Use composition over inheritance — prefer modules/services to massive subclasses.
  • Adopt hexagonal / clean architecture layering when model responsibilities are domain-heavy.
  • Introduce domain events and projections to create read-optimized models and keep write model lean.

Interview tip

Walk through a concrete refactor: show before/after code snippets, tests you added, metrics improved (reduced cyclomatic complexity, faster deploys, clearer ownership), and how the team adopted the new patterns.
