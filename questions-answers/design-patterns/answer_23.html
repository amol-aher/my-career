How Ruby supports the Strategy pattern via duck typing

Strategy encapsulates interchangeable algorithms behind a common interface. In Ruby, duck typing means you don’t need formal interfaces — objects that implement the expected methods can be used interchangeably.

Example: Payment strategies

class StripeGateway
  def charge(amount, currency)
    # call stripe
  end
end

class PaypalGateway
  def charge(amount, currency)
    # call paypal
  end
end

class PaymentService
  def initialize(gateway)
    @gateway = gateway
  end

  def checkout(amount:, currency: 'USD')
    @gateway.charge(amount, currency)
  end
end

# usage
service = PaymentService.new(StripeGateway.new)
service.checkout(amount: 1000)

service = PaymentService.new(PaypalGateway.new)
service.checkout(amount: 1000)

No inheritance or interface required — as long as the gateway responds to charge, it can be swapped in. This makes testing easy (use test doubles) and extensions straightforward.

Advantages in Ruby

  • Low ceremony — fewer classes and no interfaces required.
  • Easy to mock/stub strategies in tests.
  • Supports runtime swapping of behavior (DI via constructor or setter).

Best practices

  • Document the expected methods for the strategy to avoid confusion.
  • Fail fast if methods are missing (raise ArgumentError during initialization) to make errors obvious.
  • Use small adapters if provider APIs differ significantly to normalize method names.

Interview tip

Show the simple example, explain duck typing benefits, and note that you can still enforce contracts via tests or use lightweight RBS/type checking if desired.
