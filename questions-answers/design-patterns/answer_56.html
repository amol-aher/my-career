Anti-patterns in Rails apps and refactoring strategies

1. Fat Models

Symptom: models mix validation, persistence, business logic, API calls and notifications.

Refactor: Extract Service Objects, Repositories, and Domain classes. Move presentation logic to Presenters and side effects to background jobs.

2. Fat Controllers

Symptom: controllers orchestration of business logic, heavy param manipulation and DB operations.

Refactor: Move orchestration to Services or Interactors and strong params parsing into Form Objects.

3. N+1 Queries

Symptom: slow pages caused by lazy-loading associations in loops.

Refactor: Use .includes, batch queries, or Query Objects; add bullet and monitoring to catch regressions.

4. Global State and Singletons

Symptom: use of global mutable objects (CONFIG globals, $variables).

Refactor: Use dependency injection and configuration objects; wrap state in thread-safe classes; avoid process-global mutation.

5. Business Logic in Views

Symptom: complex conditionals and formatting directly in ERB/HAML.

Refactor: Use Presenters/Decorators, ViewComponent or helpers to centralize and test presentation logic.

6. Overuse of Metaprogramming

Symptom: dynamic methods obscure behavior and confound IDEs and tests.

Refactor: Replace with explicit methods where clarity is more important; document generated behavior and keep metaprogramming small and well-tested.

7. Blocking IO in Request Cycle

Symptom: HTTP calls, heavy computation or mailing done inline in controllers.

Refactor: Move to background jobs (Sidekiq/ActiveJob), adopt async APIs, and return early responses when suitable.

8. Big Monolithic Schema for Read-heavy Data

Symptom: a single normalized table used for both write and read-optimized queries causing slow analytics.

Refactor: Create read models, denormalize, use materialized views, or introduce a separate analytics store.

Refactor workflow and tips

  1. Write tests that describe current behavior before doing big refactors.
  2. Extract small pieces incrementally (services, presenters, queries).
  3. Use feature flags if behavior must change gradually.
  4. Monitor performance and error rates after each change.

Interview tip

Prepare a before/after example of a refactor (e.g., splitting a big model into service + presenter + query). Quantify improvements (test coverage, response time, maintenance time reduced).
