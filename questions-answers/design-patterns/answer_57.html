Implementing Repository + Unit of Work in Rails

Concept: Repository abstracts data access operations; Unit of Work groups several operations into a single transaction (commit/rollback). Together they make complex data handling explicit and testable.

Why use them in Rails?

  • Decouple domain logic from ActiveRecord and SQL.
  • Enable easier testing by mocking repository interfaces.
  • Centralize transaction boundaries and side-effect management.

Simple implementation

class OrderRepository
  def find(id)
    Order.find(id)
  end

  def save(order_entity)
    record = order_from_entity(order_entity)
    record.save!
    order_from_record(record)
  end

  private
  def order_from_entity(e); end
  def order_from_record(r); end
end

class UnitOfWork
  def initialize
    @operations = []
  end

  def register(&blk)
    @operations << blk
  end

  def commit
    ActiveRecord::Base.transaction do
      @operations.each(&:call)
    end
  end
end

# usage
uow = UnitOfWork.new
uow.register { OrderRepository.new.save(order_entity) }
uow.register { InventoryRepository.new.decrement(items) }
uow.commit

Variations and best practices

  • Implement transaction boundaries in application services rather than scattering them.
  • Keep repositories thin: CRUD and mapping logic only.
  • When using multiple DBs or microservices, Unit of Work cannot span them—use sagas or distributed transactions (compensating actions).

Testing

  • Unit-test domain services by mocking repositories (no DB).
  • Test repository implementations with integration tests hitting a test DB.

Interview tip

Explain how UoW reduced partial-success bugs in an order/fulfillment flow and how you handled multi-system compensations via sagas when necessary.
