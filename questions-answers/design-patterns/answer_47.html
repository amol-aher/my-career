Rails before_action filters and the Chain of Responsibility pattern

Analogy: before_action filters form a chain where each filter gets a chance to handle or short-circuit the request (e.g., authenticate, authorize, set_locale). This resembles the Chain of Responsibility where handlers are linked and optionally pass processing to the next handler.

Example controller filters

class ApplicationController < ActionController::Base
  before_action :authenticate_user!
  before_action :set_current_tenant
  before_action :authorize_resource

  private

  def authenticate_user!
    head :unauthorized unless current_user
  end

  def set_current_tenant
    # set tenant based on subdomain or header
  end

  def authorize_resource
    # policy check, can render 403 and stop chain
  end
end

Chain of Responsibility characteristics

  • Handlers are ordered and can decide to handle or pass on.
  • Filters can short-circuit (render/redirect) to stop processing.
  • Filters are reusable and composable across controllers.

When to extract away from filters

  • If filter logic becomes complex, move it to services or middleware.
  • For cross-cutting HTTP concerns, Rack middleware is often a better fit than controller filters.

Interview tip

Explain when controller filters are fine and when to prefer middleware or explicit handler chains (e.g., for auth across APIs with different requirements).
