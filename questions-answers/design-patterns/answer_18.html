How to construct provider-specific API requests (Shopify / Amazon / Walmart)

Different providers expect different headers, auth schemes, path parameters and payload shapes. Build a pluggable request builder that composes headers, signs requests, and renders body templates from canonical data.

Components of a request builder

  • Auth module — signs requests or injects tokens (OAuth, API key, AWS SigV4).
  • Header composer — merges default headers from connector manifest and runtime headers (e.g., correlation id).
  • URL builder — resolves base URL, path params, query strings and versioning placeholders.
  • Body templating — render payload using a templating engine (Liquid, ERB, Jinja) or transform via mapping engine (JMESPath/JSONata).
  • Serializer — set Content-Type and encode body (JSON/XML/form-data) and attach files or multipart data when needed.

Provider-specific notes

Shopify

  • Auth: X-Shopify-Access-Token header (admin REST) or OAuth Bearer token for public apps.
  • Versioning: path includes API version (/admin/api/2025-01/orders.json).
  • Payload: nested JSON under root keys (e.g., { "order": { ... } }).
  • Headers: X-Request-ID for idempotency; Content-Type: application/json.

Amazon (SP-API / MWS)

  • Auth: AWS Signature Version 4 (sign requests with credentials and region/service).
  • Complexity: multi-step authorizations (LWA tokens) and strict timestamp/signature rules.
  • Payload: XML in older MWS, JSON for newer SP-API; often requires multipart for attachments.

Walmart

  • Auth: API key + signature or OAuth depending on integration type.
  • Payload: JSON with specific schema; requires strict field validation and sometimes HMAC signing of payloads.

Example request templates

# Shopify create order template (Liquid-like)
{
  "order": {
    "email": "{{ customer.email }}",
    "line_items": [
      {% for item in order.items %}
      {"variant_id": {{ item.variant_id }}, "quantity": {{ item.qty }}}{% unless forloop.last %},{% endunless %}
      {% endfor %}
    ]
  }
}

# Amazon SP-API requires SigV4 signing rather than a simple body template

Implementation tips

  • Centralize signing logic per auth type so connectors only configure credentials.
  • Use a templating engine that supports safe filters (date, currency formatting) and escapes to avoid injection.
  • Validate final constructed payload against provider JSON schema (where available) before sending to reduce API errors.
  • Instrument request/response pairs and store last request payloads for debugging.

Interview follow-ups

  • How to test these requests? Use contract tests and recorded HTTP fixtures; run integrations against sandbox accounts when possible.
  • How to handle different content types? Build serializer interfaces that select JSON/XML/multipart serializers based on connector manifest.

In an interview, be ready to show how you would structure a request-building module and give one concrete example (Shopify) end-to-end including headers, body template and response mapping.
