Key entities for a sample web application (e-commerce / financial)

This document lists the core domain entities you should model for a typical web application. I’ll cover two examples—an e-commerce system and a finance/accounting system—and then common cross-cutting concerns (audit, multi-tenancy, events).

Cross-cutting entities & concerns

  • Audit logs — who changed what and when (store as append-only events for compliance).
  • Attachments / media — references to S3 objects and derived sizes.
  • Tenants / Organizations — for multi-tenant systems; tenant_id scoping, isolation boundaries, and billing info.
  • Integration records — external ids and sync statuses for 3rd-party systems (Shopify id, Amazon order id).
  • Feature flags and permissions — AB testing and RBAC/ACL models (roles, permissions, policies).
  • Event store — asynchronous events that power audit, projections, and integrations (Kafka/SNS topic names).

Modeling tips (DB & schema design)

  • Use a canonical primary key (UUID) plus human-friendly sequential numbers where needed (order_number) for external visibility.
  • Denormalize for read performance when necessary (order snapshots, product price snapshots) but keep canonical source of truth.
  • Index thoughtfully — indexes on relations/filters: user_id, product.sku, order.status, created_at.
  • Use event-driven patterns for integrations and slow processes: emit domain events (order.created) and process asynchronously.
  • Consider data retention and GDPR requirements — soft deletes, anonymization, and archiving for old records.

Likely interview subquestions & short answers

  • Q: How do you handle inventory consistency?
    Use pessimistic locking for critical stock operations or optimistic locks with reservation tables; maintain a reserved counter to avoid oversell and reconcile with background jobs.
  • Q: Multi-currency pricing?
    Store amounts in minor units (cents) and keep currency codes; use FX rates service for conversions and keep rate timestamps for reproducibility.
  • Q: Data partitioning / sharding?
    Shard large tables by customer_id or time ranges; use read replicas for read-heavy workloads; consider NoSQL for high-scale time-series or event data.
