Implementing the State pattern (orders & tickets)

Goal: cleanly represent object states and their allowed transitions; encapsulate state-specific behavior.

Options in Rails

  1. AASM / state_machine gems — simple DSLs to declare states, transitions, guards and callbacks.
  2. State objects (Strategy-like) — implement state classes that encapsulate behavior; model delegates to current state instance.
  3. Database state column + policy objects — persist state and use policy/query objects to handle allowed actions.

Example using AASM

class Order < ApplicationRecord
  include AASM

  aasm column: 'status' do
    state :pending, initial: true
    state :paid
    state :shipped
    state :cancelled

    event :pay do
      transitions from: :pending, to: :paid, after: :capture_payment
    end

    event :ship do
      transitions from: :paid, to: :shipped, guards: :inventory_available?
    end

    event :cancel do
      transitions from: [:pending, :paid], to: :cancelled, after: :refund_if_paid
    end
  end
end

Example using state objects (manual)

# state interface
class OrderState
  def initialize(order); @order = order; end
  def pay; raise NotImplementedError; end
  def ship; raise NotImplementedError; end
end

class PendingState < OrderState
  def pay
    @order.update!(status: 'paid')
  end

  def ship
    raise 'cannot ship pending order'
  end
end

# Order delegates
class Order < ApplicationRecord
  def state
    @state ||= case status
    when 'pending' then PendingState.new(self)
    when 'paid' then PaidState.new(self)
    end
  end

  def pay; state.pay; end
  def ship; state.ship; end
end

Trade-offs

  • Gems like AASM are fast to adopt but can encourage callbacks in models — keep side effects in services.
  • State objects provide clearer separation and testability, but require more boilerplate.
  • Always persist state in DB and use after_commit for side effects (avoid running side effects inside transaction).

Interview follow-ups

  • How to test state transitions? Unit test state classes or AASM events, assert guards, and verify callbacks are delegated to services (mock external calls).
  • Handling concurrency? Use optimistic locking (lock_version) or DB transactions with SELECT ... FOR UPDATE when performing transitions that touch inventory or cross services.

In interviews, present both quick AASM solution and a more architecturally-pure state object approach; explain how you handle side-effects, concurrency, and testing.
