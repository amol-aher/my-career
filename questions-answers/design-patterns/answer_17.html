Maximizing code reuse across multiple e-commerce integrations

With integrations for Shopify, Amazon, Walmart, etc., the goal is to minimize duplication while handling provider-specific quirks. I'll describe an adapter-based architecture and a configuration-first approach to enable integrations with minimal new code.

Key patterns

  • Adapter / Strategy pattern — define a common integration interface (create_order, fetch_orders, update_inventory) and implement provider-specific adapters.
  • Transformation / Mapping layer — use declarative mappings (JSON/YAML templates or Liquid/JMESPath expressions) to convert provider payloads to your canonical model.
  • Connector manifest — describe each provider’s capabilities, auth types, rate limits and endpoints in a manifest file (JSON). The runtime engine uses the manifest to build requests without code changes.
  • Plugin architecture — load adapters as plugins (gems or microservices). For config-only flows, allow parametrized requests/templates stored as config objects.

Architectural components

  • Canonical model — define internal DTOs (Order, Product, InventorySnapshot). All adapters map provider data to/from this model.
  • Mapper engine — library that uses mapping definitions to transform fields (supports expressions, loops, and conditions).
  • Auth handlers — pluggable auth strategies (OAuth, API keys, AWS SigV4) selected per connector manifest.
  • Request templates — store headers/body templates (Liquid/Jinja) per endpoint, with placeholders for canonical fields.
  • Retry & rate-limit manager — shared component to handle per-provider limits and retries with backoff.

Config-only approach (no new code)

  1. Create a connector manifest describing endpoints, methods, auth, headers, and a mapping to canonical fields.
  2. Provide mapping templates for request/response bodies using a template language and filters for common transforms (date formats, units).
  3. Provide event-to-endpoint bindings so workflows call connectors by name with canonical objects; the system compiles and executes provider-specific requests at runtime.

Sample connector manifest (simplified)

{
  "name": "shopify",
  "auth": {"type": "token", "header": "X-Shopify-Access-Token"},
  "endpoints": {
    "create_order": {
      "method": "POST",
      "path": "/admin/api/{{version}}/orders.json",
      "body_template": "{{ order | to_shopify_order }}",
      "rate_limit": {"calls_per_minute": 40}
    }
  }
}

Benefits

  • No-code onboarding for many providers — fill manifest and mapping templates.
  • Centralized rate limiting and retry logic reduces bugs.
  • Fewer tests for each provider — test the mapping templates and generic engine once, then validate manifests.

Trade-offs & when to write code

  • Config covers the vast majority of RESTful JSON providers. However, when provider has complex auth (e.g., OAuth flows with special PKCE steps) or streaming APIs, a small adapter may still be required.
  • Monitoring & observability must be robust to troubleshoot mapping/template errors which are harder to debug than code.

Interview subquestions

  • How to test connectors? Use contract tests: recorded HTTP fixtures (VCR-like) and schema validation for request/response templates.
  • How to handle breaking API changes? Use connector versioning and deprecation windows; allow multiple manifests to exist and migrate gradually.

This approach minimizes per-provider code while remaining flexible. It’s powerful in interview discussions—walk through an example manifest for Shopify and then show how the same engine can call Amazon with a different manifest.
