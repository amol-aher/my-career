Caching in Rails and APIs — strategies and best practices

Summary: Use caching to reduce latency, database load, and operational cost. For Rails and HTTP APIs, apply multiple cache layers: browser/CDN, HTTP reverse proxies (CDN), application-level caches (fragment/page/action), low-level in-process caches, and distributed caches (Redis/Memcached). Cache responsibly: choose appropriate TTLs, handle invalidation, stay correct (cache consistency), and ensure observability.

Cache layers and where they belong

  1. Client-side & CDN — Cache static assets and public API responses. Use Cache-Control, ETag, and vary headers. For public content use long TTLs with cache-busting for releases.
  2. Edge / Reverse proxy (CDN, Varnish) — Offload traffic; use cache keys and purge APIs for invalidation.
  3. Application-level — Rails fragment caching, page caching (rare), action caching (deprecated). Use Russian Doll caching for nested fragments.
  4. Distributed cache — Redis or Memcached for shared ephemeral data, heavy computations, session stores (if chosen), or rate-limiting counters.
  5. Database caching — Materialized views, read replicas, denormalized tables, or cache tables for expensive joins/aggregations.

Rails-specific techniques

  • Fragment caching — cache @product in views. Use cache keys that include updated_at to auto-expire when the model changes.
  • Russian doll caching — nest caches for parts of a page so changing an inner fragment only invalidates that fragment.
  • Low-level cache API — Rails.cache.fetch('key', expires_in: 5.minutes) { expensive_call } backed by Redis/Memcached.
  • HTTP caching helpers — fresh_when, stale?, ETags and conditional GETs to reduce payloads.
  • Cache digests — asset fingerprinting and view fragment digesting to help invalidation on template changes.

API caching patterns

  • Cache-Control: Public vs private. Use max-age, s-maxage (for CDNs), and must-revalidate as needed.
  • ETag / Last-Modified: Support conditional GETs to let clients/CDNs avoid fetching unchanged responses.
  • Stale-while-revalidate / stale-if-error: Useful to serve slightly stale responses while refreshing asynchronously.
  • Cache busting: Use versioned endpoints or include resource version in cache keys when data changes in incompatible ways.

Cache invalidation strategies

Invalidation is the hardest part — approaches:

  • Time-based TTL — simplest. Accept eventual consistency.
  • Event-driven invalidation — emit events (e.g., via Redis pub/sub, SNS) when data changes and invalidate keys or purge CDN.
  • Key-versioning — change version in key (e.g., posts:v3:user:123) so old keys naturally expire; suits complex dependencies.
  • Explicit purge — call CDN/purge APIs and delete Redis keys synchronously after writes (works but may be slow).

Caching for scalability — examples

# Rails low-level cache
Rails.cache.fetch([user.cache_key, 'feed', page], expires_in: 2.minutes) do
  FeedService.new(user).fetch(page: page)
end

# ETag example in controllers
fresh_when(etag: current_user.cache_key_with_version, public: false)

Patterns for feeds & denormalization

For high-read workloads like user feeds, denormalize and precompute feed timelines into Redis/Elastic or use fan-out strategies (push vs pull). Cache timelines per-user for quick reads and use event-driven invalidation on new posts.

When not to cache

  • Highly dynamic personal data where correctness is critical (bank balance) — consider short TTLs or no caching.
  • When invalidation complexity outweighs benefits.

Monitoring & observability

  • Track cache hit rate, latency, and evictions.
  • Instrument downstream vs cache-served traffic to quantify savings.
  • Set alerts for increased miss rates or high eviction rates.

Common interview follow-ups

  • How to avoid cache stampede? Use locking, request coalescing, or serve stale while recomputing (background refresh).
  • How to avoid inconsistent reads? Use short TTLs, strong invalidation on writes, or adopt read-your-writes patterns for critical flows.
  • How to choose Redis vs Memcached? Use Memcached for simple volatile caches (memory-only) and Redis for richer data structures, pub/sub and persistence.
