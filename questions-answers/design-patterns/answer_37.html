Repository pattern in a Rails application

Intent: abstract data access so domain logic depends on repository interfaces, not on Active Record directly. Useful for isolating persistence concerns and enabling easier testing.

When to use

  • When you want to swap persistence stores or run domain logic independent of database schema.
  • When you need complex read models or caching layers behind a unified interface.

Example repository

class UserRepository
  def find_by_id(id)
    User.find_by(id: id)
  end

  def find_by_email(email)
    User.find_by(email: email)
  end

  def save(user)
    user.save!
  end

  def recent_active(limit: 10)
    User.where(active: true).order(last_login_at: :desc).limit(limit)
  end
end

# usage in a service
class SomeService
  def initialize(user_repo: UserRepository.new)
    @user_repo = user_repo
  end

  def call(user_id)
    user = @user_repo.find_by_id(user_id)
    # business logic...
  end
end

Trade-offs

  • Extra layer of indirection and boilerplate — adds maintenance cost.
  • In Rails, ActiveRecord already provides rich querying; repositories can duplicate that if not carefully designed.
  • Best when you need decoupling (hexagonal/clean architecture) or when you have multiple data sources to unify.

Testing advantages

Repositories are easy to mock in tests, allowing you to write unit tests for domain logic without hitting the DB.

Interview tip

Explain scenarios where you applied a repository to isolate read heavy models or to support a migration from ActiveRecord to a microservice-backed store.
