Design patterns to avoid fat models in Rails

Rails’ "fat models, skinny controllers" guidance encourages keeping controllers thin, but models can still accumulate too much responsibility. Use these patterns to distribute responsibilities and improve testability.

Service objects

Encapsulate complex business actions into POROs. Keep models focused on persistence and simple validations.

class CreateOrder
  def initialize(user:, cart:); end
  def call; end
end

Query / Repository objects

Extract complex queries into separate classes to keep model scopes simple and testable.

class Orders::RecentForUser
  def initialize(user); @user = user; end
  def call; Order.where(user: @user).recent.limit(50); end
end

Form Objects / Presenters

Handle multi-model form submission and presentation logic outside the model (Reform, Virtus, or simple POROs).

Decorator / Presenter

Move view-specific formatting out of models (Draper or SimpleDelegator-based presenters).

Policy / Authorization objects

Use Pundit or custom policy objects to keep authorization logic out of models.

State Machines

Use AASM or state_machines for lifecycle logic instead of peppering models with status checks.

Interactor / Command

For orchestrating multi-step processes, use Interactors or Command objects (similar to service objects) to make flows explicit and testable.

Event-driven / Domain events

Emit events from models (lightweight) and handle side-effects in subscribers/workers. Keeps models from owning integration code.

Example decomposition

# controller
CreateOrder.new(user: current_user, cart: cart).call

# service
class CreateOrder
  def call
    ActiveRecord::Base.transaction do
      order = Order.create!(...)
      PaymentGateway.charge(order)
      NotifyUserJob.perform_later(order.id)
      order
    end
  end
end
