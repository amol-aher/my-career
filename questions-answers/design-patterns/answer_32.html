Service Object pattern and when to use it in Rails

Definition: A Service Object is a PORO (plain Ruby object) that encapsulates a single business operation or workflow, keeping controllers and models thin and focused.

When to use Service Objects

  • Complex business logic or multi-step processes (order checkout, payment processing).
  • Orchestration between multiple models and external services.
  • To make code more testable and easily injectable for background processing.

Typical structure

  • Single public method (commonly #call or .call class method).
  • Accept dependencies via initializer (dependency injection).
  • Return a well-defined result object or raise errors for exceptional states.

Example: CreateOrder service

class CreateOrder
  Result = Struct.new(:success?, :order, :errors)

  def initialize(user:, cart:, payment_gateway:)
    @user = user
    @cart = cart
    @payment_gateway = payment_gateway
  end

  def call
    ActiveRecord::Base.transaction do
      order = Order.create!(user: @user, total_cents: @cart.total_cents)
      charge = @payment_gateway.charge(amount: order.total_cents, id: order.id)
      unless charge.success?
        raise ActiveRecord::Rollback
      end
      order.update!(payment_status: 'paid')
      NotifyOrderJob.perform_later(order.id)
      Result.new(true, order, nil)
    end
  rescue => e
    Result.new(false, nil, [e.message])
  end
end

# controller
def create
  result = CreateOrder.new(user: current_user, cart: cart, payment_gateway: StripeGateway.new).call
  if result.success?
    render json: result.order, status: :created
  else
    render json: {errors: result.errors}, status: :unprocessable_entity
  end
end

Testing

Service objects are easy to unit-test directly: stub external dependencies (payment gateway), assert transactions, and test edge cases.

Organization & conventions

  • Place in app/services or app/interactors.
  • Use a consistent API: .call or #call returning a Result pattern.
  • Single Responsibility: keep each service focused and extract sub-operations into smaller services as needed.

Alternatives & related patterns

  • Interactors (gem) — opinionated structure for organizing service-like components.
  • Command pattern — when you want undo or queuing of operations; commands map well to services.

Interview tips

Show an example like the one above, explain why you extract logic from controllers/models, and describe how you test and monitor these services in production.
