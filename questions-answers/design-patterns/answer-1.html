Design patterns — overview and example

Executive summary: Design patterns are repeatable solutions to commonly occurring design problems in software. They capture best practice, improve communication across teams, and help build maintainable systems. This document explains what patterns are, categories, trade-offs, and walks through a concrete example (the Strategy pattern) with an idiomatic Ruby implementation and guidance on when to use — and when not to.

What are design patterns?

A design pattern is a named, proven solution describing how to solve a recurring software design problem. Patterns are not code templates but conceptual blueprints: they describe responsibilities of classes/objects and how they collaborate.

Why use them?

  • Shared vocabulary — saying "Strategy" conveys a lot of meaning to other engineers.
  • Proven solutions — patterns encapsulate experience and edge cases.
  • Maintainability — better separation of concerns and easier testing.
  • Flexibility — many patterns enable easy swapping of behavior without code churn.

High-level categories

  • Creational — control object creation (Factory, Builder, Singleton).
  • Structural — compose classes/objects into larger structures (Adapter, Decorator, Composite, Facade).
  • Behavioral — algorithms and object responsibilities (Strategy, Template Method, Observer, Command).

Example: Strategy pattern (Ruby)

Problem: You have a component that needs to perform one of several interchangeable behaviors (for example, different tax calculations, or different export formats for a report). You want to add new behaviors with minimal changes to the core flow.

Solution: Use the Strategy pattern: define a family of algorithms (strategies), encapsulate each one behind a common interface, and inject the chosen strategy into the context.

Why Strategy?

  • Encourages single responsibility — strategies focus on algorithm implementation.
  • Makes testing easy — swap in fakes or simple strategies for unit tests.
  • Open/Closed — add new strategies without modifying the context.

Ruby example — report exporter

# plain Ruby illustration of Strategy for exporting a report

module ExportStrategy
  def export(report)
    raise NotImplementedError
  end
end

class CsvExport
  include ExportStrategy
  def export(report)
    # produce CSV string
    headers = report.columns.join(',')
    rows = report.rows.map { |r| r.map(&:to_s).join(',') }
    [headers, *rows].join("\n")
  end
end

class JsonExport
  include ExportStrategy
  require 'json'
  def export(report)
    {meta: report.meta, rows: report.rows}.to_json
  end
end

class ReportService
  def initialize(exporter:)
    @exporter = exporter
  end

  def generate_report(data)
    report = build_report_from(data)
    @exporter.export(report)
  end

  private

  def build_report_from(data)
    # return a simple PORO with columns/rows/meta
    OpenStruct.new(columns: data[:columns], rows: data[:rows], meta: {created_at: Time.now})
  end
end

# usage
service = ReportService.new(exporter: CsvExport.new)
puts service.generate_report(columns: ['id','name'], rows: [[1,'alice']])

Subquestions you might be asked (and short answers)

  • Q: How is Strategy different from Template Method?
    Template Method defines the skeleton of an algorithm in a base class and subclasses implement steps. Strategy encapsulates whole interchangeable algorithms as separate classes—more flexible at runtime.
  • Q: When should I not use design patterns?
    When they overcomplicate simple problems. Prefer simple functions/classes; patterns are for recurring design problems that justify the indirection.
  • Q: How to test patterns?
    Unit-test strategies independently. For the context, assert it delegates to strategy but mock the strategy for behavior isolation.
  • Q: Are design patterns language specific?
    Patterns are conceptual but idiomatic implementations differ. Ruby favors duck typing and modules; Java/C# rely on interfaces and inheritance.

Practical notes / anti-patterns

  • Avoid creating too many tiny classes for minor variations — this leads to class explosion.
  • Prefer composition over inheritance. Strategy uses composition and is usually safer.
  • Document the rationale: name the pattern in code comments to help maintainers.

Quick takeaway: Use design patterns as communication tools and tested blueprints. For interchangeable behavior, Strategy is lightweight, testable, and suits dynamic languages like Ruby well.
