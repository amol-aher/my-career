Stateful vs Stateless APIs — guidance for microservices and monoliths

Elevator summary: Prefer stateless APIs for HTTP-based microservices and external public APIs because statelessness improves scalability, resilience, and operational simplicity. Stateful APIs (server-side session state, sticky sessions) are acceptable in limited contexts (legacy apps, interactive sessions, websockets), but when state is required, externalize it to a shared store (Redis, DynamoDB) rather than binding it to an instance.

What does statelessness mean?

Statelessness means each request carries all information necessary to process it — the server does not rely on stored session state across requests. Authentication tokens (JWT/OAuth), request parameters, or idempotency keys are examples of state carried with a request.

Benefits of stateless APIs

  • Horizontal scaling: Any instance can serve any request; simple autoscaling and load balancing.
  • Failure isolation: Replacing nodes is cheap — no session affinity to maintain.
  • Simpler deployment: Rolling upgrades and blue/green deployments are easier without session stickiness.
  • Better caching & CDNs: Stateless responses are easier to cache at intermediaries.

When stateful APIs are necessary

  • Websockets / Server-Sent Events (SSE): Persistent connections inherently maintain state (connections, subscriptions).
  • Complex multi-step transactions: Long-lived workflows where serializing intermediate state each request is expensive (but consider externalizing state).
  • Legacy apps: Existing session-based architectures where rework is costly.
  • Real-time presence / collaborative apps: Presence and cursor positions are often easier with in-memory connection state combined with an external pub/sub layer.

State management patterns

  • External session store (recommended when state needed): Store session data in Redis, DynamoDB, or a DB. Instances remain stateless; data is centralized and replicated. Example: Rails session_store with Redis.
  • JWTs and opaque tokens: JWTs are stateless tokens carrying claims (fast verification) but complicate revocation and sensitive data storage. Opaque tokens (stored and validated against Redis) enable easy revocation.
  • Sticky sessions (load balancer affinity): Route a user to the same instance. Simple but reduces resilience and complicates scaling/maintenance.
  • Client-side state: Keep minimal state in the client (e.g., local storage) and send it with each request. Useful for shopping carts or UI state but security must be considered.

Practical recommendations

  1. Default to stateless: Design APIs so any instance can process a request. Use bearer tokens, idempotency keys, and externalize long-lived state.
  2. If you need sessions, externalize them: Use Redis or a DB for sessions rather than in-memory instance state; ensure high availability and autoscaling of the session store.
  3. Use JWTs carefully: Prefer short-lived JWTs with refresh tokens; implement revocation via token blacklists (Redis) or use rotating refresh tokens.
  4. Design for web sockets: Use a connection manager (e.g., a dedicated service or a message broker) and keep minimal critical state in a durable store to allow reconnects and graceful failover.
  5. Graceful degradation: When external session stores are unavailable, surface clear errors or fallback to reduced functionality rather than silently failing.

Examples (Ruby / Rails snippets)

1) Stateless auth with JWT (verify token on each request)

class ApplicationController < ActionController::API
  before_action :authenticate!

  def authenticate!
    token = request.headers['Authorization']&.split(' ')&.last
    payload = JwtService.decode(token)
    @current_user = User.find(payload['sub'])
  rescue JWT::ExpiredSignature, JWT::DecodeError
    head :unauthorized
  end
end

2) Opaque token validated against Redis (revocable)

class SessionsController < ActionController::API
  def create
    token = SecureRandom.hex(32)
    Redis.current.setex("session:#{token}", 2.hours.to_i, user.id)
    render json: {access_token: token}
  end
end

# middleware
class TokenAuth
  def call(env)
    token = env['HTTP_AUTHORIZATION']&.split(' ')&.last
    user_id = Redis.current.get("session:#{token}")
    if user_id
      env['current_user_id'] = user_id
      @app.call(env)
    else
      [401, {'Content-Type' => 'application/json'}, [{error: 'unauthorized'}.to_json]]
    end
  end
end

Handling websockets and sticky connections

For real-time features, use a dedicated connection manager or message broker (Redis pub/sub, Kafka, or managed services like AWS AppSync/IoT). Avoid relying on sticky sessions when possible — instead, store minimal connection metadata in a central store so another instance can resume or send messages via the broker.

Trade-offs — interview talking points

  • Why stateless for microservices? Because microservices scale independently and failure of one instance shouldn’t affect client sessions. Statelessness simplifies service discovery and load balancing.
  • Performance vs complexity: Stateless JWTs reduce DB lookups but complicate revocation. Opaque tokens and Redis add a network hop but make revocation simple.
  • Operational cost: Externalizing session state increases infrastructure needs (Redis clusters) but reduces operational pain of instance affinity and enables horizontal scale.

Common interview follow-ups & concise answers

  • Q: How do you revoke a JWT? Implement short-lived access tokens + refresh tokens with server-side revoke lists or track a token version in user DB and include it in the token claims.
  • Q: When are sticky sessions acceptable? For legacy applications with heavy in-memory sessions where reengineering is not feasible; ensure LB redundancy and graceful draining during deploys.
  • Q: How to scale Redis session store? Use clustering (Redis Cluster), sharding, or a managed service (ElastiCache) and monitor memory usage and eviction policies; add LRU and TTLs to avoid unbounded growth.
Quick checklist to state vs stateless decisions:
  1. Does the feature require persistent connection (websocket)? If yes, plan for stateful connection management.
  2. Can the state be externalized to a durable store? Prefer externalizing.
  3. Is revocation and security critical? Prefer opaque tokens or short-lived JWTs with revocation.
  4. Is horizontal scaling a primary goal? Prefer stateless design.

This answer is tailored for interview settings: give concrete examples, explain trade-offs, and show you can design both stateless-by-default systems and pragmatic stateful solutions when required.
