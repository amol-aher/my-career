Adapter pattern to integrate with external APIs in Ruby

Intent: convert the interface of a class into another interface clients expect. For API integrations, adapters normalize different provider APIs to your canonical interface.

Example scenario

You have an internal InventoryService with method update_stock(sku, delta). Different providers (Shopify, Amazon) have different endpoints and auth. Implement adapters that conform to the internal interface.

module InventoryProvider
  def update_stock(sku, delta)
    raise NotImplementedError
  end
end

class ShopifyAdapter
  include InventoryProvider

  def initialize(client)
    @client = client
  end

  def update_stock(sku, delta)
    @client.post('/inventory_levels/adjust', {sku: sku, available_adjustment: delta})
  end
end

class AmazonAdapter
  include InventoryProvider

  def initialize(client)
    @client = client
  end

  def update_stock(sku, delta)
    # Amazon SP-API call with SigV4 signed request
  end
end

# usage
provider = ShopifyAdapter.new(shopify_client)
InventoryService.update_stock('SKU123', -1) # delegates to provider

Benefits

  • Decouples business logic from vendor APIs
  • Centralizes provider-specific logic (auth, retries, transformations)
  • Makes testing easier — stub adapters rather than external HTTP calls

Design considerations

  • Use a factory or registry to construct adapter instances based on config.
  • Keep adapters thin — heavy logic (mapping, rate-limiting) belongs in shared components.
  • Wrap network calls with retry/backoff and translate provider errors to domain errors.

Interview tip

Explain how adapters let you add new providers without changing core services; show how you'd test with recorded HTTP interactions and contract tests.
