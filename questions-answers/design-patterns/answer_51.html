How to structure a Rails app with complex business logic across multiple domains

Summary: For complex domains, prefer a modular, domain-oriented structure: isolate bounded contexts, keep a thin Rails surface (controllers/AR), move domain logic into PORO domain services, use explicit interfaces (repositories/adapters), and adopt an event-driven boundary between domains. This gives maintainability, testability and clear team ownership.

High-level principles

  • Bounded contexts: Identify domain boundaries (orders, billing, inventory, integrations) and isolate code and data where practical.
  • Separation of concerns: Keep persistence (AR) separate from domain logic: domain objects, services and policies.
  • Composition over inheritance: Use modules/concerns sparingly and prefer services, repositories and presenters for responsibilities.
  • Explicit dependencies: Inject services/adapters to make boundaries testable and replaceable.
  • Event-driven integration: Use domain events to decouple domains and enable asynchronous processing and eventual consistency.

Recommended folder/layout (modular monolith)

app/
  controllers/
  models/ (AR models only)
  services/          # orchestration & application services
  domain/
    orders/
      entities/      # plain Ruby domain entities, value objects
      services/      # domain services (business rules)
      repositories/  # repository adapters to AR
      events/        # domain event definitions
      projections/   # read models
    billing/
    inventory/
  queries/           # Query objects
  presenters/        # view presenters / decorators
  workers/           # background tasks
  policies/          # authorization
  serializers/       # JSON views

How domains interact

Use an application service or mediator at a boundary. Domain services emit events (e.g., order.created) to an event bus (Kafka, Redis streams, or RailsEventStore). Other domains subscribe and react by projecting read models or invoking their own domain logic.

Persistence & repositories

  • Keep ActiveRecord models thin, mapping to DB schema and relationships.
  • Implement repository adapters in domain/*/repositories which contain queries and transformations to/from AR models so domain code doesn't import AR directly.

Example: order flow simplified (code snippets)

# app/domain/orders/services/create_order.rb (domain service)
class Orders::CreateOrder
  Result = Struct.new(:ok?, :order, :errors)

  def initialize(order_repo: Orders::Repository.new, payments: Payments::Gateway.new)
    @order_repo = order_repo
    @payments = payments
  end

  def call(attrs)
    order = Orders::Entity.new(attrs)
    return Result.new(false, nil, order.errors) unless order.valid?

    @order_repo.transaction do
      persisted = @order_repo.save(order)
      payment = @payments.charge(persisted)
      raise PaymentError unless payment.success?
      EventBus.publish('order.created', order_id: persisted.id)
      Result.new(true, persisted, nil)
    end
  rescue => e
    Result.new(false, nil, [e.message])
  end
end

# app/domain/orders/repositories/orders_repository.rb
class Orders::Repository
  def save(order_entity)
    OrderRecord.create!(order_entity.to_h)
  end

  def transaction(&blk)
    ActiveRecord::Base.transaction(&blk)
  end
end

Testing strategy

  • Unit-test domain services and entities without touching DB (use repository test doubles).
  • Integration tests for repositories and AR mappings (small suite).
  • End-to-end tests for flows and event handlers.

Deployment & operational notes

  • Start as a modular monolith: use namespaces and engines only if you need independent deployments.
  • Use feature flags for migrations and schema changes across domains.
  • Integrate monitoring per domain: trace requests, event lag, and error rates.

Team & ownership

Assign domain owners. Keep change scopes small and use clear contracts (events + repository interfaces) between teams to reduce coordination overhead.

Interview tips

Draw the separation of layers: controllers -> application services -> domain -> repositories -> AR. Explain how this structure helped you ship features faster, reduced regressions, and improved tests.
