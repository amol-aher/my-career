Callbacks vs Observer pattern in Rails

Short answer: ActiveRecord callbacks are lifecycle hooks on a model (tight coupling). The Observer pattern decouples producers and consumers — observers subscribe to events and react independently. Rails provides both callbacks and higher-level pub/sub via ActiveSupport::Notifications or explicit observer classes.

ActiveRecord callbacks

Callbacks are methods defined on the model and invoked at lifecycle points: before_validation, before_save, after_commit, etc.

class Order < ApplicationRecord
  before_validation :set_order_number
  after_commit :enqueue_fulfillment_job, on: :create

  private

  def set_order_number
    self.number ||= SecureRandom.hex(6)
  end

  def enqueue_fulfillment_job
    FulfillmentJob.perform_later(id)
  end
end

Observer pattern & decoupling

Observers are external classes or subscribers that listen for model events and handle side effects. They remove responsibilities from the model and enable multiple subscribers.

# using ActiveSupport::Notifications
class Order < ApplicationRecord
  after_commit :publish_created_event, on: :create
  def publish_created_event
    ActiveSupport::Notifications.instrument('order.created', order_id: id)
  end
end

# subscriber (initializer)
ActiveSupport::Notifications.subscribe('order.created') do |*args|
  event = ActiveSupport::Notifications::Event.new(*args)
  OrderMailer.with(order_id: event.payload[:order_id]).confirmation.deliver_later
  Analytics.track('order_created', event.payload)
end

Use caseSimple lifecycle maintenanceMetrics, emails, integrations, cross-cutting concerns

Best practices

  • Use callbacks for model-intrinsic logic (setting defaults, validation-related state).
  • Prefer observers/notifications for side effects (emails, metrics, integrations).
  • Use after_commit when publishing events to ensure DB transaction success.
  • Keep callbacks small — delegate complex work to services or background jobs.

Interview follow-ups

  • Q: How to avoid ordering issues with multiple subscribers? Use durable queues (Sidekiq), ensure idempotency, and design for eventual consistency.
  • Q: When to use Rails observers gem? Historically there was an observer pattern gem; today ActiveSupport::Notifications or explicit subscriber classes are recommended.
