Using the Policy pattern (Pundit) in Rails

When to use: authorization rules that determine whether a user can perform an action on a resource. Policies centralize authorization logic and keep controllers & models clean.

Basic Pundit example

# app/policies/post_policy.rb
class PostPolicy
  attr_reader :user, :post

  def initialize(user, post)
    @user = user
    @post = post
  end

  def update?
    user.admin? || post.author_id == user.id
  end

  def destroy?
    user.admin?
  end

  def show?
    post.public? || post.author_id == user.id || user.admin?
  end
end

# controller
class PostsController < ApplicationController
  before_action :set_post, only: [:show, :update, :destroy]

  def update
    authorize @post
    @post.update!(post_params)
    head :no_content
  end
end

Policy scopes

# app/policies/post_policy.rb
class PostPolicy < ApplicationPolicy
  class Scope
    def resolve
      if user.admin? then Post.all
      else Post.where(public: true).or(Post.where(author_id: user.id))
      end
    end
  end
end

# controller
@posts = policy_scope(Post)

Advantages

  • Separation of authorization from controllers/models.
  • Easy to test policies in isolation.
  • Consistent usage via authorize and policy_scope.

Alternatives & extensions

  • CanCanCan — a different flavor that uses abilities/DSL.
  • Custom policy implementations — if you want less gem dependency.

Edge cases

  • Complex business rules mixed with authorization — keep policy limited to permission-checking and delegate complex logic to policy helpers or services.
  • Performance — avoid heavy DB work inside policy methods; push expensive operations into scopes and index accordingly.

Interview tip

Explain how you keep policy logic small, test policy methods & scopes, and how you handle multi-tenant or attribute-based access control (ABAC) scenarios.
