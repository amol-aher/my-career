How Rails Concerns relate to design patterns

Concerns are simply modules used to share behavior across models or controllers (e.g., app/models/concerns). They are a form of composition (mixins) and help implement cross-cutting patterns.

Common usage

# app/models/concerns/trackable.rb
module Trackable
  extend ActiveSupport::Concern

  included do
    has_many :events, as: :trackable
    after_create :track_create
  end

  def track_create
    events.create!(action: 'create')
  end
end

# model\ nclass Article < ApplicationRecord
  include Trackable
end

Relation to patterns

  • Decorator / Presenter: concerns aren't decorators but can provide shared helpers that decorators might use.
  • Strategy / Policy: concerns can provide shared strategies or policy helpers across multiple classes.
  • DRY composition: concerns are an implementation of the composition-over-inheritance principle.

Pitfalls & best practices

  • Avoid large "God" concerns with many responsibilities — split by responsibility (SRP).
  • Prefer explicit dependencies: document methods a concern expects to exist in the including class.
  • Use concerns for small, reusable behavior (auditing, tagging, soft deletes), not for large workflows.

Interview tip

Explain how concerns help you reuse code but also show a real refactor where you extracted behavior into a concern and later split it to avoid a God module.
