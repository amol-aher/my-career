Code Review Checklist

A lead-level checklist that I use during reviews. Organized by priority (Blocking → Important → Nice-to-have) with concrete examples and reviewer comment templates you can reuse.

Why a checklist?

Code reviews aim to ensure correctness, safety, maintainability and team knowledge-sharing. A checklist reduces cognitive load, ensures consistent coverage, and helps junior reviewers learn what's important.

Top-level quick-scan (first 60–120s)

  • Does the PR description explain intent, scope, migration steps, and how to test? (look for reproduction steps)
  • Does the change match the stated scope (no unrelated churn)?
  • Are there automated tests and CI passing?
  • Any DB migration or external dependency changes? (mark as high risk)

Detailed checklist (grouped)

Correctness & Business Logic (Blocking)

  • Does the code implement the stated requirement? Validate assumptions by reading a few code paths and tests.
  • Edge cases handled? (nil/empty inputs, invalid params, concurrent writes)
  • Are invariants preserved? (data integrity, transactional boundaries)

Tests & QA (Blocking)

  • Are there unit/integration tests covering the new behavior and common edge cases?
  • Do tests assert observable outcomes (DB changes, side effects, API responses) rather than internal implementation?
  • Is test data deterministic and isolated? Long-running flakiness or use of sleep is a smell.

Data & Migrations (Blocking)

  • Are migrations reversible or backward-compatible for zero-downtime deploys?
  • Does the migration lock large tables? If so, is there a plan to mitigate (batched migrations, pt-online-schema-change, safer alter sequences)?
  • Is data migration validated and monitored? Are there roll-back steps documented?

Security & Privacy (Blocking)

  • Any user input being interpolated into SQL/HTML/commands? Check for SQL-injection, XSS, command injection.
  • Are secrets and credentials handled safely (no secrets in code or logs)?
  • Verify authorization checks — not only authentication. Is access control enforced at controller and service boundaries?

Performance & Scalability (Important)

  • Database query count and shape — watch for N+1 queries (look for `.includes` vs N+1 patterns).
  • Are heavy operations done in request thread? Consider background jobs, streaming responses, pagination.
  • Caching strategy — appropriate caching and cache invalidation explained?

Observability & Error Handling (Important)

  • Are errors handled and logged with enough context (request id, user id) and without leaking PII?
  • Are metrics and traces emitted for important flows? Any new external calls instrumented for latency/errors?
  • Are exceptions re-thrown where necessary, or swallowed silently?

Maintainability & Readability (Important)

  • Is the code easy to read? Prefer expressive variable names and small functions.
  • Is there duplication that should be extracted?
  • Are public method signatures and side effects clear? Add docstrings where behavior is non-obvious.

Architecture & Design (Important)

  • Does the change follow the project's architectural patterns? If diverging, is there an architecture note rationalizing the choice?
  • Is coupling and cohesion balanced — avoid introducing tight coupling between unrelated modules.

Frontend-specific (Vue.js) (Important/Nice-to-have)

  • Component reactivity and props — avoid mutating props, prefer emits for parent communication.
  • Are components small and reusable? Is state management (Vuex/Pinia) used appropriately?
  • Accessibility basics (labels, keyboard, aria) and responsive behavior.

DevOps & CI (Important)

  • Will this change impact build time, deploy sequence, or infra (new env vars, SQS topics, IAM changes)?
  • Are releases safe? Are feature flags used for risky features?

Licensing & Third-party (Nice-to-have)

  • Does adding a new dependency introduce licensing, security or maintenance concerns?

Common subquestions & answers

Q: How large should a PR be?

A: Aim for PRs that are conceptually small. Good practical rules: under 400–800 lines of change, focused on one intent. When a change spans multiple subsystems, consider an architecture note and break into smaller PRs. Small PRs review faster and reduce risk.

Q: How to handle style nits?

A: If the project has an auto-formatter (RuboCop, Prettier), prefer to auto-fix style. Leave only higher-level style discussions for PR comments and avoid bikeshedding. Use "nit" comments for trivial preferences.

Q: How to review migrations safely?

A: Look for non-blocking migrations (ADD COLUMN with default causes table rewrite in Postgres). Prefer null-then-backfill-then-constraint approach. Request a rollout plan for large tables and confirm monitoring/rollback steps.

Q: What to do when you discover an architectural smell?

A: For smaller issues suggest refactors with examples. For larger architecture problems, ask the author to open a design/ADR and schedule a synchronous discussion if needed.

Usage tip: Keep a short, team-specific review checklist in your PR template so reviewers and authors converge on expectations.
