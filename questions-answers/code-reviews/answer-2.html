Performance Metrics I Monitor for Controllers / API Requests

High-level SLIs & SLOs

  • Availability / Error rate — success rate of requests (HTTP 2xx vs 5xx/4xx), e.g., SLO 99.9% for 5xx-free responses.
  • Latency percentiles — p50, p90, p95, p99 per endpoint. SLOs often defined on p95 or p99 (e.g., p95 < 300ms).
  • Throughput — requests per second (RPS) and concurrency.

Endpoint-level telemetry (what I instrument)

  • Request Duration (total time): server-side wall clock measured at entry/exit (include p50/p95/p99).
  • DB Time: total time spent executing queries for a request (by summing SQL durations).
  • # of DB queries: watch for increases or spikes (N+1s).
  • External call latency & error rate: downstream APIs, payment gateways, S3, etc.
  • Allocations / memory churn per request (Ruby objects allocated) — high allocations can increase GC pause times.
  • CPU and memory usage per service (aggregate) and per container/pod if applicable.
  • Cache hit ratio for crucial caches (Redis/memcached).
  • Payload size (request and response) and compression effectiveness.
  • Queue/Background job lag when requests enqueue work instead of handling synchronously.

Why these metrics matter (examples)

  • High p95 with low p50: indicates tail latency — perhaps a single slow DB query or expensive I/O. Focus on p95/p99 for user experience.
  • Rising # of DB queries: typical sign of N+1 after a change — use Bullet or log slow queries.
  • High allocations: Ruby-specific signal that GC overhead will increase; consider object allocation reduction or reuse.

Tools & techniques

Prometheus + Grafana Datadog / NewRelic / Dynatrace Skylight / Scout (Rails profiling) ActiveSupport::Notifications Rack-mini-profiler Bullet (detect N+1) pg_stat_statements / EXPLAIN ANALYZE

Instrument both application and infrastructure. Use tracing (OpenTelemetry) to follow requests across services.

Practical controller-level checks I do when reviewing code

  1. Is the controller doing heavy work? Move to a service/background job if CPU/IO heavy.
  2. Is pagination applied on list endpoints? Avoid returning unbounded result sets.
  3. Are database queries eager-loaded where needed to avoid N+1 (`includes`, `preload`)?
  4. Are slow queries explained with indexes and alternative plans (EXPLAIN ANALYZE)?
  5. Is caching leveraged for idempotent, read-heavy endpoints (HTTP cache headers, ETag, fragment caches)?

Common performance issues and remediation

  • N+1 queries — detect with Bullet; fix with `includes` or query redesign, batch loads.
  • Large payloads — paginate, stream responses, or send summarized data.
  • Slow DB queries — add indexes, rewrite queries, denormalize, materialized views, or precompute.
  • High GC pause — reduce allocations, use object pools, tune Ruby GC flags, or scale horizontally.
  • Third-party slowdowns — add circuit breakers, timeouts, fallbacks, or make calls asynchronous.

How to set thresholds & alerts

  • Use historical baselines per endpoint to set p95/p99 thresholds rather than flat values across the board.
  • Alert on relative anomalies (e.g., p95 increased by 2x in last 1h) and on absolute breach (p95 > target).
  • Combine alerts: p95 + error rate + DB slow queries to reduce noisy/irrelevant alerts.

Subquestions & short answers

Q: How do I profile a slow endpoint in production?

Capture traces (OpenTelemetry), enable request sampling, inspect DB slow logs and use flamegraphs (Skylight) to find hotspots. Reproduce in staging with representative data, then run benchmarks.

Q: How to detect N+1 in review?

Search diffs for iterations calling associations inside loops (`each` + `user.posts.count`) or for code that fetches associations lazily. Ask for a query count metric or a Bullet log snippet.

Q: Should I optimize prematurely in controllers?

No. Prioritize correctness and clarity. Optimize when you have evidence: metrics or reproducible slowness. Use profiling to validate optimizations.

Tip: keep a lightweight "performance checklist" in the PR template to encourage authors to include benchmarks, query counts, and expected traffic/scale.
