Memory leaks and GC issues caused by metaprogramming — examples and fixes

Yes — metaprogramming can cause leaks. Below are typical patterns I've encountered in production and how I fixed them.

Common causes

  • Massive creation of anonymous classes/modules (Class.new inside loops) — each class remains reachable if referenced or constantized.
  • Per-object singleton classes for many objects (heavy use of define_singleton_method or extend).
  • Closures holding large objects (blocks capturing big arrays or DB connections).
  • Persistent caches keyed by dynamic method names or objects without eviction.

Diagnosis techniques

  • Use ObjectSpace.each_object(Class).count or ObjectSpace.each_object(Module) to find class churn.
  • Use memory profilers: memory_profiler, derailed_benchmarks, or Ruby's ObjectSpace for heap dumps.
  • Check GC stats: GC.stat, and use flamegraphs for allocations.

Concrete fixes with examples

1) Reuse classes or modules instead of creating many

# Bad: inside a loop
1000.times do |i|
  klass = Class.new { define_method(:foo) { i } }
  # storing klass somewhere keeps it alive
end

# Fix: reuse or store only necessary behavior
shared_module = Module.new do
  def foo; @i end
end
# then use lightweight objects with instance variables rather than generating classes

2) Avoid capturing large objects in closures

# Bad
big = BigObject.load!
define_method(:use_big) { big.do_something } # big stays alive

# Fix: copy minimal needed data
min = big.minimal_representation
define_method(:use_big) { min.process }

3) Use WeakRef for caches that should not keep objects alive

require 'weakref'
cache = {}
obj = SomeBig.new
cache[:obj] = WeakRef.new(obj)
# later
begin
  strong = cache[:obj].__getobj__
rescue WeakRef::RefError
  # object collected
end

4) Remove dynamically defined constants when no longer needed

k = Object.const_set("TmpClass#{i}", Class.new)
# use it
Object.send(:remove_const, "TmpClass#{i}") if Object.const_defined?("TmpClass#{i}")

Operational mitigations

  • Limit lifetime of dynamic objects (scoped work in background job with process restart).
  • Use process recycling for long-lived servers (Puma phased restart, Kubernetes pod restarts) when leaks can't be eliminated quickly.
  • Tune GC settings (RUBY_GC_HEAP_* and others) and consider using jemalloc.

Summary

Metaprogramming can create memory pressure but with monitoring (ObjectSpace, profilers), safer patterns (reuse, WeakRef), and lifecycle management you can eliminate or mitigate leaks.
