Building a safe sandboxed evaluator for Ruby code snippets

Running arbitrary Ruby code safely is hard. The most robust solution is to run untrusted code out-of-process with hard OS-level restrictions. Below are patterns, trade-offs, and a practical example.

Requirements checklist

  • Process isolation (fork/exec) or containerization.
  • Resource limits (CPU, memory, disk, file descriptors).
  • Timeouts to avoid infinite loops.
  • No sensitive data or credentials available to the child.
  • Controlled networking (deny outbound access).
  • Safe library loading (restrict require/load).

Recommended architecture

  1. Run the snippet in a docker container or sandboxed VM with a restricted user.
  2. Set ulimits (ulimit -v, -t) and cgroups to bound memory and CPU.
  3. Mount a read-only filesystem or ephemeral tmpfs for execution.
  4. Use a small bootstrapper binary that loads a minimal Ruby interpreter and runs the code.
  5. Collect stdout/stderr and ensure the parent enforces a wall-clock timeout and kills the container if exceeded.

Practical lightweight example (subprocess + timeout)

require 'open3'
def run_safely(code, timeout: 2)
  # Note: this is a simple example, not a complete secure sandbox.
  cmd = "ruby -e #{Shellwords.escape(code)}"
  stdout = ''
  stderr = ''
  status = nil

  Open3.popen3(cmd) do |i,o,e,t|
    i.close
    begin
      Timeout.timeout(timeout) do
        stdout = o.read
        stderr = e.read
      end
    rescue Timeout::Error
      Process.kill('KILL', t.pid) rescue nil
      return {error: 'timeout'}
    end
    status = t.value
  end
  {stdout: stdout, stderr: stderr, status: status.exitstatus}
end

# Usage:
run_safely("puts 'hello'; STDOUT.flush", timeout: 1)

Warnings: The above approach still runs arbitrary Ruby on the host. Use containers or restricted VMs for production.

Advanced controls

  • Use seccomp / AppArmor to restrict syscalls inside containers.
  • Network isolation: disable networking or use internal network with strict egress rules.
  • Filesystem: run with no persistent mounts and no access to secrets.
  • Use wasm/other sandboxed runtimes: compile Ruby in a restricted interpreter or run code in WASM for stronger sandboxing guarantees.

Alternatives

  • Use a domain-specific non-Turing-complete language for user snippets (safer and easier to sandbox).
  • Expose a safe API/DSL instead of raw Ruby — interpret allowed expressions only.

Conclusion

Do not run untrusted code in-process. Use containers/VMs, strict OS-level limits, and short timeouts. For full safety combine multiple isolation layers (containers, cgroups, seccomp) and audit continuously.
