How method_missing works, how to use it, and dangers of overuse

Short explanation: method_missing(name, *args, &block) is invoked when Ruby's method lookup cannot find a method. You can override it to provide dynamic behavior, delegation, or DSL-like syntax. But it must be used carefully — it can mask bugs, break introspection, and hurt performance.

How it works (lookup flow)

  1. Ruby looks up the method name in the receiver's method table and its ancestors.
  2. If not found, Ruby calls method_missing on the receiver.
  3. If method_missing calls super, a NoMethodError is raised.

Method signature

def method_missing(name, *args, &block)
  # name is a Symbol
  super # to raise NoMethodError when appropriate
end

Common usages

  • Delegation / Proxy: forward unknown methods to an internal object.
  • Lazy define: handle first call dynamically and define a concrete method for subsequent calls.
  • DSLs: interpret method names and arguments as commands.
  • Compatibility layers: support legacy method names or provide shims.

Examples

Simple delegation

class Proxy
  def initialize(target) @target = target end

  def method_missing(name, *args, &block)
    if @target.respond_to?(name)
      @target.public_send(name, *args, &block)
    else
      super
    end
  end

  def respond_to_missing?(name, include_private=false)
    @target.respond_to?(name, include_private) || super
  end
end

Define-on-first-call (performance)

class Lazy
  def method_missing(name, *args, &block)
    self.class.define_method(name) do |*a, &b|
      # computed logic
      "computed #{name} with #{a.inspect}"
    end
    send(name, *args, &block)
  end

  def respond_to_missing?(name, include_private=false) true end
end

Dangers and pitfalls

  • Masks bugs: A typo in method name may silently be handled and return unexpected results rather than raising an error.
  • Introspection breaks: respond_to?, methods, and doc tools won't recognise virtual methods unless respond_to_missing? is implemented.
  • Performance: method_missing is slower than direct method calls; heavy use in hot paths is costly.
  • Infinite recursion: Calling undefined helper method inside method_missing can re-enter the same path leading to stack overflow.
  • Thread-safety: Dynamically defining methods in multi-threaded code requires synchronization.
  • Visibility and security: Ensure you don't unintentionally expose private methods or secrets via delegation.

Best practices

  1. Always implement respond_to_missing? to reflect dynamic methods.
  2. Check whether you can define_method instead — it's often clearer and faster.
  3. Limit the scope: only respond to a narrow set of method name patterns.
  4. Use explicit exceptions and clear messages when rejecting unknown names.
  5. Add thorough unit tests for dynamic behavior.

Subquestions you may get

Q: When should I use method_missing vs define_method?

Use method_missing when you need very flexible catch-all behavior. If you can determine methods that will be used, prefer define_method at class-definition time or define-on-first-call for performance.

Q: How to avoid interfering with private methods?

Use public_send when delegating to ensure you don't call private methods unintentionally. Honor the include_private parameter in respond_to_missing? if appropriate.

Conclusion

method_missing is a useful metaprogramming primitive but should be used with restraint and proper safeguards (respond_to_missing?, tests, define-on-first-call) to avoid the common pitfalls.
