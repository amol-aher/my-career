Safely adding behavior to core classes (String, Array, etc.)

Adding behavior to core classes can be risky. Here are safe strategies and examples.

Avoid global monkey-patching

Prefer alternatives that limit scope:

  • Refinements: Lexical, non-invasive (use using).
  • Wrapper classes / utility modules: Compose behaviors instead of altering core classes.
  • Sub-classing: Create a subclass when appropriate (less common for String/Array).
  • Explicit namespacing: Add helper modules with namespaced methods (e.g., StringHelpers.palindrome?(s)).
  • Extending single objects: Use obj.extend(Module) to add behavior to one instance only.

Example: refinement (safe)

module MyStringRefinements
  refine String do
    def reverse_words
      split(/\s+/).reverse.join(' ')
    end
  end
end

using MyStringRefinements
"hello world".reverse_words # => "world hello"

Example: wrapper helper (safe)

module StringHelpers
  def self.reverse_words(s)
    s.split(/\s+/).reverse.join(' ')
  end
end

StringHelpers.reverse_words("a b c") # => "c b a"

Example: extend a single object

s = "hello world"
s.extend(Module.new { def shout; upcase + '!' end })
s.shout # => "HELLO WORLD!"

When monkey-patching may be acceptable

  • Polyfills for missing language features across platforms (documented and minimal).
  • Short-lived migration shims with a clear removal plan.
  • Tests covering interactions and a controlled release.

Mitigation and governance

  1. Code review policy prohibits undocumented core changes.
  2. CI tests include full regression tests to detect breakages across gems.
  3. Use linters to detect reopenings of core classes.
  4. Document any additions and provide a deprecation/migration plan.

Summary checklist

  • Can we implement this as a wrapper/refinement/subclass? Prefer that.
  • If we must patch, scope it tightly and add tests.
  • Use semantic names to avoid collisions (eg. namespacing).

Conclusion

Prefer non-invasive approaches (refinements, wrappers, extend single objects). When global patches are unavoidable, govern them with strict tests, documentation, and a migration plan.
