Approach to building an ActiveRecord-like query DSL using metaprogramming

An ActiveRecord-like DSL is chainable, lazy, composable, and maps Ruby expressions to SQL safely. Below is a high-level design, tactical choices, and a small implementation sketch showing the essential techniques.

Design goals

  • Immutable, chainable Relation objects (calls like .where return a new relation).
  • Lazy evaluation—SQL is generated and executed only when needed (to_a, first, count).
  • Safe parameter binding to avoid SQL injection.
  • Pluggable adapters for different SQL dialects.
  • Ability to define dynamic scopes and named queries (metaprogramming).

Core components

  1. Relation — holds a query AST (conditions, order, limit).
  2. Node/AST — small objects representing predicates (AND/OR/Column/Eq).
  3. Adapter / SQL Generator — turns AST into SQL + bind params.
  4. Model class methods — .where, .select, .order, and dynamic finders.

Simple implementation sketch

# A minimal relation-ish implementation
class Relation
  attr_reader :table, :where_clauses, :limit_count
  def initialize(table, where_clauses = [], limit_count = nil)
    @table = table
    @where_clauses = where_clauses
    @limit_count = limit_count
  end

  def where(cond, *binds)
    Relation.new(table, where_clauses + [[cond, binds]], limit_count)
  end

  def limit(n)
    Relation.new(table, where_clauses, n)
  end

  def to_sql
    sql = "SELECT * FROM #{table}"
    unless where_clauses.empty?
      parts = where_clauses.map { |c, binds| "(#{c})" }
      sql += " WHERE " + parts.join(" AND ")
    end
    sql += " LIMIT #{limit_count}" if limit_count
    sql
  end

  def to_a(connection)
    sql = to_sql
    connection.execute(sql) # naive - prefer prepared statements
  end
end

# Model sugar
class Model
  def self.table_name(name = nil)
    @table_name = name if name
    @table_name || self.name.downcase + "s"
  end

  def self.all
    Relation.new(table_name)
  end

  def self.where(cond, *binds)
    all.where(cond, *binds)
  end
end

Using metaprogramming for convenience

  • Dynamic finders / attribute methods: define attribute accessors based on schema via define_method when model class is loaded.
  • Named scopes: def self.scope(name, body); define_singleton_method(name, &body); end
  • SQL generation: use an AST builder (Arel-like) instead of concatenating strings.

Example: define named scope

class Model
  def self.scope(name, &block)
    define_singleton_method(name) do |*args|
      instance_exec(*args, &block)
    end
  end
end

class User < Model
  scope :recent, ->(n=5) { all.order("created_at DESC").limit(n) }
end

Important engineering considerations

  • SQL injection: Use prepared statements and parameter binding. Never interpolate user input into SQL strings.
  • Performance: Keep relations lazy and build SQL only when necessary; cache prepared statements; use connection pooling.
  • Testing: Unit test SQL generation and integration test against a real DB.
  • Migrations & schema introspection: Dynamically define attribute methods based on schema metadata.
  • Extensibility: Keep AST and SQL generator separate; add adapter-specific generators.

Summary

Implementing an ActiveRecord-like DSL requires clear abstractions (Relation, AST, Adapter) and careful use of metaprogramming for ergonomics (define_method, scopes). Prioritize safety (parameter binding) and performance (lazy evaluation and caching).
