Trade-offs between method_missing and define_method for dynamic behavior

Behavioral comparison

Aspectmethod_missingdefine_method
PerformanceSlower on each call (dispatch via missing path)Fast (normal method dispatch)
MemoryLower memory (one handler) initiallyMore memory (many methods)
DiscoverabilityPoor (respond_to? must be implemented)Good (methods visible)
ComplexitySimple to implement catch-allBetter explicit control, but may require generating many methods
Use caseFlexible DSLs, ad-hoc handlingGenerated APIs, attribute accessors, performance-critical features

Best compromise: define-on-first-call

def method_missing(name, *args, &blk)
  if can_handle?(name)
    self.class.define_method(name) do |*a, &b|
      handle(name, *a, &b)
    end
    send(name, *args, &blk)
  else
    super
  end
end

This pattern gives the simplicity of method_missing initially and the performance of defined methods subsequently.

When to choose which

  • Use method_missing for flexible DSLs or where it's infeasible to enumerate expected methods.
  • Use define_method for known patterns and when you want good IDE support and performance.
  • Prefer define-on-first-call when you need both flexibility and performance.

Additional considerations

  • Implement respond_to_missing? when using method_missing.
  • Document generated behavior to aid maintainers.
  • Be mindful of thread-safety when defining methods at runtime.

Summary

Method_missing is flexible but can be slow and opaque; define_method is explicit and fast. Use both strategically and consider define-on-first-call as a hybrid approach.
