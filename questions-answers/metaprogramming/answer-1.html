respond_to_missing? in Ruby

Short answer: respond_to_missing?(method_name, include_private = false) is the method you implement so that Ruby’s reflective method respond_to? (and related introspection) knows whether you handle certain method names dynamically (for example via method_missing).

Why it exists

When you implement method_missing to claim methods that don't exist at compile time, most introspection utilities (like respond_to?, methods, documentation tools, and other libraries) still only look at the object's concrete method table. To make introspection accurate you implement respond_to_missing? so respond_to? returns true for the virtual methods you can handle.

Signature and behavior

Method signature:

def respond_to_missing?(method_name, include_private = false)
  # return true/false
end

Implementation should call super when you don't handle the method, to preserve normal behavior (and to support inheritance correctly).

Example: Delegator / Proxy pattern

This is a common pattern: an object delegates unknown methods to an internal target.

class Proxy
  def initialize(target)
    @target = target
  end

  def method_missing(method_name, *args, &block)
    if @target.respond_to?(method_name)
      @target.public_send(method_name, *args, &block)
    else
      super
    end
  end

  def respond_to_missing?(method_name, include_private = false)
    @target.respond_to?(method_name, include_private) || super
  end
end

arr = Proxy.new([1,2,3])
arr.push(4)               # works via method_missing
arr.respond_to?(:push)    # => true (because respond_to_missing? says so)

Best practices

  • Always implement respond_to_missing? when you use method_missing to claim methods: this keeps introspection tools and other libraries happy.
  • Use super inside respond_to_missing? so that ancestor behavior is preserved.
  • Keep your logic simple and predictable—favor explicit definitions with define_method where possible rather than catching everything in method_missing.
  • Consider documenting dynamic methods in your README or YARD comments so users/developers know what methods are expected.

Pitfalls

  • If you forget respond_to_missing?, respond_to? (and many libraries/gems) will misreport capabilities.
  • Overly-broad method_missing + respond_to_missing? can make debugging and auto-complete painful.
  • Don't use eval carelessly in method_missing—it can introduce security and performance issues.

Subquestions (and answers)

Q: When is respond_to_missing? called?

Ruby's respond_to? implementation checks the object's method tables first; if not present, it calls respond_to_missing?(method_name, include_private). So implementers of method_missing should implement respond_to_missing?.

Q: Should I override respond_to? instead?

Generally no—override respond_to_missing? to keep compatibility and allow inheritance/super calls. Overriding respond_to? is more error-prone.

Q: How does include_private affect behavior?

If you can respond to private methods, honor include_private = true. Otherwise ignore it or forward appropriately.

Summary

respond_to_missing? is the companion to method_missing that keeps Ruby's reflection and libraries honest. Implement it whenever you claim methods dynamically and make sure to call super when appropriate.
