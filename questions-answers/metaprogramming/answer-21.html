Difference between eval, instance_eval, and class_eval

Quick summary:

  • eval(string, binding=nil) executes Ruby code in the given binding (default is caller's). It has full access to local variables of that binding and can create/modify locals/constants there.
  • instance_eval executes a block or string in the context of a specific object; inside the block self becomes that object. It's used to add per-object behavior or evaluate DSL blocks on an object instance.
  • class_eval (a.k.a. module_eval) executes a block or string in the context of a class or module; it's typically used to define instance methods dynamically on that class.

Behavioral differences & examples

eval

x = 1
eval("x + 2") # => 3

# eval with binding (access a local variable in method scope)
def test_eval
  local = 10
  eval("local + 5", binding) # => 15
end

instance_eval

obj = Object.new
obj.instance_eval do
  def secret; "only on this object" end
  @foo = 42
end

obj.secret    # => "only on this object"
# obj2 = Object.new; obj2.secret # NoMethodError

class_eval / module_eval

klass = Class.new
klass.class_eval do
  def hello; "hi" end
end

klass.new.hello # => "hi"

Local variables and closures

eval can access and modify local variables via a binding; instance_eval and class_eval with blocks capture closures differently:

  • define_method with a block captures surrounding local variables (closure).
  • class_eval with a string does not capture outer local variables; with a block it shares the block's lexical scope differently.

When each is appropriate

  • Avoid eval unless you absolutely must execute dynamic Ruby source from a trusted source. It's dangerous (code injection), hard to debug, and slows optimization.
  • Use instance_eval for building internal DSLs where a block needs to be evaluated on an object (e.g., configuration blocks).
  • Use class_eval for defining instance methods or inserting code into a class context dynamically. Prefer passing a block to avoid string eval.
  • Prefer define_method over string-based class_eval for safety and closure semantics.

When to avoid them

  • Never eval untrusted input — huge security risk.
  • Avoid using these in hot paths without benchmarking; dynamic code may prevent some interpreter optimizations.
  • Avoid widespread use that makes code hard to reason about — prefer explicit definitions or factory methods.

Practical patterns

# Safer: use define_method with closures rather than class_eval string
[:a, :b].each do |name|
  define_method(name) { instance_variable_get("@#{name}") }
end

Summary

All three allow dynamic code execution, but eval acts on bindings and local scope (most dangerous). instance_eval and class_eval are contextual — use them for DSLs and dynamic definitions, but prefer safer alternatives like define_method and avoid string eval.
