Ruby method lookup path (including modules, prepend, refinements, singleton classes)

Understanding Ruby's method lookup is vital for metaprogramming. Here's the conceptual order Ruby uses when resolving an instance method call:

High-level lookup order (instance method call)

  1. Singleton class (a.k.a. eigenclass) of the receiver — methods defined only on that object or class-level methods for class objects.
  2. Modules prepended into the singleton class (if any).
  3. The receiver's class (look for instance methods).
  4. Modules prepended into the class (in the order they were prepended, last prepended searched first).
  5. Included modules — modules included into the class are searched next (in reverse include order: last included first), including their included ancestors.
  6. Superclass chain — repeat steps 3–5 for each superclass up to Object and BasicObject.
  7. Method not found — method_missing on the original receiver is called.

Where refinements fit

Refinements are lexically scoped modifications to method lookup: when you write using SomeRefinement in a file or module, method calls in that lexical scope will prefer the refined method implementation when calling methods on the target class. Refinements are applied at the call site, not directly altering the global ancestor chain. Important notes:

  • Refinements are lexical (activated where using appears).
  • They can be disabled or not active inside eval'd strings or separate files that don't have the using statement.
  • Refinements have complex interaction with nested scopes and are intentionally conservative to avoid surprising global effects.

Examples and diagrams

# singleton methods / eigenclass
o = Object.new
def o.foo; :singleton end

class C; include M; prepend P; end
# Lookup when calling o.foo:
# 1. o's eigenclass -> methods defined on o
# 2. eigenclass prepended modules
# 3. C (the object's class)
# 4. modules prepended into C
# 5. modules included into C (reverse include order)
# 6. superclass chain

Notes & gotchas

  • prepend wins over class methods: Prepending a module places it earlier in the chain, so it can override methods and call super to reach the original implementation.
  • Multiple includes: Module inclusion order matters — last included module gets searched first.
  • Singleton ancestors: You can inspect the actual lookup chain with obj.singleton_class.ancestors and obj.class.ancestors.
  • Refinements are subtle: Because they are lexical, debugging can be confusing — a method call might behave differently inside a file that has using versus one that doesn't.

Practical tips

  • Use prepend for instrumentation and AOP-like wrappers (it supports super nicely).
  • Avoid complex chains of includes/ prepends unless necessary; prefer explicit composition.
  • Use singleton_class, ancestors, and method(:name).owner to inspect where a method is defined.

Inspecting lookup

module A; end
module B; end
class X; include A; prepend B; end

x = X.new
p x.singleton_class.ancestors
p X.ancestors
# Use method(:foo).owner to find where foo is located:
# p x.method(:foo).owner

Summary

The lookup path is deterministic: singleton class → class/prepends → includes → superclass chain → method_missing. Refinements operate at the caller's scope and can alter resolution for methods on specified classes in that lexical context.
