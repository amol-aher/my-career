How ActiveRecord implemented dynamic finders like find_by_name_and_email (older versions)

In older Rails (pre-4.x), ActiveRecord used method_missing to implement dynamic finders such as find_by_name_and_email. The idea: parse the method name to extract attribute names and compose a query.

How it worked (simplified)

def method_missing(method_name, *args, &blk)
  if method_name =~ /^find_by_(.+)$/
    attrs = $1.split('_and_')
    conditions = attrs.zip(args).map { |a, v| "#{a} = ?" }.join(" AND ")
    where([conditions, *args]).first
  else
    super
  end
end

To improve performance, Rails later used a define-on-first-call pattern: once a dynamic finder was invoked, Rails defined a concrete method (via define_singleton_method on the model class) so subsequent calls avoid method_missing overhead.

Why Rails moved away from many dynamic finders

  • Method explosion: large number of possible combinations made API surface hard to document and maintain.
  • Surprising behavior and subtle bugs when attribute names change or when associations are involved.
  • Encouraged brittle code that depended on method names rather than explicit queries.

Modern approach

Modern Rails recommends using where, find_by (with hash), or named scopes for clarity:

User.where(name: 'Ada', email: 'a@b.com').first
User.find_by(name: 'Ada', email: 'a@b.com')

Security considerations

When implementing dynamic finders, ensure safe parameter binding. Never interpolate user input into SQL.

Summary

Dynamic finders were a clever metaprogramming convenience implemented via method_missing and later optimized by dynamically defining methods. Rails moved to more explicit APIs for maintainability and clarity.
