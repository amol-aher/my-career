Differences between define_method and class_eval/module_eval

Both define_method and class_eval/module_eval allow you to create methods at runtime, but they behave differently in terms of lexical scope, closures, safety, and semantics.

Key differences

  • Lexical binding / closures: define_method accepts a block or Proc and preserves its surrounding lexical scope — it creates a closure capturing local variables. class_eval with a block evaluates the block in the context of the class but does not capture the outer lexical local variables in the same way.
  • Self and method body: In a define_method block, self inside the method (when called) is the instance, same as a normal method. With class_eval string, the method body is defined as if written in the class body and has its own lexical scope.
  • Use of super: Methods defined with class_eval behave like regular methods and support super normally. For define_method, using super inside the block behaves differently historically; modern Ruby versions handle it better but edge cases exist.
  • Safety: define_method avoids string eval and is safer than class_eval with strings. Prefer define_method to avoid parsing and security issues.
  • Source locations: Methods defined with class_eval using strings may show different source locations and can make backtraces less clear. define_method attaches the Proc's source location, which might point to the place where the block was created.

Examples

define_method

class User
  [:name, :email].each do |attr|
    define_method(attr) { instance_variable_get("@#{attr}") }
    define_method("#{attr}=") { |v| instance_variable_set("@#{attr}", v) }
  end
end

class_eval (block)

klass = Class.new do
  def greet
    "hello"
  end
end

klass.class_eval do
  def farewell
    "bye"
  end
end

class_eval (string)

klass.class_eval <<-RUBY
def dynamic_method(x)
  x * 2
end
RUBY

When to choose which

  • Use define_method when you need closures or want to avoid eval.
  • Use class_eval (with blocks) when you want to define multiple methods or want the method to behave as if it was defined in class body, including normal super behavior.
  • Avoid class_eval with strings unless you must generate code textually; prefer blocks or define_method.

Edge cases & gotchas

  • Keyword arguments and forwarding: historically there were differences in how define_method and class_eval handled keyword args; test on your Ruby version.
  • super from blocks passed to define_method can be surprising — favor class_eval if you rely heavily on super.

Conclusion

define_method is the safer, closure-friendly tool for runtime method creation. class_eval is useful when you want to create methods that behave like statically defined methods at the class body level. Choose based on the need for closure capture, super semantics, and safety.
