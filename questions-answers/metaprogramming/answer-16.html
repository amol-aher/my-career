Difference between send, public_send, and __send__

Ruby provides multiple message-sending helpers. They are crucial in metaprogramming when you need to invoke methods by name.

send

send(method_name, *args, &block) calls the method (even if it is private or protected). It bypasses Ruby visibility checks.

class Foo
  private
  def secret; "shh" end
end

f = Foo.new
f.send(:secret) # => "shh"

public_send

public_send respects Ruby's public visibility — it raises NoMethodError if the method is private or protected.

f.public_send(:secret) # => NoMethodError

__send__

__send__ is an alias for send. It's used to avoid clashing with objects that define their own send method. It behaves the same as send.

# If an object defines a custom send method:
class Bar
  def send; :custom end
end

b = Bar.new
b.send        # => :custom (calls the custom method)
b.__send__(:to_s) # invokes Kernel#__send__ to call :to_s

When to use which

  • Prefer public_send when calling methods by name from user input or external data to avoid invoking private methods accidentally.
  • Use send / __send__ when you intentionally need to access private/protected methods (rare, internal tools, or tests).
  • Use __send__ if objects might define their own send method to avoid ambiguity.

Security & safety tips

  • Never send user-supplied method names without validation — attackers could call sensitive private methods.
  • Prefer static dispatch when possible; using send widely reduces clarity and static analysis value.

Subquestion: relation to respond_to?

Before using public_send/send based on a method name, check respond_to? (or respond_to_missing?) to ensure the object claims to implement the method. Use the include_private flag if you plan to call private methods.

Conclusion

public_send for safe public dispatch, send (or __send__) for internal or reflective needs. Use the less permissive option when you can.
