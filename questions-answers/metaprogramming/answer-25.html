How closures capture variables when dynamically defining methods, and pitfalls

Ruby closures capture variables from their surrounding lexical scope. When you use define_method with a block, that block closes over local variables. This is powerful but can cause subtle bugs if loop variables or mutable objects are captured.

Common pitfall: loop variable capture

# wrong
methods = {}
3.times do |i|
  define_method("m#{i}") { i }
end
# All methods may return 3 (the final value) depending on the exact binding behavior

Fix: capture a fresh local inside the loop:

3.times do |i|
  j = i
  define_method("m#{j}") { j }
end

Examples

class C
  def initialize(label)
    @label = label
  end

  def build_methods
    (1..3).each do |n|
      val = "val#{n}"
      self.class.define_method("greet_#{n}") do
        "#{@label}: #{val}"
      end
    end
  end
end

c = C.new("X")
c.build_methods
c.greet_1 # => "X: val1"

Memory & GC considerations

Closures keep referenced objects alive. Capturing large objects for many dynamically defined methods can increase memory usage. If you only need a value at define-time, consider duplicating or freezing smaller values or passing them as method defaults.

Keyword args and arity

When building methods dynamically, be careful with keyword arguments and argument forwarding — Ruby versions differ in how blocks and define_method handle keyword splats. Test on your target Ruby versions.

Best practices

  • Prefer define_method with explicit local captures instead of string eval.
  • Use descriptive local variables inside loops to avoid accidental capture of the loop variable.
  • If defining many methods, consider generating a small data-structure and a single generalized method that reads it (tradeoff between memory and speed).

Conclusion

Closures are powerful and allow elegant metaprogramming, but be mindful of variable capture, memory, and Ruby-version differences. Explicitly capture variables when in doubt, and write tests to verify behavior.
