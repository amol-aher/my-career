How Ruby's constant lookup works, and how const_missing and autoload fit in

Constants in Ruby are resolved via a mix of lexical scope and ancestor lookup. When a constant lookup fails, const_missing on the module/class is invoked. autoload registers a file to be loaded the first time the constant is accessed.

Constant lookup basics

  1. If you reference a constant with a namespace (e.g., Foo::Bar), Ruby looks up Foo first then looks for Bar inside Foo.
  2. For unqualified constants (e.g., Bar inside a class definition), Ruby searches in the current lexical scope (the innermost module/class nesting), then it searches the inheritance chain of the current class/module, and finally falls back to looking in Object and its ancestors.
  3. Module.nesting and lexical scope affect resolution — constants defined in an enclosing module are found in nested definitions.

const_missing

When Ruby cannot find a constant, it calls const_missing on the module/class where the lookup took place. You can override const_missing to implement lazy-loading, dynamic constant generation, or friendly error messages.

module MyLib
  def self.const_missing(name)
    # attempt to autoload or compute constant
    if name == :Thing
      require_relative "my_lib/thing"
      const_get(name) # now available
    else
      super
    end
  end
end

Notes: Use super when you can't handle the constant, so Ruby raises the usual NameError. Overriding const_missing globally is dangerous — be narrow and explicit.

autoload

autoload(:MyClass, 'path/to/file') registers that file to be required the first time MyClass is referenced. It's a simple lazy-loading mechanism.

autoload :Foo, 'foo'  # when Foo is first referenced Ruby require 'foo'

Caveats: Historically autoload had thread-safety issues in multi-threaded programs. Many codebases prefer explicit require calls or use loader libraries (e.g., Zeitwerk in Rails) that provide thread-safe autoloading and predictable behavior.

Practical patterns

  • Use a loader library: In large apps, prefer a robust autoloader (Rails uses Zeitwerk) which handles nested constants, directories, and thread-safety.
  • Use const_missing sparingly: For glue code or very targeted lazy-loads; prefer autoload or explicit require where possible.
  • Provide clear error messages: If const_missing cannot resolve a constant, raise with a helpful message.

Example: namespaced autoload

module MyApp
  module Services
    autoload :Mailer, 'my_app/services/mailer'
  end
end

# Later, referencing MyApp::Services::Mailer will require the file automatically.

Subquestions you might encounter

Q: What's the difference between const_get and a plain constant reference?

const_get is runtime reflection that asks a module to return a named constant by symbol/string and can be used when the name is dynamic. Plain constant references are resolved at parse/runtime via Ruby's constant lookup rules.

Q: Should I override const_missing to implement autoloading?

Prefer explicit autoload or a loader (Zeitwerk) for large projects. Overriding const_missing is a useful technique for small, targeted cases, but can complicate debugging.

Conclusion

Ruby's constant lookup is flexible but has nontrivial rules. Use autoload or a proper loader for lazy-loading and reserve const_missing for targeted, well-documented behavior. Always call super when you can't handle a constant to preserve normal error semantics.
