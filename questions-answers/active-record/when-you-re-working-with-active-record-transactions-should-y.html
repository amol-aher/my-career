When you’re working with Active Record transactions, should you use ! (bang) methods or not?

Summary

Use bang methods (save!, create!, update!) inside transaction blocks when you want exceptions to be raised automatically on failure — this makes rollbacks reliable and keeps code simpler. Use non-bang methods when you want to handle validation failures gracefully without exceptions, but then you must explicitly control rollback behavior.

Deep dive — tradeoffs between bang and non-bang

  • Bang methods: raise exceptions (e.g., ActiveRecord::RecordInvalid) which will cause the transaction to rollback if uncaught. Good when failures are exceptional and you want to abort the entire operation.
  • Non-bang methods: return false on validation failure. This requires explicit checks and manual rollback (e.g., raise ActiveRecord::Rollback). Without explicit handling, you might end up with partial success or a commit with missing components.
  • Readability and maintainability: Bang methods lead to clearer intent in transactional flows and reduce boilerplate checks. Non-bang methods can be used when conditional logic needs to continue on validation failure.

Practical guidelines

  1. Prefer bang methods in transactional code paths where partial writes are unacceptable.
  2. If using non-bang methods, always check return values and raise/rollback explicitly on failure.
  3. Keep transactions short and don't call external services inside them; if you must, wrap external calls and handle compensating actions.

Code examples

# Preferred: bang methods inside transaction
ActiveRecord::Base.transaction do
  order = Order.create!(user: user, total: 100)
  charge = Payment.create!(order: order, amount: 100)
end

# If using non-bang, explicitly rollback
ActiveRecord::Base.transaction do
  order = Order.create(user: user, total: 100)
  unless order.persisted?
    raise ActiveRecord::Rollback, "Order invalid"
  end
  charge = Payment.create(user: order, amount: 100)
  unless charge.persisted?
    raise ActiveRecord::Rollback, "Payment failed"
  end
end

Interviewer follow-ups

  • Q: Are there cases where you prefer non-bang?
    A: Yes — when you want to accumulate errors and show validation messages to the user without using exceptions for control flow; but then don't forget explicit rollback handling.
  • Q: What about performance/exception cost?
    A: Raising exceptions has a small cost but is negligible compared to DB work; clarity and correctness usually trump micro-optimizations.
