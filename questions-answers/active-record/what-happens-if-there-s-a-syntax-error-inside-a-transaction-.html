What happens if there’s a syntax error inside a transaction block after creating records?

Summary

There are two things to clarify: a syntax error (a Ruby parse-time error) and a runtime exception occurring inside the transaction. A true syntax error prevents the code from loading/being executed at all (you'll get a SyntaxError at parse/require time). A runtime exception raised after creating records will cause the transaction to rollback (unless it's rescued inside the transaction block). After rollback, after_commit callbacks will not run; after_rollback callbacks will.

Details — SyntaxError vs RuntimeError

  • SyntaxError (parse-time): If the Ruby interpreter encounters a syntax error while parsing the file, the code won't run and the transaction won't start — you will see a SyntaxError before any DB operations are executed. This is a developer-time error and must be fixed before running.
  • Runtime exception: If your code executes and then a runtime exception occurs inside the transaction block (e.g., NoMethodError, RuntimeError), Rails will rollback the transaction. Any writes performed during the transaction will be reverted.

Lifecycle callbacks

  • after_commit callbacks only run if the transaction commits successfully. They will not run after a rollback.
  • after_rollback callbacks will run when a rollback occurs. Use them to clean up non-DB side effects or to notify other systems of failure.

Example scenarios

# 1) SyntaxError example (won't run)
# file with invalid Ruby syntax will raise SyntaxError at load time and no DB work occurs.

# 2) Runtime exception inside transaction
ActiveRecord::Base.transaction do
  user = User.create!(name: 'Alice')   # persisted inside transaction but not committed yet
  do_something_that_raises            # RuntimeError raised here
end
# RuntimeError propagates (unless rescued) and transaction is rolled back -> user not persisted.

# 3) Rescuing exceptions inside transaction (beware)
ActiveRecord::Base.transaction do
  user = User.create!(name: 'Bob')
  begin
    risky_call
  rescue => e
    # If you rescue and don't re-raise or call rollback, the transaction will still attempt to commit
    # unless you explicitly raise ActiveRecord::Rollback
    raise ActiveRecord::Rollback
  end
end

Best practices

  • Avoid rescuing exceptions inside transaction blocks unless you are going to re-raise or explicitly rollback; otherwise the transaction may commit despite an error.
  • Keep side-effects out of transactions (HTTP calls, enqueues) or use after_commit callbacks to perform external work once DB changes are durable.
  • Write tests that simulate exceptions and verify rollback, and include integration tests for failure paths.

Interviewer follow-ups

  • Q: Will after_commit run if an exception is rescued inside the transaction?
    Only if the transaction ultimately commits. If you rescue an exception and do not rollback, the transaction may still commit and after_commit will run — this is usually undesirable. Prefer explicit rollback.
  • Q: How to ensure external side-effects don't run on rollback?
    A: Enqueue external work in after_commit (not during transaction). For example, enqueue background jobs in after_commit so they are only queued on successful commit.
