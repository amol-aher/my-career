Have you ever used Active Record transactions in your code? How can the record fail?

Summary

Yes — I regularly use ActiveRecord transactions to ensure atomicity of multi-step database operations. Transactions group several DB changes so they either all succeed (commit) or none do (rollback). Records can fail for multiple reasons: validation failures, database constraint violations (uniqueness, NOT NULL, foreign key), exceptions raised in callbacks, deadlocks, connection issues, or explicit rollback commands.

Deep dive — How records can fail inside transactions

  • Model validations: Calling save (non-bang) returns false if validations fail. If not handled, you might think the transaction succeeded while changes were not persisted.
  • Bang methods and exceptions: save!, create!, update! raise ActiveRecord::RecordInvalid on validation failures — these exceptions will by default cause the transaction to rollback when uncaught.
  • Database-level constraints: Uniqueness, NOT NULL, foreign key constraints cause DB errors (e.g., PG::UniqueViolation) which raise exceptions and trigger rollback.
  • Callback errors: If an ActiveRecord callback (before_save, before_create) raises an exception or returns false (in older Rails), it can prevent persistence or cause a rollback.
  • Deadlocks & connection errors: DB deadlocks or lost connections raise exceptions from the adapter which cause rollback.
  • Manual rollback: Calling raise ActiveRecord::Rollback or other exceptions inside a transaction will roll the transaction back (behavior differs slightly depending on how you raise/handle exceptions — see below).

Practical examples

# Using bang methods — exceptions will rollback by default
ActiveRecord::Base.transaction do
  user = User.create!(email: 'a@example.com')
  account = Account.create!(user: user, balance: 0)
  # If any create! raises, the whole transaction is rolled back
end

# Using non-bang methods — you must check return values
ActiveRecord::Base.transaction do
  user = User.create(email: 'a@example.com') # returns user, but user.persisted? may be false
  unless user.persisted?
    # explicitly rollback
    raise ActiveRecord::Rollback, "user invalid"
  end
  account = Account.create(email: nil) # might fail DB constraint and raise
end

Interviewer follow-ups (and answers)

  • Q: Which failures are better detected at app level vs DB level?
    A: Use model validations for user-friendly messages and DB constraints for enforcing invariants (defense in depth). Always rely on DB constraints for critical invariants like uniqueness in concurrent environments.
  • Q: How do you avoid deadlocks?
    A: Keep transactions short, access rows in a consistent order, use appropriate isolation levels, and retry transient deadlock errors with backoff.
