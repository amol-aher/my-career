Technically challenging project — approach, learnings, outcome

System architect · Technical lead · Senior software engineer (Ruby on Rails, AWS, SQL, Vue.js)

Context & challenge: We built a realtime analytics pipeline that ingested millions of events per day, required near‑real‑time dashboards, strict cost limits, and correctness guarantees (exactly‑once processing where possible). The stack included Ruby services producing events, Kafka for ingestion, a stream-processing layer (Kafka Streams / Flink), and a Postgres + Redshift combination for real-time and historical queries.

How we approached it
  1. Define SLAs & requirements: latency targets for dashboards, acceptable data lag, cost constraints, and order/duplicate tolerances.
  2. Measure & profile: baseline existing latency and costs; created synthetic load to reproduce scale issues.
  3. Prove assumptions with spikes: implemented two spikes: one using a managed Kafka + KStream approach; another using a micro-batch architecture (Kinesis + Lambdas + Redshift COPY).
  4. Choose architecture: We adopted Kafka + stream processors (Flink) for low-latency aggregations and a CDC pipeline (Debezium -> Kafka) for slowly-changing dimensions.
  5. Reliability & idempotency: design producers and consumers to be idempotent; use deduplication via event IDs and compacted topics.
  6. Testing & deployment: contract tests, chaos tests, and capacity testing. Canary deploys and progressive rollouts with feature flags.
Technical highlights & code snippets

Sidekiq worker producing events to Kafka (Ruby)

class EventProducerWorker
  include Sidekiq::Worker

  def perform(event_type, payload)
    event = {
      id: SecureRandom.uuid,
      type: event_type,
      ts: Time.now.utc.iso8601,
      payload: payload
    }
    KafkaClient.produce('events', event.to_json)
  end
end

Idempotent consumer pseudocode (Java/Scala-ish)

def process(record):
  event = parse(record.value)
  if already_processed(event.id): return
  begin_transaction()
  apply_updates(event)
  mark_processed(event.id)
  commit()
Outcome & learning
  • Achieved near-real-time dashboards (latency < 5s for key aggregates).
  • Reduced cost by batching less-critical computations into hourly Redshift jobs.
  • Key lessons: validate assumptions with spikes, invest in observability (end-to-end tracing), and design idempotency from the start.
