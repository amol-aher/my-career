Making decisions without full information — approach and feelings

System architect · Technical lead · Senior software engineer (Ruby on Rails, AWS, SQL, Vue.js)

Example decision: Choosing an initial shard/partition key for a new write-heavy table when full access patterns weren't available.

Decision process
  1. Gather what data exists (approximate traffic, sample keys from logs).
  2. Enumerate options and failure modes (hot partitions, rebalancing cost).
  3. Choose a conservative approach (composite key with secondary index) that allows later re-partitioning with a clear migration path.
  4. Mitigate with monitoring and a rollback/migration plan.
How it felt

Uncomfortable but manageable — the key is to be explicit about uncertainties and document the decision and its assumptions so it can be revisited with new data.

Example SQL & plan
-- Conservative approach: hash + range to reduce hotspots
CREATE TABLE events (
  id uuid PRIMARY KEY,
  user_id bigint NOT NULL,
  created_at timestamptz NOT NULL,
  bucket int NOT NULL GENERATED ALWAYS AS (hashtext(user_id::text) % 1024) STORED
);
CREATE INDEX idx_events_bucket_created_at ON events(bucket, created_at);
