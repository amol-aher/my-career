Question 144: How would you design a high-throughput, low-latency job-processing system in Ruby? Discuss concurrency model, reliability, backpressure, and observability.

Concept

Job processing requires balancing concurrency, fault tolerance, throughput, and visibility. Ruby provides options like Sidekiq (Redis-backed) or custom thread/process pools.

Optimal answer (concise)

Use process-based concurrency (e.g., Sidekiq workers) to bypass GVL, Redis for queuing, multiple processes for parallelism, and structured logging/metrics for observability. Apply backpressure via SizedQueue or Redis queue limits.

Subquestions & answers

  • Concurrency model: processes for CPU-bound tasks; threads or async IO for IO-bound work.
  • Reliability: durable queues (Redis, Kafka), retries with dead-letter queues.
  • Backpressure: limit job inflow with SizedQueue or Redis BRPOP blocking.
  • Observability: instrument jobs with metrics (time, memory, retries).

Best practices

  • Use proven frameworks like Sidekiq or Sneakers instead of reinventing.
  • Implement monitoring dashboards (Grafana, Prometheus).
