Question 4: How do you handle multi-tenancy in your application?

Concept

Multi-tenancy means serving multiple customers (tenants) from one application deployment. Strategies trade off isolation, complexity, and cost: (1) shared schema with tenant_id, (2) schema-per-tenant (Postgres schemas), (3) database-per-tenant.

Optimal answer (concise)

Choose shared schema with strong tenant scoping for most cases; use schema-per-tenant or database-per-tenant when regulatory isolation or per-tenant scaling/backups are required.

Subquestions & answers

  • How to enforce scoping? — use middleware to set Current.tenant, add default_scope or explicit scoping, and use database constraints & indexes including tenant_id.
  • Migrations? — single DB: run once; schema/DB per tenant: run migrations per tenant (automation required).
  • Noisy neighbor? — enforce resource quotas, rate-limit heavy requests, and monitor per-tenant performance.

Example (simple current tenant)

# app/controllers/application_controller.rb
before_action :set_tenant
def set_tenant
  Current.tenant = Tenant.find_by!(subdomain: request.subdomain)
end

# scoping in models (explicit preferred over default_scope)
class Post < ApplicationRecord
  scope :for_tenant, ->(t) { where(tenant_id: t.id) }
end

Best practices / Pitfalls

  • Avoid default_scope traps; explicit scoping reduces surprises.
  • Index on tenant_id and composite indexes for common queries.
  • Test cross-tenant access patterns to prevent data leaks.
