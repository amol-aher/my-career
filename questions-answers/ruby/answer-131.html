Question 131: Explain memory visibility issues between threads and how Ruby ensures (or does not ensure) visibility.

Concept

Memory visibility refers to whether a write by one thread becomes visible to another thread. Without proper synchronization, updates may be reordered or not seen due to CPU/cache and compiler optimizations.

Optimal answer (concise)

Ruby relies on the underlying VM/OS memory model. On MRI the GVL provides strong ordering for Ruby-level operations while held; on JRuby the JVM memory model applies and requires proper synchronization (Mutex, volatile/atomics) to ensure visibility. Use Mutex or atomic primitives to establish happens-before relationships.

Subquestions & answers

  • Does Mutex ensure visibility? — Yes: entering/exiting mutex creates memory fences, ensuring writes before unlock are visible after lock.
  • What about Thread-local? — Thread-local storage isolates data per thread; no visibility needed across threads.
  • Atomics? — Use stdlib/gems providing atomic types for low-level visibility guarantees.

Example

# safe publish with mutex
mutex = Mutex.new
shared = nil
writer = Thread.new do
  mutex.synchronize { shared = {x: 1} }
end
reader = Thread.new do
  mutex.synchronize { p shared } # guaranteed to see write after lock
end
[writer, reader].each(&:join)

Best practices / Pitfalls

  • Always synchronize shared mutable state. Don't assume writes are instantly visible without locks.
  • On JRuby, consider java.util.concurrent primitives if interoperating with Java.
