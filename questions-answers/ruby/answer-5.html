Question 5: Why are you using a single database instead of splitting tenants across databases?

Concept

Choosing a single DB is an architectural decision balancing operational simplicity, cost, and isolation. Single DB with shared schema is common because it simplifies migrations, pooling, and aggregate queries.

Optimal answer (concise)

Single DB simplifies operations (one migration, lower cost, easier analytics). Use DB-per-tenant only when you need strong isolation, per-tenant backup/restore, or separate SLAs.

Subquestions & answers

  • When to use DB-per-tenant? — regulatory compliance, heterogenous schemas, per-tenant scaling/backups.
  • Operational costs? — DB-per-tenant increases connection pool usage and migration complexity.
  • Hybrid? — large tenants can be moved to their own DB while smaller ones use shared DB.

Best practices / Pitfalls

  • Design schema with tenant discriminator and proper indexes.
  • Monitor per-tenant query costs and consider offloading heavy tenants.
  • Automate tenant onboarding and migrations if adopting DB-per-tenant later.
