Question 135: Explain Ruby’s memory model wrt threads. Which operations are atomic? Which are not?

Concept

Ruby's memory model behavior depends on the VM. On MRI the GVL gives some atomicity for certain operations (like fixing object_id updates) but higher-level race conditions still exist. Some primitive operations may be atomic (assignment of a reference on MRI under GVL), while compound operations are not.

Optimal answer (concise)

Simple assignments and certain VM-level operations may appear atomic on MRI due to GVL, but you should not rely on atomicity for compound operations like counter increment (read-modify-write). Use Mutex or atomic types for correctness.

Subquestions & answers

  • Atomic on MRI? — reference assignment is atomic because of GVL, but increments (a += 1) are not atomic.
  • On JRuby? — rely on JVM memory model; use synchronization or atomics.

Example

# not atomic
x = 0
threads = 10.times.map { Thread.new { 1000.times { x += 1 } } }
threads.each(&:join)
puts x # likely less than 10000 without mutex or atomic

Best practices / Pitfalls

  • Always use synchronization for compound updates and shared state mutations.
