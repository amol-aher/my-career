Question 89: How would you debug a memory leak in a Ruby application?

Concept

Memory leaks are caused by lingering references preventing GC. Debugging involves reproducing the leak, collecting heap dumps, and tracing object growth over time.

Optimal answer (concise)

Use memory profilers (ObjectSpace, derailed_benchmarks, memory_profiler, ruby_heap_dump), capture heap snapshots over time, identify increasing object types/retained paths, and fix reference leaks (caches, global arrays, closures).

Subquestions & answers

  • Tools: ObjectSpace.each_object, memory_profiler, derailed_bench, heap dump tools, and for JRuby use Java profilers.
  • Common culprits: long-lived caches, class variables, thread locals, and closures holding references.

Example process

# simple investigative script
GC.start
puts ObjectSpace.count_objects[:TOTAL]
ObjectSpace.each_object(MyLargeClass).take(10).each { |o| p o.object_id }

Best practices / Pitfalls

  • Reproduce in a staging-like environment; avoid relying on dev differences (autoload, code reloading).
  • Be careful with ObjectSpace in production due to overhead.
