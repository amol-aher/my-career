Question 153: What are the concurrency/security implications of eval-ing untrusted code inside threads?

Concept

Evaluating untrusted code is dangerous: it can execute arbitrary operations, access process resources, allocate memory, or interfere with other threads. In multi-threaded contexts, it can introduce timing attacks or resource exhaustion.

Optimal answer (concise)

Never eval untrusted code in-process. If you must run untrusted code, isolate it in a sandboxed process, container, or use language-level sandboxing (very hard to get right). Threads do not provide security isolation.

Subquestions & answers

  • Resource limits: untrusted code can exhaust CPU, memory, or file descriptors.
  • Attack surface: code can call system or file APIs; use separate OS-level isolation.

Best practices / Pitfalls

  • Prefer fork+exec with seccomp/containers and strict resource limits. Avoid in-process eval for untrusted inputs.
