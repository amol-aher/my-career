Blue-Green Deployments on AWS

What is blue-green?

Blue-green deployment means maintaining two production environments: blue (current live) and green (new version). Traffic is switched from blue to green once the new environment passes validation.

Approaches on AWS

  1. ECS (ALB target groups): Create new task set in ECS service (for Fargate/EC2) and attach to a separate ALB target group. Use ALB listener rules or weight-based routing to move traffic.
  2. EKS (Kubernetes): Deploy green as new k8s deployments/services and shift traffic via Ingress controller (ALB Ingress) or service mesh (Istio/Linkerd) using weighted routing.
  3. Lambda: CodeDeploy supports traffic shifting for Lambda aliases (linear/canary) and automated validation hooks.
  4. Elastic Beanstalk: Has built-in blue/green support to swap CNAMEs between environments.
  5. Route53 weighted routing: Use DNS weights to gradually increase traffic to green — suitable when ALB-level routing isn't available.

Step-by-step example (ECS on Fargate)

  1. Build a new container image and push to ECR.
  2. Create a new task definition revision for the green version.
  3. Register a new target group (green) on ALB and register the green tasks to it.
  4. Run smoke tests against the green target group (internal test URLs or health endpoints).
  5. Switch traffic: update ALB listener rule weights or update service to point to the green target group.
  6. Monitor metrics for a rollback window; if everything looks good, decommission blue or keep it warm for quick rollback.

Automating the shift using CodeDeploy

CodeDeploy can perform the traffic shifting automatically and supports hooks for validation. For ECS, you configure a CodeDeploy application with BLUE_GREEN deployment configuration and provide target groups and a listener.

Database migration considerations

  • Prefer backward-compatible DB changes. Use feature flags for schema-dependent features.
  • For incompatible schema changes, consider a phased approach: add columns, update code to write both formats, backfill and then switch readers.
  • Avoid tight coupling of deploy to DB migration during traffic shift unless you have robust rollback for the migration.

Rollback strategy

Keep the blue environment ready for at least the rollback window. If metrics cross thresholds, automate or manually revert traffic and investigate. For DB changes that are destructive, ensure you have backups and tested rollback scripts.

Subquestions (examples)

How long should I keep the blue environment after switching?

Keep it warm for at least the length of your rollback window — typically 15–60 minutes for simple services, or longer if business-critical metrics need observation. Cost vs safety trade-offs apply.

How to ensure zero downtime?

Ensure session state is externalized (Redis/DynamoDB), readiness and liveness probes are accurate, and health checks prevent routing to unhealthy instances. Use graceful connection draining on ALB/targets.

Conclusion

Blue-green is a strong strategy to reduce risk during production releases. On AWS, combine ALB, ECS/EKS, CodeDeploy, and Route53 depending on your stack. Prepare for DB migrations and automate validations to make traffic shifts safe.
