Deploying Docker Images to ECS / EKS via CI/CD

Overview

CI/CD for containerized apps follows a common flow: build → scan → push to registry → update deployment. On AWS you typically push images to ECR; on Kubernetes you push to any OCI registry. The pipeline then updates ECS task definitions or Kubernetes manifests/Helm charts and applies them to EKS.

High-level steps

  1. Build the image (multi-stage Dockerfile) and tag it using an immutable tag (commit SHA) and optionally a semantic tag.
  2. Run SCA/vulnerability scans (Trivy, Clair, Amazon ECR image scanning) and block on critical issues.
  3. Push the image to a registry (ECR, Docker Hub, Artifactory).
  4. Create/update deployment artifact: ECS task definition revision or updated Kubernetes deployment/Helm chart referencing the new image tag.
  5. Deploy via orchestration: for ECS update service (rolling or blue/green), for EKS `kubectl set image` or `helm upgrade` and wait for readiness/rollout status.
  6. Run smoke tests and observability checks, then promote or roll back based on health.

GitHub Actions sample (ECR + ECS)

name: Build and Deploy to ECS
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: aws-actions/configure-aws-credentials@v2
        with:
          role-to-assume: ${{ secrets.AWS_ROLE }}
          aws-region: us-east-1
      - name: Build image
        run: |
          IMAGE=${{ env.ECR_REGISTRY }}/myapp:${{ github.sha }}
          docker build -t $IMAGE .
          docker push $IMAGE
      - name: Update ECS task definition & deploy
        run: |
          # Use aws cli or ecs-deploy script to register new task def and update service
          ./scripts/deploy-ecs.sh $IMAGE

Helm / kubectl sample (EKS)

# Update Helm values.yaml with new image tag and run
helm upgrade myapp ./chart --set image.tag=sha-abcdef
kubectl rollout status deployment/myapp --namespace production --timeout=5m

Best practices

  • Use immutable tags: Always reference images by SHA so deployments are reproducible.
  • Scan images early: Integrate Trivy/Inspector scans in CI and fail builds on critical vulnerabilities.
  • Keep secrets out of images: Use IAM task roles (ECS task role / IRSA for EKS) and Secrets Manager/SSM for secrets at runtime.
  • Automate rollbacks: Use health checks and alarms (CloudWatch, Prometheus) to trigger rollback or stop rollout.
  • Blue-green / canary: Prefer safe rollout strategies for production (ECS + CodeDeploy, service mesh or ingress weight for EKS).

Operational notes

Monitor image registry costs and configure lifecycle policies. For EKS, consider using an image pull secret with least privilege and enable image caching on nodes for speed. For ECS Fargate, use task execution roles to pull from ECR.

Subquestions & answers

How do you handle DB migrations when deploying containers?

Run migrations as dedicated pipeline jobs or init containers that run once per deployment; prefer backward-compatible migrations with feature flags. For complex migrations, perform them during a maintenance window or orchestrate as part of a blue-green deploy.

How to do zero-downtime?

Use readiness probes, ALB/NLB draining, and deployment strategies (rolling, canary, blue-green). Ensure state is externalized (Redis, S3).

Conclusion

Automating container deployments to ECS/EKS reduces human error and speeds releases. The critical pieces are immutable artifacts, secure registry usage, safe rollout strategies, and robust monitoring with automated rollback.
