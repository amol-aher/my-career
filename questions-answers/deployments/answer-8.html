Designing Highly Available Deployments on AWS

Principles

  • Eliminate single points of failure.
  • Distribute across failure domains (AZs and regions).
  • Automate recovery: health checks, auto-healing and autoscaling.
  • Design for graceful degradation.
  • Test failover regularly (chaos engineering).

Architecture pattern (multi-AZ, single-region)

Client -> Route53 -> ALB (multi-AZ) -> AutoScaling Group / ECS tasks / EKS nodes (multi-AZ)
                                       \-> RDS (Multi-AZ) -> Read replicas (for read scaling)
                                       \-> ElastiCache (Multi-AZ)

Key components

  • Networking: VPC with public/private subnets in at least two AZs. NAT gateways and route tables configured per AZ for resiliency.
  • Load balancing: Use ALB for HTTP; enable cross-zone load balancing and health checks with meaningful endpoints.
  • Auto scaling: Configure ASGs or Kubernetes HPA based on CPU/requests/custom metrics.
  • Databases: Use RDS Multi-AZ or Aurora for automatic failover. Use read replicas for scaling reads and promote when needed.
  • Stateless services: Store uploads in S3 and session state in ElastiCache or DynamoDB to allow horizontal scaling.
  • Resilience: Implement retries with exponential backoff, circuit breakers and timeouts.
  • Monitoring & Recovery: CloudWatch alarms, automated runbooks and Lambda/SSM automation to remediate common failures.

Multi-region considerations

For stronger SLAs, replicate data and services across regions. Choose an appropriate DR strategy:

  • Warm standby: Smaller footprint in secondary region that can scale up.
  • Pilot light: Minimal resources in the secondary region and automated scripts to scale up.
  • Active-active: Full production in multiple regions with data replication and conflict resolution.

Testing and validation

  • Run failover drills and simulate AZ/network failures.
  • Use synthetic transactions to validate user journeys.
  • Ensure recovery time objectives (RTO) and recovery point objectives (RPO) meet requirements.

Subquestions & sample answers

How do you ensure the database doesn't become a single point of failure?

Use RDS Multi-AZ for automatic failover and cross-region read-replicas for disaster recovery. For low RPO, use Aurora Global Database or multi-master solutions where conflict resolution is handled by the DB.

How do you handle session state?

Keep services stateless; store sessions in ElastiCache (Redis) or DynamoDB. Alternatively, use JWTs for sessionless authentication where appropriate.

How to handle stateful workloads?

Stateful workloads require careful planning: use persistent volumes (EBS) with replication strategies, or move to managed databases that handle replication (RDS/Aurora). For file artifacts, use S3 with lifecycle policies.

Conclusion

Highly available systems combine architectural choices (multi-AZ/region), managed services (RDS/Aurora), automation (autoscaling, health checks), and operational practices (monitoring, runbooks and chaos tests). These together form a resilient system.
