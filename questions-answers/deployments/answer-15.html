Managing Infrastructure as Code (CloudFormation / CDK / Terraform)

Principles of IaC

  • Keep infrastructure definitions in version control and review changes.
  • Use modular, reusable components.
  • Automate plan & apply via pipelines with approvals for production.
  • Ensure secrets are not stored in code or state files.

Tool comparisons

ToolNotes
CloudFormationAWS-native declarative JSON/YAML; strong service coverage; stacks and change sets; slower iteration for complex logic.
CDK (Cloud Development Kit)Use familiar languages (TS/Python/Java) to generate CloudFormation; good for higher-level constructs and abstractions.
TerraformProvider ecosystem & multi-cloud; declarative HCL; remote state and locking; large community modules.

Best practices & patterns

  • Modularization: split infra into environment-aware modules (network, compute, database).
  • Remote state & locking: Terraform: S3 + DynamoDB; CDK/CFN: use change sets and parameterization.
  • State hygiene: avoid sensitive values in state; use data sources to fetch secrets at runtime where possible.
  • Testing: unit tests (cdk assertions), integration tests (Terratest), linting (tflint, cfn-lint).
  • Policy-as-code: enforce guardrails with OPA, Sentinel, AWS Config, or IAM boundaries.
  • Drift detection: schedule drift checks and have remediation paths.

Workflow example (Terraform)

  1. Develop module locally and run terraform fmt, terraform validate.
  2. Create a PR — CI runs terraform plan against a workspace and shows diffs in the PR.
  3. After review, merge — pipeline runs terraform apply with proper credentials and remote state lock.
  4. Use a promotion model: separate state/workspace for staging and production with controlled approvals.

Handling secrets in IaC

  • Do not hardcode secrets in templates.
  • Use Secrets Manager or SSM to store sensitive values and reference them (using data sources) at deploy-time, or inject secrets via CI/CD without writing to state.
  • Encrypt remote state with KMS and restrict access to state storage.

Change management & governance

  • Require PR reviews for all infra changes.
  • Use CI to run static analysis and policy checks on IaC changes.
  • Keep a change log and use tagging conventions for resources for cost allocation and ownership.
Pro tip: Use versioned modules and semantic versioning for infra modules to allow safe upgrades and rollbacks.

Common interview subquestions

How do you handle drift?

Detect drift with periodic checks (terraform plan against remote state or CloudFormation drift detection) and remediate via automated pipelines or runbooks after validating the cause.

When to use CDK vs Terraform?

Use CDK when you want high-level constructs and tight CloudFormation integration and prefer language DSLs. Use Terraform when you need multi-cloud support and a mature ecosystem of reusable modules.

How to test IaC?

Unit-level assertions (cdk assertions), static linting (cfn-lint, tflint), and integration tests (Terratest, localstack) in pipelines. Run plans in CI and require PR approvals before apply.

Conclusion

Managing IaC is about people and process as much as tooling. Choose a tool that fits team skills, enforce review and testing, secure remote state and secrets, and implement policy checks to keep environments safe and predictable.
