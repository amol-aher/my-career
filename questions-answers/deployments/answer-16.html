Stages in a Typical CI/CD Pipeline

Overview

A CI/CD pipeline automates building, testing, and deploying software. Stages vary by team maturity, but the canonical pipeline includes stages from source to production with testing and gating in between.

Typical pipeline stages

  1. Source / PR Validation: Triggered by commits or PRs. Run linters, unit tests, static analysis, and SCA (software composition analysis).
  2. Build: Compile code, build container images, and produce immutable artifacts (images or packaged artifacts).
  3. Package & Store Artifacts: Push images to ECR or artifacts to S3/Artifactory. Tag artifacts with immutable references (commit SHA).
  4. Integration Tests: Run tests that verify interactions between components (DBs, APIs) in a short-lived environment.
  5. Security & Compliance Scans: Image vulnerability scan, SAST, secret scanning, and policy checks.
  6. Deploy to Staging: Deploy artifact to staging environment using IaC and run smoke and E2E tests.
  7. Manual/Automated Approval: Optional human approval or automated quality gates based on metrics.
  8. Production Deploy: Promote artifact and use safe strategies (blue/green, canary, rolling).
  9. Post-Deploy Validation: Run synthetic transactions, monitor SLOs, and validate key metrics.
  10. Observability & Rollback: Monitor and trigger rollback if thresholds are breached.

Auxiliary pipeline components

  • Secrets management (pull secrets at deploy time)
  • Feature flags for decoupling deploy from release
  • Canary analysis tooling and metrics dashboards
  • Artifact provenance and traceability

Example pipeline flow using GitHub Actions + ECR + ECS

1) on: pull_request -> run unit tests, lint
2) on: push to main -> build image, push to ECR, terraform plan for staging
3) CI deploy to staging -> run integration tests
4) After approval -> terraform apply for prod, update ECS service

Interview subquestions

How do you manage slow tests?

Run slow, expensive tests in nightly pipelines and keep PR checks fast (unit/fast integration). Use test selection to run only affected tests on PRs.

How to shorten lead time?

Parallelize pipeline steps, cache dependencies between builds, keep tests deterministic, and break large monolith tests into smaller suites.

Metrics to measure pipeline health

  • Lead time for changes
  • Deployment frequency
  • Change failure rate
  • Mean time to recovery (MTTR)
