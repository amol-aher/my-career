Designing a GitOps Workflow for AWS Deployments (ArgoCD / Flux)

GitOps principles

  • Git is the single source of truth for desired system state (manifests).
  • Changes are made via pull requests and automatically reconciled to the cluster.
  • Declarative, observable, and auditable deployments.

Core components

  • ArgoCD or Flux: Reconciler that watches Git repos and applies manifests to Kubernetes clusters.
  • Image registry (ECR): Where container images are stored.
  • CI system: Builds images and updates Git (image tag PRs) or triggers deploy repos.
  • Secrets management: SOPS (with KMS) or ExternalSecrets (pull from Secrets Manager).
  • Progressive delivery: Argo Rollouts or service mesh for canary and traffic shaping.

High-level workflow

  1. Developer merges code -> CI builds image with commit SHA tag and pushes to ECR.
  2. CI opens a PR in the infra repo updating the image tag (or uses automated image update tooling).
  3. PR is reviewed and merged (policy checks, IaC checks).
  4. ArgoCD/Flux detects change and reconciles cluster state, applying new manifests.
  5. Argo Rollouts or service mesh increments traffic to new pods; monitors metrics and can rollback on failure.

Repository layout patterns

  • Mono-repo: All k8s manifests in one repo with environment folders (prod/staging/dev).
  • Multi-repo: One repo per service and one "environment" repo that composes apps (App of Apps)
  • App of Apps: Central ArgoCD Application points to environment repo that contains child Applications per service.

Example ArgoCD Application manifest (app-of-apps)

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-service
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/my-service-manifests
    targetRevision: main
    path: overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: my-service
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Image update automation

Use tools to automatically update manifests when new images are pushed:

  • Flux Image Automation — watches registry, updates Git manifests, and Flux reconciles.
  • argocd-image-updater — ArgoCD companion that updates image tags in the Git repo.
  • CI bot approach: CI opens PR to infra repo with updated image tag (works well with code review and approvals).

Secrets & config

  • Use SOPS encrypted files (git-crypt alternative) with KMS for storing secrets in Git securely.
  • Or use ExternalSecrets to inject secrets from AWS Secrets Manager at runtime; avoid plaintext secrets in git.

Progressive deployment & safety

  • Use Argo Rollouts for canary analysis and automated promotion when metrics look healthy.
  • Integrate Prometheus alertmanager with Argo for rollback triggers.
  • Use Kubernetes podDisruptionBudgets and readiness/liveness probes to maintain availability during rollouts.

Multi-cluster & multi-account

Deploy ArgoCD per cluster or a central ArgoCD with cluster credentials. Use AWS IAM roles for service accounts (IRSA) and configure cross-account access for secrets and image pulls.

CI integration example (simple)

# CI job outline:
- build image -> tag with SHA -> push to ECR
- run security scans, tests
- create PR on infra repo updating image tag (or call Flux image update API)
- after merge, ArgoCD reconciles and deploys

Observability & audits

  • ArgoCD UI shows differences, sync history, and health.
  • Enable audit logs (K8s API server, ArgoCD, Git provider) for traceability.
  • Record who merged what PR, when, and which artifact was deployed.

Subquestions & answers

Q: How to handle secrets without committing them to Git?

A: Use ExternalSecrets to fetch values from AWS Secrets Manager at runtime or use SOPS with KMS-encrypted secrets stored in Git (ensure KMS keys are tightly controlled).

Q: How to do canary analysis automatically?

A: Use Argo Rollouts with Prometheus analysis templates to measure p50/p95 latency, error rate, and custom business metrics. Configure automated promotion when metrics meet thresholds.

Q: How to promote from staging to production?

A: Promote by updating the production overlay in the infra repo (PR-based). For automation, use Flux or argocd-image-updater to create PRs that are reviewed and merged to promote.

Note: GitOps scales well when teams agree on conventions (manifest layout, labels, sync policies). Treat Git as the audit source of truth and automate safely around it.
