How I Handle Secrets and Credentials in CI/CD Pipelines

Principles

  • Never store plaintext secrets in source control.
  • Prefer ephemeral credentials and least privilege.
  • Audit access and rotate secrets regularly.

Practical methods

  • CI provider secrets: use encrypted secrets facilities (GitHub Secrets, GitLab CI variables) for small teams.
  • OIDC for cloud credentials: configure provider OIDC (e.g., GitHub Actions OIDC) and allow the pipeline to assume an IAM role with short-lived credentials — avoids storing AWS keys in the CI provider.
  • External vaults: integrate HashiCorp Vault or AWS Secrets Manager to fetch secrets at runtime in the job. Use short-lived tokens and inject secrets into build step environment only at execution.
  • Ephemeral builders: use ephemeral runner instances or containers so secrets never persist long-term on runners.
  • Masking & logging: ensure CI masks secrets in logs and prevent commands that echo env variables.

Example: GitHub Actions + AWS OIDC

  1. Create IAM role with a trust policy for GitHub OIDC subject.
  2. Grant minimal permissions to role (deploy only to specific resources).
  3. In workflow, use aws-actions/configure-aws-credentials with OIDC to obtain temporary creds.
  4. Use short-lived creds to push to ECR or run terraform apply.

Rotations, revocations & audits

  • Rotate service accounts and secrets on a schedule (Secrets Manager automated rotation).
  • Immediately revoke secrets tied to incidents and rebuild artifacts if necessary.
  • Monitor CI logs and CloudTrail for suspicious usage of pipeline roles.
Warning: Avoid passing unescaped secrets to shell commands; prefer injecting as environment variables and use masking helpers provided by CI platforms.

Subquestions

How to inject database credentials during deploy?

Use Secrets Manager and configure the runtime to read secrets on startup. For migrations in pipelines, assume a short-lived role that can read the secret and perform migration, then discard the credential.

How to test pipeline that uses secrets safely?

Use test secrets in non-prod accounts and restrict test roles. Use feature flags to avoid accidental production-side effects during tests.

Checklist

  • Use OIDC or short-lived STS creds for cloud providers.
  • Use vault-backed secrets for sensitive values.
  • Mask secrets and avoid logging sensitive data.
  • Use ephemeral runners and rotate secrets regularly.
  • Audit access and alerts on anomalous usage.
