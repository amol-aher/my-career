How to Handle Database Migrations in a CI/CD Pipeline

Principles

  • Make migrations backward-compatible (additive changes first).
  • Keep migration execution and code deploy separate so you can control order and retry behaviors.
  • Automate backups and have rollback plans before destructive changes.

Patterns

Safe (zero-downtime) migration sequence

  1. Add new columns or tables (nullable/defaults).
  2. Deploy code that writes to both old and new schema (dual-write) but reads from old.
  3. Backfill data into new schema.
  4. Deploy code to read from new schema and stop writing old fields.
  5. Remove old columns after safe verification.

Running migrations in pipeline

Add a dedicated migration stage in your pipeline before switching traffic or during the deployment process:

stages:
- build
- deploy (new artifact to green)
- run-migrations (ephemeral job against DB)
- verify (smoke tests)
- switch-traffic

Tools and techniques

  • Rails: Use `rails db:migrate` in a controlled environment.
  • Flyway / Liquibase: Versioned migration frameworks that support rollbacks and auditing.
  • Feature flags: Toggle usage of new schema until fully validated.
  • Backups: Automated DB snapshots before destructive changes.

Handling migrations for microservices

For services with separate databases, apply service-level migrations under that service's pipeline. For cross-service schema changes, coordinate via a release plan with multiple services and feature flags.

Dealing with failures

  • For non-destructive migrations, revert application code to previous version and keep new schema changes; fix and reapply migration if needed.
  • For destructive migrations, restore from backup if necessary and follow postmortem to reduce risk.

Subquestions

When do you run migrations — pre-deploy or post-deploy?

A: Typically run migrations after deploying the new code to a green environment and before switching traffic. For additive migrations, it can run before code deploy. Sequence depends on compatibility.

How to test migrations?

A: Run migrations in ephemeral environments with production-like data subsets and run integration tests. Use schema drift checks and CI-based dry-run validations.

Conclusion

Design migrations to be backward-compatible, automate them in a controlled pipeline stage with backups and verification, and use feature flags to minimize user impact and enable quick rollback when needed.
