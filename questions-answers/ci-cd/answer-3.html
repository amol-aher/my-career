AWS Services — Practical Usage Beyond Lambda

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

An exhaustive tour of AWS services commonly used alongside (or instead of) Lambda, with real-world use-cases, integration patterns with Rails/Kubernetes/Sidekiq, and operational notes.

Compute and Container Services

  • EC2: Virtual machines for workloads requiring full control (legacy systems, specialized drivers, stateful services).
  • ECS / Fargate: Container orchestration with tight AWS integration; Fargate removes node management for serverless containers.
  • EKS: Managed Kubernetes — use when you need portability, custom scheduling, or complex k8s ecosystems.
  • Elastic Beanstalk: PaaS for simple app deployments (less used in mature infra stacks).

Storage & Databases

  • S3: Object storage for assets, backups, and presigned URLs. Use lifecycle rules, versioning, and MFA delete for important buckets.
  • EBS / EFS: Block storage for single-node use (EBS) or shared file systems (EFS) for multiple instances/pods.
  • RDS / Aurora: Managed relational databases with Multi-AZ, read replicas, and automated backups. Aurora provides better scaling for read-heavy workloads.
  • DynamoDB: NoSQL key/value store for high throughput, single-digit ms latency use cases.
  • Redshift / Glue / Athena: Data warehousing and analytics (ETL, SQL-on-S3).

Networking & Delivery

  • Route 53: DNS management with health checks and weighted routing.
  • Elastic Load Balancer (ALB/NLB): Distribute traffic to instances, targets, or IPs. ALB for HTTP routing and path-based rules; NLB for high-throughput TCP.
  • CloudFront: CDN for assets and API edge caching; use with signed cookies for protected content.

Messaging, Queues & Events

  • SQS: Durable queues for decoupling producers & consumers; Standard and FIFO options.
  • SNS: Pub/Sub for fan-out to SQS, Lambda, HTTP endpoints, and email/SMS.
  • Kinesis: Streaming data platform for ingestion and real-time processing (Streams / Firehose).
  • EventBridge: Event bus with routing and rules — great for near-real-time orchestration and cross-account events.

Caching, State & Identity

  • ElastiCache (Redis / Memcached): Session stores, caches, and Sidekiq backing store (often Redis).
  • Secrets Manager / SSM Parameter Store: Secure storage for secrets and configuration with rotation support (Secrets Manager).
  • KMS: Key management for encryption of secrets and resources.
  • Cognito: User pools and identity federation for apps (or use Auth0/third-party).

CI/CD, Build & Observability

  • ECR: Container registry integrated with IAM and lifecycle policies.
  • CodeBuild / CodePipeline / CodeDeploy: AWS-native CI/CD components for building, testing, and deploying artifacts, though teams often prefer GitHub Actions + Terraform + ArgoCD.
  • CloudWatch & X-Ray: Logs, metrics, alarms, and distributed tracing for observability.

Security, Governance & Infra-as-Code

  • IAM: Core identity and access management — enforce least privilege, use roles, and enable MFA for admins.
  • Organizations / SCPs: Multi-account governance and service control policies to restrict actions.
  • CloudFormation / CDK / Terraform: IaC tools for provisioning and managing resources declaratively.
  • WAF / Shield: Web application firewall and DDoS protection.

How these services fit with Rails / Sidekiq / Kubernetes

  • Sidekiq: Backed by ElastiCache (Redis) and scheduled by cron or bucketed queues; metrics in CloudWatch/Datadog for latency and retry sets.
  • Rails assets & uploads: S3 + CloudFront for static assets and presigned uploads from clients.
  • DB: RDS/Aurora for primary relational data with read replicas; use backups and PITR for recovery.
  • Queues: Use SNS+SQS for cross-service events and fanout; use SQS FIFO for ordered processing and dedupe.
  • Container images: Push to ECR; use IAM roles for build agents and ECR lifecycle rules to prune images.
  • Observability: Ship logs to CloudWatch/ElasticSearch; use X-Ray or OpenTelemetry for traces across services.

Operational concerns & trade-offs

  • Cost: Balance managed services (higher cost, less ops) vs self-managed (lower cost, more ops). EKS incurs control plane/node costs; Fargate might be cheaper at low scale.
  • Latency: Prefer regional services and VPC endpoints for low-latency access and security.
  • Resilience: Multi-AZ deployments and cross-region DR for critical systems.
  • Vendor lock-in: Use abstraction layers where portability is a concern (e.g., Terraform, containerization), but accept some lock-in for productivity gains.

Subquestions you should expect

  1. How do you store secrets securely?
    Use Secrets Manager for rotation-capable secrets and SSM Parameter Store for configuration. Use KMS to encrypt secrets and IAM to limit access.
  2. How to design for high availability?
    Multi-AZ RDS, read replicas, autoscaling for compute, and health-checked load balancers. Use multiple AZs by default and cross-region backups.
  3. How to handle backups and DR?
    Automate snapshots, cross-region replication for critical backups, test restores regularly, and document RTO/RPO for each system.
  4. How do you minimize costs?
    Right-size instances, use reserved instances/savings plans, use lifecycle rules on ECR/S3, and prefer serverless where appropriate for spiky workloads.
