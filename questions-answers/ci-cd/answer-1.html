CI/CD Fundamentals and Goals

CI/CD is about automating the lifecycle from code change to production in a safe, repeatable, and auditable way. The goals I follow:

  • Fast feedback: Developers get quick signals from linting, unit tests, and static analysis on PRs.
  • Automated verification: Integration tests, security scans, and contract tests before merging.
  • Deterministic builds: Build artifacts are reproducible and immutable (image + checksum).
  • Safe deployments: Use progressive delivery (canary, blue/green) and automated rollbacks.
  • Observability & traceability: Correlate deploys with metrics and logs and enable easy rollback triggers.

Typical CI Pipeline Stages

  • Pre-merge (PR) checks: Lint, unit tests, basic static analysis, type checks (Sorbet/TypeProf), and lightweight integration tests.
  • Build: Compile, bundle, install dependencies, build container image (multi-stage Docker), run tests inside the image where appropriate.
  • Scan: SAST (Brakeman), dependency scanning (bundler-audit / SCA), image scanning (Trivy/Clair).
  • Artifact publish: Push built images to a registry (ECR/GHCR) with immutable tags (git SHA + semver).
  • Deploy: Deploy to staging via Helm/manifest apply or trigger ArgoCD/Flux/GitOps flow. Run smoke tests and integration tests on staging.
  • Promote: Promote the tested artifact to production using controlled workflows (manual gates, approvals, or automated based on SLOs).
  • Post-deploy verification: Alerting checks, synthetic tests, and rollback if error budget exceeded.

Docker best practices

  • Multi-stage builds: Build artifacts in a build stage and copy only runtime artifacts to the final image to keep images small.
  • Minimal base images: Use distroless or slim images to reduce attack surface.
  • Non-root user: Run processes as a non-root user in containers.
  • Build args & secrets: Do not bake secrets into images; use build-time args only for non-sensitive values and runtime secrets via environment or secret mounts.
  • Image tagging: Use repo:gitsha for immutability and repo:latest only for convenience (not recommended for production deploys).
  • Image scanning: Integrate Trivy or Clair into the pipeline and fail builds on critical vulnerabilities.

FROM ruby:3.2.2 AS builder
WORKDIR /app
COPY Gemfile Gemfile.lock ./
RUN bundle install --without development test

COPY . .

FROM gcr.io/distroless/ruby
WORKDIR /app
COPY --from=builder /app /app
USER nobody
CMD ["puma", "-C", "config/puma.rb"]

Kubernetes best practices

  • Resources: Define requests and limits for CPU/memory to enable the scheduler to make smart decisions.
  • Probes: Add readiness and liveness probes to detect unhealthy pods and avoid traffic to startup pods.
  • Config & Secrets: Use ConfigMaps for non-sensitive config and Secrets (backed by KMS/Secrets Manager) for sensitive data. Consider tools like SealedSecrets or SOPS for GitOps workflows.
  • RBAC & NetworkPolicy: Use least-privilege RBAC and enforce network segmentation with NetworkPolicies.
  • Autoscaling: Use HPA for pod autoscaling and Cluster Autoscaler for node-level scaling.
  • Namespaces: Organize environments and teams via namespaces and resource quotas.

Deployment strategies & progressive delivery

  • Rolling updates: Default for Kubernetes; gradually replace pods with new versions.
  • Canary releases: Deploy a fraction of traffic to new version and monitor metrics before increasing.
  • Blue/Green: Deploy parallel environment and switch traffic atomically via load balancer or DNS.
  • Feature flags: Combine with canary to control feature rollout (LaunchDarkly, Flipper).
  • GitOps: Use ArgoCD or Flux for declarative deployments and auditability.

Database migrations & schema changes

Migrations are one of the riskiest parts of deploys. I use the expand-contract pattern:

  1. Expand: Deploy backward-compatible changes first (add columns, new tables).
  2. Migrate data: Backfill data to new structures in background jobs.
  3. Switch: Deploy code that uses the new column but remains tolerant of the old.
  4. Contract: Remove old columns after verification.

Also use pg_repack and online tools for large table maintenance and avoid locking operations during peak traffic.

Secrets, IAM & Security

  • Use AWS Secrets Manager or SSM Parameter Store for secrets; for Kubernetes use IAM Roles for Service Accounts (IRSA) + external-secret tooling to inject secrets.
  • Encrypt everything at rest where possible (RDS SSE, S3 SSE, EBS encryption).
  • Apply IAM least privilege and use short-lived credentials (STS roles) for deployment agents.
  • Scan dependencies (SCA), static analysis (Brakeman), and container image scanning as part of CI gates.

Observability & operations

  • Centralized logging (CloudWatch, ELK/Opensearch), metrics (Prometheus + Grafana or CloudWatch Metrics), and tracing (OpenTelemetry, X-Ray).
  • Automated alarms for SLO breaches and playbooks for runbooks and incident response.
  • Use health checks, readiness endpoints and chaos experiments (Chaos engineering) for resilience testing.

Infra as Code and environments

  • Use Terraform or CloudFormation/CDK for provisioning. Keep infra code versioned and peer-reviewed.
  • Use separate AWS accounts or projects per environment (dev/stage/prod) for blast-radius containment.
  • Automate environment provisioning in CI for ephemeral preview environments per PR.

Subquestions you should expect

  1. How do you handle rollbacks?
    Prefer automatic rollback on health-check or error rate spikes using deployment controllers or Argo Rollouts; keep the previous image tag readily available to redeploy quickly.
  2. How do you handle DB migrations that can't be backward compatible?
    Use feature toggles and schedule maintenance windows; for large schema moves, use a queued migration strategy or migrate in a read-only mode with traffic shifting.
  3. How do you secure your pipelines?
    Use least-privilege service accounts, sign artifacts, restrict secrets to the runner environment, and require approvals for production deployments.
  4. Do you use GitOps?
    Yes — it provides audit trails, declarative state, and easier rollbacks. ArgoCD + Helm or Kustomize is typical for K8s.
