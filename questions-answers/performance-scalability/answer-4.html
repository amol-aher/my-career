Caching Strategies and Where to Cache

This document describes caching layers, what to cache, eviction, and concrete examples used in production.

Common Cache Locations

  • Browser / CDN: Cache static assets and publicly cacheable API responses.
  • Edge / CDN (CloudFront, Fastly): Cache whole responses or GraphQL responses for unauthenticated or shared data.
  • API Gateway / Reverse proxy (Varnish): Cache at HTTP layer for high traffic endpoints.
  • Application-level in-memory (Rails.cache backed by Redis/Memcached): Cache computed fragments, query results, rendered templates.
  • Local in-process caches: LRU cache for extremely hot items to avoid network hops.
  • Database-level caching: Materialized views, result caching (Postgres pg_stat_statements for planning).

What to Cache

  • Expensive queries and aggregations.
  • Computed business data (leaderboards, trending).
  • HTTP responses for public endpoints.
  • Third-party API responses (with proper TTL).

Eviction and Consistency Strategies

  • TTL-based: Simple expiration for eventually-consistent data.
  • Write-through / Write-behind: Update cache synchronously or asynchronously on writes.
  • Cache invalidation: Invalidate keys on update events using Pub/Sub or application hooks.
  • Stale-while-revalidate: Serve stale data while refreshing in background.

Rails example: Caching a Query Result

def top_products
  Rails.cache.fetch("top_products_v1", expires_in: 10.minutes) do
    Product.order(sales_count: :desc).limit(50).to_a
  end
end

Where I personally cache in systems

  1. Redis cluster for application-level caches and rate-limits.
  2. Cloud CDN (CloudFront) for static + public API caching.
  3. Memcached for ephemeral low-latency caches when needed.
  4. Local in-process LRU for microservices that require ultra-low latency lookups.

Monitoring Cache Effectiveness

Track cache hit/miss rates, Redis memory usage, eviction rates, and request latency when cache is cold vs warm.
