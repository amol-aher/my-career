Rails Concurrency — How Rails Handles Multiple Requests

Clarify the phrase: Rails itself (the framework) is thread-safe starting with Rails 4/5 when configured; Ruby MRI has a Global VM Lock (GVL) that limits parallel CPU-bound Ruby execution, but I/O-bound concurrency works well. App server choice (Puma, Unicorn) and Ruby implementation (MRI vs JRuby) matter.

Ruby VM behavior

  • MRI (CRuby): Has a Global VM Lock (GVL) which allows only one native thread to execute Ruby code at a time. IO operations release the GVL, enabling concurrency for I/O-bound workloads.
  • JRuby: Implements true native threads without a GVL and permits parallel execution of Ruby code on multiple CPUs.

Rails & thread safety

Rails is thread-safe when apps avoid global mutable state and configure the application server properly. Rails 5+ is designed to be thread-safe by default for typical use-cases.

App servers — how they enable concurrency

  • Puma: Multi-threaded within worker processes; handles many concurrent connections (good for IO-bound).
  • Unicorn: Prefork, process-based, each worker handles one request at a time (good for CPU-bound to isolate memory).
  • Passenger: Supports both threaded and process modes.

Practical implications

  • Tune Puma workers and threads to match CPU and DB connections. Example: workers=2, threads=5.
  • Ensure ActiveRecord pool size is >= max threads per worker.
  • For CPU-heavy workloads, prefer more processes (workers) or move heavy work to background jobs or use JRuby.

Sample Puma config

# config/puma.rb
workers Integer(ENV['WEB_CONCURRENCY'] || 2)
threads_count = Integer(ENV['RAILS_MAX_THREADS'] || 5)
threads threads_count, threads_count
preload_app!
on_worker_boot { ActiveRecord::Base.establish_connection }

When to use JRuby

If you need parallel CPU-bound Ruby execution across cores and want native threading, JRuby is an option. It changes runtime characteristics (JVM GC, threading model).

Summary

Rails handles concurrency via the app server and runtime. For IO-bound apps, Puma + MRI + threads is excellent. For CPU-bound parallelism, use processes, background workers, or JRuby. Always tune DB pools and resources accordingly.
