API Versioning Strategies in Rails for Backward Compatibility

Versioning ensures clients continue working when you evolve APIs. There are multiple patterns with trade-offs.

Common versioning approaches

  • URL versioning: /api/v1/users — explicit, easy to route, cacheable; easiest to implement.
  • Header versioning: Use custom Accept header (Accept: application/vnd.myapp.v1+json) — cleaner URLs but harder for some clients and caching.
  • Query param: ?version=1 — simple but not ideal for caching and opaque.

Rails implementation patterns

Namespaces for controllers

# config/routes.rb
namespace :api do
  namespace :v1 do
    resources :users
  end
  namespace :v2 do
    resources :users
  end
end

Header-based routing middleware

class ApiVersion
  def self.call(req)
    accept = req.get_header('HTTP_ACCEPT')
    if accept&.include?('application/vnd.myapp.v2+json')
      'v2'
    else
      'v1'
    end
  end
end

Backward compatibility best practices

  • Additive changes (new fields) are safe; removing or changing semantics requires version bump.
  • Deprecation warnings in responses and migration guides for clients.
  • Keep old versions running as long as necessary based on client usage metrics.

Deprecation process

  1. Announce deprecation and date.
  2. Provide migration guides and examples.
  3. Monitor client usage and send reminders.
  4. Shutdown old version after notice period and low usage.

Summary

URL versioning via namespaces is the simplest and most common in Rails. Combine with clear deprecation process and metrics to avoid breaking clients unexpectedly.
