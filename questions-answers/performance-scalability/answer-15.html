Design When There Is No Database — Queue-Only Architectures

A queue-first architecture (Kafka/RabbitMQ) can be durable and scalable but requires careful design for state, ordering, replays, and consumer scaling.

Key challenges

  • State or derived materialized views need persistent storage (state store, RocksDB, or sink connector).
  • Durability and retention decisions (how long messages live).
  • Scaling consumers to match throughput — partitioning is essential.
  • Exactly-once or at-least-once processing semantics and idempotency.

Kafka-specific patterns

  • Scale by partitions: Increase partitions for parallelism.
  • Stateful stream processing: Use Kafka Streams or ksqlDB with RocksDB for local state.
  • Sinks & Connectors: Persist derived data to S3, warehouses, or NoSQL stores with Kafka Connect.
  • Compaction: Enable log compaction for the latest state-per-key.

RabbitMQ-specific patterns

  • Competing consumers: Start more consumers; tune prefetch_count to control in-flight messages.
  • DLQs and retries: Use dead-letter exchanges and delayed retry queues.
  • Mirrored queues / quorum queues: For HA across nodes.

State & durability

If you need state beyond transient processing, build materialized views: consumers write state to a durable store (e.g., RocksDB, Redis, DynamoDB) or sink to S3/warehouse.

Backpressure & flow control

Producers must respect backpressure: pause or throttle when consumer lag grows. In Kafka, monitor consumer lag and scale consumers or producers appropriately.

Summary

Queue-only systems are powerful for streaming pipelines. They require a plan for state, retention, scaling via partitioning, and robust error handling to achieve production-grade guarantees.
