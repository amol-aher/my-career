Integrating Redis or Memcached for Caching in a Rails App

This document covers why you'd choose Redis vs Memcached, how to configure Rails to use them for different caching needs, examples, operational concerns, and common pitfalls.

Redis vs Memcached — quick comparison

  • Redis: Rich data structures, persistence options (AOF/RDB), pub/sub, Lua scripting, used for caching, queues, rate-limiting, session store.
  • Memcached: Simple, memory-efficient, multi-threaded, pure key-value caching, no persistence, often slightly faster for simple caches.

When to use which

  • Use Redis when you need data structures (lists, sets), persistence, pub/sub (e.g., Sidekiq uses Redis).
  • Use Memcached when you want a lightweight cache layer and don’t need Redis features.

Rails configuration examples

Redis as cache_store

# Gemfile
gem 'redis'
gem 'redis-rails' # optional
# config/environments/production.rb
config.cache_store = :redis_cache_store, {
  url: ENV.fetch("REDIS_URL") { "redis://127.0.0.1:6379/1" },
  error_handler: -> (method:, returning:, exception:) {
    # report to error tracker like Sentry
  }
}

Using Redis for sessions

# Gemfile
gem 'redis-rails' # or redis-session-store

# config/initializers/session_store.rb
Rails.application.config.session_store :cache_store, key: '_app_session'

Memcached (Dalli) as cache_store

# Gemfile
gem 'dalli'

# config/environments/production.rb
config.cache_store = :mem_cache_store, "memcached1:11211", "memcached2:11211",
  { pool_size: ENV.fetch("RAILS_MAX_THREADS") { 5 }.to_i, expires_in: 1.hour }

What to cache where

  • Short-lived computed results and fragments — app cache (Redis/Memcached).
  • Session data — Redis (if sessions need persistence across restarts).
  • Distributed locks or leader election — Redis (SETNX), or Redlock with caution.
  • Rate limiting counters — Redis (INCR + EXPIRE) or token buckets.

Implementation patterns

Low-level caching

Rails.cache.fetch("hot:top_products", expires_in: 10.minutes) do
  Product.order(sales_count: :desc).limit(50).to_a
end

Fragment caching in views

<% cache product do %>
  <%= render 'product', product: product %>
<% end %>

Cache warming and stale-while-revalidate

value = Rails.cache.fetch(key, expires_in: 5.minutes) do
  compute_value
end
# optionally background refresh when near expiry

Operational considerations

  • Run Redis as a cluster (or managed AWS Elasticache) for HA, enable AUTH and TLS between app and Redis.
  • Monitor memory usage, eviction rates, latency and hit/miss ratio.
  • Use separate DB indices in Redis (DB 0,1,2) for isolation or separate clusters for critical data (sessions) and cache.
  • Set reasonable TTLs to avoid stale data and evictions.

Common pitfalls

  • Over-caching per-user highly-personalized data — increases memory use.
  • Thundering herd on cache expiry — use jitter and background refresh or locking.
  • Using Redis both for critical data and ephemeral cache fills up memory — separate clusters or RDB/AOF tuning helps.

Monitoring & metrics to track

  • Cache hit / miss ratio.
  • Evictions per second.
  • Redis memory used, connected clients, latency.
  • Application-level metrics: request latency when cache cold vs warm.

Wrap-up

Both Redis and Memcached have their place. Redis is more versatile and commonly used in modern Rails stacks (sessions, Sidekiq, rate-limits). Memcached can be chosen for simple, high-throughput caches. In all cases, design TTLs and invalidation carefully, monitor, and separate critical stores from ephemeral caches.
