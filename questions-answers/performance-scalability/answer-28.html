Database Connection Pooling in Rails — How it Works & Tuning

Rails manages DB connections per-process. Proper tuning avoids connection starvation and excessive DB connections.

How it works

Each Rails process (Puma worker, Unicorn worker) maintains a pool of connections (size from database.yml). Threads check out a connection when executing queries and return it afterward.

Key config

# config/database.yml
production:
  adapter: postgresql
  pool: 5
  timeout: 5000

Tuning rules of thumb

  • DB max connections should be >= total required by all processes: DB_MAX >= puma_workers * puma_threads + sidekiq_concurrency + slack.
  • Set pool size to at least the number of threads per process that might make DB calls concurrently.
  • Use pgbouncer in transaction pooling mode if you cannot increase DB connections.

Practical steps to tune

  1. Identify concurrent clients/processes and their threads/workers.
  2. Compute required connections and set DB MAX accordingly.
  3. Monitor pg_stat_activity for connection usage and waiting queries.
  4. Use connection_pool_timeout to catch misconfigurations early (errors when pool exhausted).
