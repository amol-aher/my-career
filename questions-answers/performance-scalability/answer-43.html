Avoiding the Distributed Monolith

A distributed monolith occurs when services are split but still tightly coupled (synchronous calls, shared DB, coordinated deploys). To avoid this:

Guidelines

  • Design for autonomy: Each service must be independently deployable and testable.
  • Prefer async integration: Use events and eventual consistency to decouple services.
  • Define clear contracts: Use consumer-driven contracts (Pact) and version APIs.
  • Avoid shared DB: Each service should own its data; for shared views use replication or read-models.
  • Resilience engineering: Implement timeouts, circuit breakers, bulkheads, retries with backoff.
  • Automated CI/CD: Independent pipelines for each service to avoid coordinated deploys.

Operational practices

  • Contract tests and integration tests running in CI.
  • Feature flags to toggle integrations during rollout.
  • Run chaos experiments to verify fault tolerance.

Example anti-pattern and fix

Anti-pattern: Service A calls Service B synchronously for every request. Fix: Service B emits events with required data, or introduce a cached read-model replicated to Service A.
