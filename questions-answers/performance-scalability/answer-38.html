Designing a Rails App to Handle 1M+ Requests per Day

1,000,000 requests/day is an average of ~11.6 req/s, but you must plan for peak traffic, burstiness, and scaling. Below is a practical architecture and techniques to ensure reliability and cost-effectiveness.

High-level architecture

Users -> CDN (CloudFront) -> API Gateway / ALB -> App pool (Puma) -> Redis cache / Read replicas -> Primary DB (writes)
                          \-> Event bus (Kafka) -> Worker pool -> Data warehouse / analytics

Key strategies

  • Edge caching: Cache public and semi-public responses at CDN to cut origin load significantly.
  • Aggressive caching: Use Redis/Memcached for query results, and cache rendered pages where possible.
  • Autoscaling: Scale app instances on latency and queue depth for workers, not just CPU.
  • Offload heavy processing: Move non-urgent tasks to background workers and make them idempotent.
  • DB optimization: Read replicas for read scaling, partitioning/sharding for large tables, pgbouncer for connection pooling.
  • API rate limiting: Protect system from abusive clients using rate limits (Rack::Attack).
  • Observability: Track p50/p95/p99, queue lag, cache hit ratio, and DB metrics; set SLOs.

Capacity planning example

If peak is 200 req/s, and average app instance handles ~50 req/s (after caching), you'll need around 4 app instances plus buffer and autoscaling to cover traffic spikes.

Database considerations

  • Separate read and write workloads (use read replicas).
  • Use materialized views or precomputed aggregates for heavy queries.
  • Consider denormalization for critical read paths.

Testing & validation

Load-test with k6 or Gatling to simulate peak and burst traffic. Use chaos testing to validate resilience.

Cost optimization

  • Cache aggressively to reduce compute and DB costs.
  • Right-size instances and use spot instances for non-critical workers.

Summary

Handling 1M+ requests/day is achievable with good caching, autoscaling, decoupling via queues, DB read scaling, and careful monitoring. Focus on peak capacity and failure modes rather than daily average.
