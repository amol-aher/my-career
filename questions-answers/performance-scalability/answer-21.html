Scaling Monolithic Rails Apps Horizontally & Load Balancing

Rails monoliths are common but they can scale horizontally when designed for statelessness and with appropriate architecture. Below are practical strategies, trade-offs, and concrete examples.

1. Make the app stateless

Move session state to Redis (or signed cookies), store uploads in S3, and use external caches so any web process can serve any request.

# Example: cookie_store (signed) or Redis session store
Rails.application.config.session_store :cache_store, key: '_myapp_session'
# or use redis-session-store gem

2. Horizontal scaling patterns

  • Multiple app instances behind a load balancer: Use AWS ALB, Nginx, or HAProxy to distribute traffic.
  • Autoscaling groups / containers: Deploy Puma/Unicorn processes in autoscaling groups or Kubernetes pods.
  • Use services for heavy concerns: Extract heavy compute, file processing, or real-time features into services if needed.

4. Load balancing considerations

  • Use sticky sessions only if necessary — prefer stateless tokens.
  • Health checks: readiness and liveness endpoints to avoid routing to unhealthy instances.
  • Graceful shutdown: SIGTERM should be handled to stop accepting new requests and finish in-flight ones.

5. Caching & read scaling

Use Redis and CDN. Offload read traffic to read replicas for DB heavy reads.

6. Background jobs & queues

Offload non-critical sync work to Sidekiq/ActiveJob. Create separate worker pools for heavy jobs.

7. Rolling deployments & zero downtime

Use blue-green or rolling with health checks; ensure DB migrations are backward-compatible when you have multiple app versions running.

8. When to split into services

Start with horizontal scaling. If deployment times, release coordination, or scaling characteristics differ greatly, consider splitting by bounded contexts into microservices.
