Handling Failed Background Jobs — Retries, Dead Jobs, and Strategies

Designing retries and dead-job handling is critical to reliability. Below are patterns and concrete examples.

Default Sidekiq behavior

  • Sidekiq retries failed jobs with an exponential backoff by default (up to 25 retries historically; configurable).
  • After exhausting retries, jobs land in the Dead set (dead queue) for manual inspection or automated draining.

Strategies for handling failures

  1. Idempotency: Make jobs idempotent (use unique keys or dedupe logic) so retries are safe.
  2. Classify errors: Retry transient errors (network/db timeouts) but fail fast for unrecoverable errors (validation failed) using custom error handling.
  3. Custom retry policies: Use Sidekiq options or middleware to adjust retry counts and backoff.
  4. Dead job automation: Alert on growth of dead set and use automated pipelines to retry or notify owners.

Example: custom retry logic

class MyWorker
  include Sidekiq::Worker
  sidekiq_options retry: 5

  def perform(id)
    do_work
  rescue TransientError => e
    raise e # will retry
  rescue PermanentError => e
    # log and drop: don't retry
  end
end

DLQ (Dead Letter Queue) patterns

  • Move failed messages to a DLQ with metadata (error, traceback, attempts) and an automated process for retries after fixes.
  • Use poison-message handling to prevent repeated immediate failures (move to DLQ fast).

Notification & observability

Integrate Sidekiq Web UI, Prometheus metrics, and alerts (PagerDuty/Slack) when retries exceed thresholds or the dead set grows.

Best practices

  • Keep job work small and fail-fast where possible.
  • Use exponential backoff and include jitter to avoid retry storms.
  • Provide a manual retry path for dead jobs after root cause is resolved.

Summary

Design jobs to be idempotent, classify errors for retry policies, monitor the dead set, and provide clear operational flows to inspect and re-run failed jobs.
