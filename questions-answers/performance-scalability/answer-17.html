Puma — Mechanisms for High Concurrency and Compute

Puma offers a hybrid concurrency model: multiple worker processes (multiprocessing) each with multiple threads (multithreading). This gives a balance between GIL limitations and IO concurrency.

Key knobs

  • workers (processes): Each worker runs in a separate OS process — good for CPU isolation.
  • threads (min,max): Threads inside workers allow multiple concurrent requests for IO-bound code.
  • preload_app! Enables copy-on-write memory sharing for faster worker spawn (works best with Ruby's COW-friendly GC).

Puma config example

# config/puma.rb
workers Integer(ENV['WEB_CONCURRENCY'] || 2)
threads_count = Integer(ENV['RAILS_MAX_THREADS'] || 5)
threads threads_count, threads_count
preload_app!
port ENV.fetch("PORT"){3000}
on_worker_boot do
  ActiveRecord::Base.establish_connection
end

Best practices

  • Ensure DB pool size >= threads * workers to avoid connection starvation.
  • For CPU-bound work, prefer more workers and fewer threads; consider offloading to background workers.
  • Use Puma clustered mode with a fronting proxy (Nginx) for connection buffering and SSL termination.

When Puma might not be enough

If your app is heavily CPU-bound and needs parallel CPU utilization, consider JRuby (true JVM threads), or move CPU-heavy tasks to separate services/workers written in languages with better concurrency characteristics.
