Handling Skewed Partitions (Hot Regions / Heavy Shards)

Partition skew—when one partition (e.g., a region) holds most of the data—breaks naive partition-by-region strategies. Fixing it requires re-sharding, virtual shards, or composite keys to evenly distribute load.

Strategies

1. Sub-sharding (add a secondary shard key)

Instead of single-level partition (region), add another dimension (hash of user id, date bucket) so each region has multiple shards.

-- Example: partition by (region, hash_prefix)
ALTER TABLE events PARTITION BY LIST (region);
-- within a region, create hash-based child partitions or multiple physical shards

2. Virtual shards (application-side)

Map logical shards to physical nodes and use consistent hashing or a shard map service to reassign hot logical shards across nodes without downtime.

3. Time-based rolling partitions

Split hot data by time windows (daily/monthly partitions). Old partitions can be archived or compressed.

4. Reshard / rebalance

For databases that support it (MongoDB, Cassandra), trigger chunk splits and balancing. For Postgres, attach/detach partitions and move data off large partitions into smaller ones.

5. Hot key mitigation

Identify hot keys and add sharding prefixes to distribute their records across partitions. For example, store prefixed_id = (hash(id) % 8) || '-' || id and shard by that.

6. Scale vertically for the hot partition

As a stopgap, scale up resources (CPU, IOPS) on the node serving the big partition while you design re-sharding.

Operational considerations

  • Plan re-sharding migrations during low-traffic windows.
  • Monitor partition sizes, IO contention, and per-partition query latency.
  • Test rebalancing operations in staging with a clone of production data.

Summary

Skew requires splitting partitions further (sub-shards), virtual shards, or moving to a system with automatic rebalancing. Short term, scale up; medium term, redistribute the data by adding dimensions to your partition key.
