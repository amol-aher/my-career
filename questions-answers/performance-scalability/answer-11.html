Index Limits — Alternatives When Indexes Slow Down Writes

When you're constrained on how many indexes you can add (because each index increases write cost and storage), you need an ensemble of techniques to retain read performance while preserving write throughput. Below are pragmatic approaches, trade-offs, and examples.

1. Measure first

Use pg_stat_user_indexes, EXPLAIN (ANALYZE, BUFFERS), and APM traces to identify the hot queries where an index will be most beneficial. Prioritize indexing those queries that yield the best ROI.

2. Partial / Conditional Indexes

Create indexes that only cover rows you actually query often (e.g., active=true). This reduces index size and write overhead.

-- Postgres: partial index
CREATE INDEX CONCURRENTLY idx_orders_active_created_at ON orders (created_at)
WHERE status = 'active';

3. Expression / Functional Indexes

Index the expression you query instead of raw column (useful for lower cardinality or computed values).

CREATE INDEX CONCURRENTLY idx_users_lower_email ON users (lower(email));

4. Covering Indexes and Index-only scans

Design composite indexes that include columns used in WHERE and SELECT so the DB can satisfy the query from the index itself (index-only scan) and avoid touching heap pages.

CREATE INDEX CONCURRENTLY idx_sales_product_day ON sales (product_id, created_at) INCLUDE (amount);

5. BRIN for very large append-only tables

Use BRIN indexes for large, naturally ordered datasets (e.g., time-series) — tiny and cheap for writes.

CREATE INDEX idx_logs_created_at_brin ON logs USING BRIN (created_at);

6. Materialized Views / Pre-aggregation

Offload heavy aggregations to materialized views that refresh periodically or incrementally, so reads don't require adding more indexes.

CREATE MATERIALIZED VIEW daily_user_stats AS
SELECT date_trunc('day', created_at) AS day, user_id, count(*) as cnt
FROM events GROUP BY day, user_id;
-- Refresh periodically
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_user_stats;

7. Denormalization and read-optimized tables

Duplicate frequently-read fields into purpose-built read tables or documents (cache hot read-paths) maintained via background jobs or event streams.

8. Use an external search/index engine

Move complex multi-field search to Elasticsearch/Opensearch where inverted indexes are designed for read-heavy, complex queries without polluting transactional DB indexes.

9. Batching & Write Path Optimization

Batch writes to reduce index maintenance overhead per-row: bulk insert/upsert, deferred constraints, and write-behind queues.

10. Selective Index Retention

Maintain index lifecycle: add, monitor, and remove indexes that provide little benefit. Use telemetry to show hit rate and size.

11. Practical checklist

  • Identify top queries and candidate indexes with EXPLAIN.
  • Start with partial/functional/BRIN indexes before adding full indexes.
  • Consider materialized views or denormalized read tables for complex aggregations.
  • Move complex search to a separate search engine.
  • Monitor write latency and index bloat; iterate.
