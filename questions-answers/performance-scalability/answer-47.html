Database per Service vs Shared Database

Database per service (recommended for microservices)

  • Pros: Loose coupling, independent schema evolution, clearer ownership and scaling.
  • Cons: Data duplication, complexity in maintaining read models and joins.

Shared database (anti-pattern)

  • Pros: Simpler queries and joins across domains, simpler transactions.
  • Cons: Tight coupling, danger of cross-service schema changes breaking other services, deployment coordination.

When to tolerate shared DB

For small teams or transitional periods, a shared DB can be pragmatic, but plan to decouple as complexity grows. Use schema ownership policies and read-only views to limit risk.

Alternatives & patterns

  • Use change-data-capture (CDC) to stream changes and populate local read models.
  • Expose data via APIs or events rather than direct DB access.
  • Use materialized views or read replicas for cross-service queries.
