Partitioning and Sharding in DynamoDB

Core concepts

DynamoDB distributes data across partitions using the partition key. Each partition has capacity limits; good partition key design is essential to avoid hot partitions.

Design considerations

  • Choose high-cardinality partition key: Avoid low-cardinality keys (e.g., 'status'). Use user_id, order_id, or hashed keys.
  • Write sharding: If a hot key is unavoidable (e.g., leaderboard), add a random suffix or time-based shard (userId#0..N).
  • Adaptive capacity: DynamoDB can auto-allocate extra throughput to hot keys, but avoid relying on it for high sustained loads.
  • GSIs/LSIs: Global Secondary Indexes increase flexibility but also consume additional capacity and can create hotspots if not planned.
  • On-demand vs provisioned: On-demand handles traffic spikes smoothly but may cost more at scale; provisioned with autoscaling gives more control.

Example: write sharding pattern

# Instead of key = "leaderboard"
# Use key = "leaderboard#"
shard = (user_id.hash % 10).to_s
partition_key = "leaderboard#" + shard

Streaming & scaling

Use DynamoDB Streams for downstream processing and to populate aggregated read models or other stores.

Monitoring

Monitor ConsumedCapacity, ThrottledRequests, Provisioned/OnDemand usage, and latency metrics. Tune partition key, increase capacity or add sharding accordingly.
