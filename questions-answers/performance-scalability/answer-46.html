Ensuring Idempotency in Distributed APIs

Idempotency techniques

  • Idempotency keys: Client supplies a unique key (UUID) per logical operation; server stores processed keys and result.
  • Upserts / conditional writes: Use DB upsert or compare-and-set to perform operation only once.
  • Deduplication store: Keep a store (Redis) mapping idempotency_key -> result/status.
  • Design idempotent operations: Make endpoints such that repeating them doesn't change outcome (PUT semantics).

Rails example: idempotency key

class PaymentsController < ApplicationController
  def create
    key = request.headers['Idempotency-Key'] || params[:idempotency_key]
    cached = IdempotencyStore.fetch(key)
    return render json: cached if cached

    result = PaymentProcessor.create(payment_params)
    IdempotencyStore.store(key, result)
    render json: result
  end
end

# IdempotencyStore can be Redis-backed using SETNX with TTL

Considerations

  • Expire idempotency records after reasonable TTL to save storage.
  • Include client identity in key or namespace to avoid collisions.
  • Handle partial failures where operation started but didn't complete — use compensating actions.
