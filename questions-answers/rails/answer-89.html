Controllers and Models in Rails — Responsibilities and Interaction

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Best practices for controller and model responsibilities, keeping code maintainable and testable, and interaction patterns between layers.

Controller responsibilities

  • Handle HTTP layer: params, authentication, authorization, and rendering responses.
  • Delegate business logic to service objects or models.
  • Map domain errors to HTTP status codes.
  • Keep controllers thin — orchestrators rather than processors.

Model responsibilities

  • Represent domain data and invariants: validations, associations, scopes, and small domain methods.
  • Encapsulate persistence logic and domain rules that are intrinsic to the entity.
  • Avoid putting orchestration, external API calls, or heavy workflows directly in models.

Interaction patterns

  • Controller calls a service object which manipulates models and enqueues jobs, returns a Result object back to controller for rendering.
  • Use presenters/decorators for view-layer formatting and serializers for JSON responses.
# Controller (thin)
def create
  result = CreateOrder.new(current_user, order_params).call
  if result.success?
    render json: OrderSerializer.new(result.order), status: :created
  else
    render json: { errors: result.errors }, status: :unprocessable_entity
  end
end

Testing strategy

  • Unit test models (validations, scopes), unit test service objects, and integration tests for controller flows.
  • Use fixtures/factories sparingly; prefer explicit object builders in tests for clarity.

Subquestions you should expect

  1. What about concerns?
    Use concerns for small shared behavior but prefer composition over inheritance. Avoid large concerns that hide dependencies.
  2. How to handle background jobs?
    Enqueue jobs from services or models where it makes sense; keep asynchronous side-effects explicit.
