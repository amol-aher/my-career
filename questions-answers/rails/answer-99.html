Performance-heavy Task Optimized — Case Study

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

A step-by-step case study: problem, measurement, hypothesis, remediation, results, and lessons learned.

Problem statement

Example: A dashboard page that rendered in ~2.8s p95 under load, with heavy DB usage, causing poor user experience. Many concurrent users amplified the issue.

Initial measurement

  • APM showed request time 2.8s (p95), DB queries per request: ~24, many small queries.
  • Bullet flagged multiple N+1s in associations, and EXPLAIN showed seq scans on a large table due to missing index.

Hypothesis & plan

  1. Fix N+1 queries by eager loading and batching.
  2. Add targeted indexes to remove seq scans.
  3. Cache computed aggregates at edge (Redis) and precompute with background jobs.

Remediation steps

  • Rewrote ActiveRecord queries with includes and selective select to reduce columns fetched.
  • Created composite index on (user_id, created_at DESC) to support common queries and ordering, created concurrently.
  • Moved heavy statistics to a nightly background job that writes to a summary table and used Redis for per-minute hot counters.
  • Introduced fragment caching for parts of the view with cache keys based on content versions.

Results and metrics

  • Queries per request reduced from ~24 → ~4 on average.
  • p95 latency dropped from 2.8s → 430ms.
  • DB CPU utilization decreased, and the system handled 2x concurrent users with the same infrastructure.

Lessons learned

  • Profile early — don't optimize blind.
  • Prefer small, focused changes (indexes, eager loads) before large refactors.
  • Cache carefully and invalidate using versioned keys.

Subquestions you should expect

  1. How to ensure cache consistency?
    Use versioned cache keys and event-driven invalidation (write-through or explicit purge on updates).
  2. How to test index effectiveness?
    Use EXPLAIN ANALYZE on staging-sized dataset or run queries against a recent production replica, and measure latency before/after.
