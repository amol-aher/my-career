Separating Business Logic — Service Classes vs Controllers/Models

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Patterns for extracting business logic: when to use service objects, policies, presenters, and where to keep logic in models or controllers.

Principles and goals

Keep code maintainable, testable, and single-responsibility. Controllers should orchestrate; models encapsulate domain invariants; service objects encapsulate application workflows that span multiple models or external systems.

When to keep logic in models

  • Logic tightly coupled to data invariants (validations, callbacks directly related to persistence).
  • Query-scoped logic (scopes) and small helper methods that operate on a single model.
  • Shared domain behavior that multiple consumers use.

When to use service classes

  • Complex workflows involving multiple models, external APIs, transactions, or background jobs.
  • Operations that would otherwise make models 'fat' and hard to test.
  • When you need explicit inputs, outputs, and error handling separate from persistence concerns.
# Example service pattern
class ChargeCustomer
  def initialize(customer:, amount_cents:)
    @customer = customer
    @amount_cents = amount_cents
  end

  def call
    PaymentGateway.charge(@customer.payment_token, @amount_cents)
    Invoice.create!(customer: @customer, amount_cents: @amount_cents)
  rescue PaymentError => e
    Result.failure(e.message)
  end
end

Supporting patterns

  • Form objects — for complex parameter validation and transformation before persistence (Reform, ActiveModel).
  • Policy objects — Pundit for authorization checks outside controllers.
  • Presenters/Decorators — for view-specific logic (Draper or simple POROs).
  • Interactors/Command objects — for orchestrating multi-step processes with clear success/failure semantics.

Testing and clarity

Service objects are easier to unit test (no DB) or with simple fixtures. Keep public APIs of services minimal and return Result objects or raise well-defined exceptions.

Subquestions you should expect

  1. Avoiding too many small services?
    Group related operations into a cohesive service; avoid premature extraction. Refactor when a method reaches a complexity threshold or is used by many controllers.
  2. Where to put validation failures?
    Use form objects or service objects to validate business rules; model validations for persistence invariants.
