Database Separation for Microservices

The Shared Database Antipattern

Keeping a single database for all microservices creates tight coupling and violates service autonomy:

  • Schema Lock-In: Services become dependent on central schema changes
  • Performance Contention: Resource competition between services
  • Deployment Blocking: Database changes require coordinated releases
  • Security Risks: Excessive privileges granted to multiple services

Separation Approaches

Option 1: Database Per Service

Each microservice owns its dedicated database instance:

  • Pros: Complete autonomy, optimized schemas, independent scaling
  • Cons: Data duplication, eventual consistency challenges, complex joins
  • Implementation: Use managed services (AWS RDS, Google Cloud SQL) per service

Option 2: Schema-Based Separation

Single database with logically separated schemas:

  • Pros: Lower operational overhead, easier cross-service queries
  • Cons: Still risks schema coupling, harder to enforce access controls
  • Implementation: PostgreSQL schemas or MySQL databases within same cluster

Option 3: Polyglot Persistence

Choose optimal database technology per service needs:

  • Example: Use PostgreSQL for relational data, Redis for caching, Elasticsearch for search
  • Benefit: Right tool for each workload type
  • Challenge: Increased operational complexity

Migration Strategies

Strategy 1: Dual Write

Temporarily write to both old and new databases during migration:

# Pseudocode for dual write
def create_order(order_data)
  old_db.create_order(order_data)
  new_db.create_order(order_data)
end

Strategy 2: Change Data Capture (CDC)

Replicate data changes asynchronously using CDC tools:

  • Tools: Debezium, AWS DMS, pglogical
  • Process: Capture binlog changes → transform → load to target DB

Strategy 3: Event Sourcing

Store state changes as immutable events:

# Order placed event
{
  "type": "order_placed",
  "payload": {
    "id": "123",
    "items": [...],
    "total": 99.99
  }
}

Handling Cross-Service Data Needs

When services need data from others, consider:

  • API Calls: Direct service-to-service requests (simplest but synchronous)
  • Event-Driven: Publish events for interested parties to consume
  • Materialized Views: Precomputed aggregates stored in read-only replicas
  • Batch Processing: Scheduled jobs to synchronize data periodically

Decision Framework

Factor Database Per Service Shared Database
Autonomy ✅ High ❌ Low
Scalability ✅ Independent scaling ❌ Limited by shared resources
Complexity ❌ Higher operational burden ✅ Simpler management
Data Consistency ❌ Eventually consistent ✅ Strongly consistent

Recommendation: Start with database-per-service for greenfield projects. For brownfield migrations, use gradual separation with CDC/event sourcing.
