N+1 Problem in Rails — Identification and Fixes

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

How to detect N+1 queries and practical fixes: eager loading, batch loading, Dataloader, Bullet gem, and SQL analysis.

What is N+1 and why it matters

N+1 occurs when code loads a collection (N rows) and then issues a query per row to fetch associations — leading to O(N) database calls and large performance costs.

How to identify

  • Use the Bullet gem in development to detect N+1 and unused eager loads.
  • Examine logs (ActiveRecord::Base.logger) for repeated queries in a request.
  • Use APM and DB slow query logs to see hotspots.

Fixes — eager loading and batching

Use includes, preload, or eager_load depending on the needs (see separate file for detailed differences).

# N+1 example
users = User.all
users.each { |u| puts u.profile.name } # triggers N additional queries

# Fix
users = User.includes(:profile).all
users.each { |u| puts u.profile.name } # single additional query

Advanced fixes — Dataloader / graphql-batch

For GraphQL or complex resolvers use batching (Dataloader) to group loads across fields and requests. For background batch processing, use pluck or SQL joins to reduce object hydration.

When eager loading hurts

Be careful not to over-eager-load large associations which increases memory usage and leads to large result sets. Use selective loading (select specific columns) and pagination.

Subquestions you should expect

  1. How to handle polymorphic associations?
    Use batch queries with IN and map results or consider denormalizing where read performance is critical.
  2. How to spot hidden N+1s?
    Use Bullet, enable SQL logging in staging, and use APM traces to see number of DB calls per request.
