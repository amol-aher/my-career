Database Locking: Optimistic vs Pessimistic

Database locking is a concurrency control mechanism used to ensure data integrity when multiple users or processes attempt to access or modify shared data simultaneously. Two primary approaches exist: optimistic locking and pessimistic locking, each with distinct characteristics and suitable use cases.

1. Optimistic Locking

Optimistic locking operates under the assumption that concurrent access conflicts are rare. Instead of locking resources preemptively, it allows transactions to proceed without restrictions and only checks for conflicts at commit time.

How It Works:

  1. A version number or timestamp column is added to the table being locked
  2. When reading data, the current version/timestamp is recorded
  3. During update, the system compares the stored version with the current version
  4. If versions match, the update proceeds and the version is incremented
  5. If versions differ, the update fails (indicating a conflict)
-- Example table structure with version column
CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    price DECIMAL(10,2),
    version INT DEFAULT 0
);

-- Update operation with optimistic locking
UPDATE products 
SET price = 19.99, version = version + 1
WHERE id = 123 AND version = @current_version;

Advantages:

  • No locking overhead during read operations
  • Better performance in low-concurrency scenarios
  • Simpler implementation than pessimistic locking
  • Reduced risk of deadlocks

Disadvantages:

  • Update conflicts require application-level resolution
  • Potential for failed transactions requiring retries
  • Not suitable for high-contention scenarios

2. Pessimistic Locking

Pessimistic locking takes a conservative approach by acquiring exclusive locks on resources before any modification occurs. It prevents other transactions from accessing the locked resource until the lock is released.

How It Works:

  1. Before reading/modifying data, a lock is explicitly acquired
  2. The lock remains active until the transaction completes
  3. Other transactions attempting to access locked resources must wait
  4. Locks are typically released automatically when the transaction commits or rolls back
-- Acquiring a pessimistic lock in SQL
SELECT * FROM products WHERE id = 123 FOR UPDATE;

-- The row is now locked exclusively until the transaction ends

Advantages:

  • Guarantees no conflicting modifications
  • Suitable for high-contention scenarios
  • Prevents lost updates and dirty reads

Disadvantages:

  • Increased blocking and waiting times
  • Risk of deadlocks if not managed carefully
  • Reduced concurrency and throughput
  • More complex implementation

When to Use Each Approach

  • Optimistic Locking: Web applications with mostly read operations, collaborative editing tools, e-commerce product catalogs
  • Pessimistic Locking: Banking transactions, reservation systems, auction platforms, inventory management

Subquestions and Detailed Answers

How does optimistic locking handle concurrent updates?

When two transactions attempt to update the same record concurrently:

  1. Both transactions read the record with its current version number
  2. The first transaction to commit succeeds, incrementing the version number
  3. The second transaction fails because its version check detects a mismatch
  4. The application must then reload the updated data and retry the operation

This approach ensures data consistency but requires application-level conflict resolution logic.

What are common deadlock scenarios in pessimistic locking and how to avoid them?

Common deadlock scenarios include:

  • Circular waits: Transaction A holds lock on Resource 1 and waits for Resource 2; Transaction B holds lock on Resource 2 and waits for Resource 1
  • Resource ordering: Transactions acquiring locks in different orders
  • Long-running transactions: Holding locks for extended periods

Avoidance strategies:

  • Always acquire locks in a consistent order across transactions
  • Keep transactions as short as possible
  • Implement timeout mechanisms for lock acquisition
  • Use deadlock detection algorithms provided by the database

How do modern ORMs like ActiveRecord implement these locking strategies?

ActiveRecord implements both approaches:

Optimistic Locking:

  • Adds a lock_version integer column to models
  • Automatically increments version on save
  • Raises ActiveRecord::StaleObjectError on version mismatch
  • Enabled with has_optimistic_locking

Pessimistic Locking:

  • Provides lock method (Model.lock)
  • Supports FOR UPDATE clauses in SQL
  • Can lock multiple records with ids_in_list.lock
  • Locks are held until transaction completion

What performance considerations should be made when choosing between these approaches?

Performance trade-offs:

  • Optimistic Locking:
    • Lower overhead for read operations
    • Higher throughput in low-contention scenarios
    • Retries may increase network round trips
    • Version checking adds minimal overhead
  • Pessimistic Locking:
    • Blocking reduces overall throughput
    • Lock management consumes database resources
    • Longer transaction durations impact performance
    • Deadlock resolution adds complexity

The choice depends on the expected concurrency level and acceptable failure rates for your application.

How do these locking strategies interact with database isolation levels?

Interaction with isolation levels:

  • Optimistic Locking: Often combined with READ COMMITTED isolation to allow non-blocking reads while ensuring write consistency through version checks
  • Pessimistic Locking: Typically used with REPEATABLE READ or SERIALIZABLE isolation to prevent phantom reads and ensure consistent views
  • Both approaches can coexist within the same application, applied selectively based on data sensitivity
  • The chosen isolation level affects visibility of uncommitted changes but doesn't replace explicit locking mechanisms
