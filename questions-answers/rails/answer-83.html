Managing Dependencies and Avoiding Tight Coupling

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Techniques to keep code modular: dependency inversion, interfaces/abstractions, hexagonal architecture, and test doubles.

Principles

Favor loose coupling: depend on abstractions, not concrete implementations. Apply SOLID principles and separation of concerns.

Techniques & patterns

  • Dependency Injection: Inject collaborators (via constructor or method) rather than instantiating them inside classes.
  • Interfaces & adapters: Define a small interface (duck-typing in Ruby) and implement adapters for external systems (HTTP client, payment gateway).
  • Hexagonal (Ports & Adapters): Keep core domain pure and adapt external systems at the edges.
  • Service boundaries: Use well-defined service objects or modules with minimal public surface.
  • Use gems for shared infra: Extract non-domain shared concerns into internal gems or engine packages to enforce boundaries.

Practical examples

# Bad (tight coupling)
class OrderProcessor
  def call
    gateway = Stripe::Client.new(ENV['STRIPE_KEY'])
    gateway.charge(...)
  end
end

# Better (injected)
class OrderProcessor
  def initialize(payment_gateway)
    @gateway = payment_gateway
  end

  def call
    @gateway.charge(...)
  end
end

Testing & CI

Use test doubles and contract tests for external collaborators. Consumer-driven contract testing (PACT) helps prevent coupling surprises between services.

Subquestions you should expect

  1. How to manage gem dependencies?
    Pin versions in Gemfile.lock, run dependency scanning, and use security update bots (Dependabot). Use group(:development, :test) to exclude dev-only gems from production.
  2. When to extract modules into gems?
    When multiple services or apps share the same code and you want a single source of truth for infra code, but balance with the overhead of maintaining a gem.
