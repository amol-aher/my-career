Includes vs Eager Load in Rails

Both `includes` and `eager_load` are ActiveRecord methods designed to preload associations and avoid N+1 query problems. However, they differ significantly in their implementation and use cases.

Basic Definitions

  • includes: Preloads specified associations using either separate queries or a LEFT OUTER JOIN, depending on whether conditions are applied to the association
  • eager_load: Always uses a LEFT OUTER JOIN to preload associations, regardless of conditions
# Using includes
User.includes(:posts)

# Using eager_load  
User.eager_load(:posts)

Key Differences

Feature includes eager_load
Query Strategy Uses separate queries OR LEFT OUTER JOIN Always uses LEFT OUTER JOIN
Conditions on Associations Switches to JOIN when conditions are present Always JOINs, even without conditions
Performance More efficient when no conditions are needed Potentially slower due to larger result set
Filtering Can filter on main model attributes Can filter on both main and associated models
Null Records Returns null records for missing associations Returns null records for missing associations

Behavior with Conditions

The most significant difference appears when applying conditions to associations:

# With includes and conditions
User.includes(:posts).where(posts: { published: true })

# Generated SQL (uses JOIN):
SELECT "users".* FROM "users"
LEFT OUTER JOIN "posts" ON "posts"."user_id" = "users"."id"
WHERE "posts"."published" = TRUE

# With eager_load and conditions
User.eager_load(:posts).where(posts: { published: true })

In both cases, Rails generates similar SQL because conditions force the use of JOINs. However, `includes` without conditions would generate simpler SQL:

# Simple includes (no conditions)
User.includes(:posts)

# Generated SQL:
SELECT "users".* FROM "users";
SELECT "posts".* FROM "posts" WHERE "posts"."user_id" IN (1, 2, 3);

When to Use Each Method

Use includes when:

  • You need to preload associations without filtering on them
  • You want optimal performance for simple associations
  • You're working with large datasets where JOINs would be inefficient
  • You need to access association attributes without conditions

Use eager_load when:

  • You need to filter or sort based on association attributes
  • You require a single query for all data
  • You're dealing with complex queries involving multiple associations
  • You need to ensure all associated records are loaded in one go

Advanced Usage Patterns

Nested Associations

# Loading deeply nested associations
User.includes(posts: :comments)

# With conditions on nested associations
User.includes(posts: :comments).where(comments: { approved: true })

Combining with Other Scopes

# Combining with ordering
User.includes(:posts).order('posts.created_at DESC')

# With eager_load
User.eager_load(:posts).order('posts.created_at DESC')

Performance Considerations

  • JOIN Efficiency: While JOINs can be efficient for small datasets, they become problematic with large tables due to increased memory usage
  • Indexing: Proper indexing on foreign keys is crucial for both methods
  • Result Set Size: `eager_load` can return much larger result sets when associations have many records
  • Loading Strategy: For read-heavy applications, `includes` often provides better performance; for write-heavy, `eager_load` might be preferable

Common Pitfalls

  • Over-fetching Data: `eager_load` can retrieve unnecessary columns when multiple associations are loaded
  • Complex Queries: Deeply nested `eager_load` queries can become difficult to optimize
  • Memory Issues: Large JOIN results can consume excessive memory
  • Unexpected Behavior: Mixing `includes` with conditions can lead to unexpected JOIN behavior

Subquestions and Detailed Answers

How do these methods interact with has_many :through associations?

For `has_many :through` associations:

  • `includes` typically loads the source association first, then the through association
  • `eager_load` joins all three tables together
  • This can lead to very complex queries with `eager_load`, potentially affecting performance
  • For complex through associations, `includes` is generally preferred unless filtering on the through association is required
# Through association example
class User < ApplicationRecord
  has_many :memberships
  has_many :groups, through: :memberships
end

# With includes
User.includes(memberships: :group)

# With eager_load
User.eager_load(memberships: :group)

What are the implications for pagination?

Pagination interacts differently with each method:

  • includes: Works well with pagination as it doesn't alter the main query structure
  • eager_load: Can cause issues with pagination because the JOIN operation changes the result set size
  • When using `eager_load` with pagination, ensure proper scoping to avoid incorrect record counts
  • For paginated results with associations, `includes` is generally safer and more predictable
# Pagination with includes
User.includes(:posts).page(1).per(20)

# Pagination with eager_load (requires careful handling)
User.eager_load(:posts).offset(20).limit(20)

How do these methods work with STI (Single Table Inheritance)?

STI adds complexity to association loading:

  • Both methods respect STI type columns when loading associations
  • `includes` may generate additional queries to load STI types
  • `eager_load` includes STI type information in the JOIN clause
  • For STI models, `includes` often produces cleaner SQL while maintaining flexibility
  • When filtering by STI type, `eager_load` becomes necessary
# STI example
class Vehicle < ApplicationRecord
  has_many :parts
end

class Car < Vehicle; end
class Truck < Vehicle; end

# With includes
Car.includes(:parts)

# With eager_load and STI type filter
Vehicle.eager_load(:parts).where(type: 'Car')

What are the alternatives to includes and eager_load?

Additional ActiveRecord methods for association loading:

  • preload: Similar to `includes` but always uses separate queries, never JOINs
  • select: Can be combined with `includes` to limit loaded columns
  • references: Used with `includes` to explicitly add JOIN clauses
  • cached associations: For static data that rarely changes
  • batch loading: Methods like `find_each` with manual association loading
# Using preload
User.preload(:posts)

# Combining select with includes
User.includes(:posts).select('users.id, users.name, posts.id, posts.title')

How do these methods affect database indexes?

Indexing considerations:

  • Both methods benefit from indexes on foreign keys
  • `eager_load` benefits from composite indexes covering JOIN conditions
  • For filtered associations, indexes on the filter columns improve performance
  • When using `includes` with conditions, ensure indexes exist on the filtered columns
  • Explain plans can help identify missing indexes for complex queries

Example index recommendations:

  • Foreign key indexes: `add_index :posts, :user_id`
  • Composite indexes: `add_index :posts, [:user_id, :published]` for filtered eager_load
  • Partial indexes: For frequently filtered attributes
