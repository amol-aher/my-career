Background Jobs — Tools, Patterns and Experience

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Overview of background job systems I have used: Sidekiq, Shoryuken, Resque, Delayed Job, ActiveJob, AWS Lambda, Faktory; comparison and best practices.

Tools I've used

  • Sidekiq: Primary choice for high-throughput Rails jobs (Redis-backed, multithreaded). Used with sidekiq-unique-jobs, sidekiq-scheduler, and Sidekiq Pro features.
  • Shoryuken: SQS-native worker for AWS-first architectures.
  • Resque & Delayed Job: Used in legacy systems; Resque for fork-per-job model, Delayed Job for simple DB-backed queuing.
  • ActiveJob: Rails abstraction to swap underlying adapters.
  • AWS Lambda / Step Functions: Used for serverless event-driven jobs and orchestrations.
  • Faktory: Language-agnostic job broker for polyglot systems.

Patterns & practices

  • Idempotency: Design jobs so reruns are safe; use DB constraints or idempotency tokens.
  • Job size: Keep payloads small; store large payloads in S3 and pass references.
  • Retries: Use exponential backoff and differentiate retryable vs non-retryable errors.
  • Queue sharding: Separate queues by priority and resource needs (IO-bound vs CPU-bound).
  • Monitoring: Track queue latency, retry sets, dead sets, and worker health.

Operational considerations

  • Tune Redis: persistence, eviction policies, memory sizing.
  • Set Sidekiq concurrency to match process CPU/IO characteristics and DB pool size.
  • Protect Sidekiq Web UI with auth and only expose internally.

When to choose each tool

  • Use Sidekiq for most Rails apps with Redis and high throughput needs.
  • Use Shoryuken when SQS is preferred as the primary queueing system (e.g., cross-account messaging).
  • Use Lambda for short-lived, event-driven tasks with automatic scaling and pay-per-use economics.

Subquestions you should expect

  1. How to handle long-running jobs?
    Break into smaller jobs, use orchestration (batches), or use dedicated machines with higher timeouts. For very long tasks, consider external workers or Step Functions.
  2. How to prevent duplicate processing?
    Use unique job middleware, idempotency keys stored in DB, and dedupe logic at the consumer level.
