Common Performance Bottlenecks in Ruby on Rails Applications

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Typical bottlenecks and how to detect and mitigate them: DB queries, N+1, missing indexes, GC, view rendering, external I/O, connection limits, memory bloat, and asset delivery.

Database-related bottlenecks

  • N+1 queries and inefficient joins.
  • Missing or poorly designed indexes causing seq scans.
  • Large unbounded queries and OFFSET-based pagination.
  • Long-running transactions blocking other operations.

Detection: EXPLAIN ANALYZE, slow query logs, APM traces.

Application-level bottlenecks

  • Heavy CPU-bound work performed in-request rather than background jobs (image processing, PDF generation).
  • Slow view rendering due to complex templates or un-cached fragments.
  • Poorly optimized Ruby code and excessive object allocations leading to GC pressure.
  • Thread/connection pool starvation (Puma threads > DB pool size).

External I/O & network

  • Blocking external API calls without timeouts or retries.
  • Large synchronous file uploads or downloads done in-request.
  • CDN/misconfigured caching causing repeated full-origin loads.

Infrastructure and configuration

  • Underprovisioned DB (insufficient IOPS, small instance types).
  • Single Redis node causing latency for Sidekiq or cache ops.
  • Improper autoscaling policies leading to slow scaling reactions.

Runtime and GC issues

  • High object allocation rates causing frequent GC pauses. Tune Ruby GC (RUBY_GC_HEAP_*, GC.compact where available).
  • Memory leaks in code or gems causing increased paging or OOM restarts.

Mitigation checklist

  • Profile first (rack-mini-profiler, Skylight, NewRelic).
  • Fix N+1s and add targeted indexes.
  • Move heavy tasks to background workers and cache results.
  • Tune Puma workers/threads and DB pool sizes.
  • Use CDNs for static assets and cache API responses where safe.

Subquestions you should expect

  1. How to prioritize optimizations?
    Target the critical path for user-perceived latency and high-frequency requests first; focus on hot code paths identified by profiling.
  2. How to measure improvement?
    Use before/after metrics: p95 latency, DB query counts per request, CPU and memory usage, and error rates.
