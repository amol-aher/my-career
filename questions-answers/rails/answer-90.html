Deciding Where to Put Indexes in a Database — Practical Guidance

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

How to choose indexes: analyze query patterns, cardinality, selectivity, composite indexes, covering indexes, maintenance costs, and monitoring.

Why indexes matter

Indexes speed up reads by avoiding full table scans but add write overhead and storage costs. Use them where query performance benefits outweigh maintenance costs.

What to look for before adding an index

  • Slow queries from EXPLAIN or slow query logs.
  • Columns used in WHERE, JOIN, ORDER BY, and GROUP BY clauses.
  • Cardinality & selectivity — high-cardinality columns benefit more from indexes.
  • Query frequency and read vs write ratio.

Composite and covering indexes

Composite indexes cover multiple columns and should be ordered based on how queries use them (left-most prefix rule). A covering index contains all columns needed for a query so the DB can satisfy the query from the index alone.

-- Example: queries filtering by user_id and status, ordering by created_at
CREATE INDEX index_orders_on_user_id_status_created_at ON orders (user_id, status, created_at DESC);

Partial and expression indexes

  • Partial indexes: Index only rows that matter (Postgres supports WHERE clauses on indexes).
  • Expression indexes: Index on expressions (lower(email) for case-insensitive search).
CREATE INDEX index_users_on_lower_email ON users (lower(email));
CREATE INDEX index_active_orders_on_user ON orders (user_id) WHERE status = 'active';

When not to add an index

  • Low-selectivity columns (boolean flags with 90/10 distribution) unless combined in a composite index.
  • Tables with extremely high write rates where indexes cause write amplification unless necessary.
  • Don't index columns only used in occasional ad-hoc queries without profiling evidence.

Operational considerations

  • Monitor index usage with Postgres pg_stat_user_indexes and pg_stat_all_indexes.
  • Use CONCURRENTLY flag for creating/dropping indexes in production to avoid locks.
  • Consider index bloat and periodic maintenance (REINDEX, pg_repack).

Subquestions you should expect

  1. How to pick index column order?
    Put the most selective column first and match common query patterns (where + order by).
  2. How to measure index effectiveness?
    Use EXPLAIN ANALYZE, check index scans vs seq scans, and monitor performance before and after adding indexes.
