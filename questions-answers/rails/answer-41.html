Database Architecture in Microservices

I strongly prefer using separate databases for each microservice rather than a shared database. This approach aligns with the fundamental principles of microservices architecture and offers significant advantages in scalability, autonomy, and maintainability.

Core Reasons for Separate Databases:

  1. Service Autonomy: Each microservice owns its own data, allowing teams to develop, deploy, scale, and maintain their service independently without affecting others.
  2. Technology Flexibility: Different services can use different database technologies optimized for their specific needs (e.g., PostgreSQL for relational data, MongoDB for documents, Redis for caching).
  3. Scalability: Services can scale horizontally based on their specific load patterns without being constrained by other services' database performance.
  4. Fault Isolation: Database failures are contained within a single service, preventing cascading failures across the entire system.
  5. Ease of Evolution: Schema changes can be made independently without coordinating with other teams, enabling faster iteration.

Sub-question: How do you handle data consistency across services?

In a microservices architecture with separate databases, we use eventual consistency patterns rather than strong ACID transactions. Key approaches include:

  • Event-Driven Architecture: Services publish domain events when data changes, and other services subscribe to these events to update their state asynchronously.
  • Compensating Transactions: If an operation fails partway through, we execute compensating actions to revert previous steps (e.g., canceling a reservation if payment fails).
  • Sagas: Long-running transactions managed through a sequence of local transactions and compensating actions.
  • CQRS (Command Query Responsibility Segregation): Separating read and write operations allows optimizing each for different consistency requirements.

Sub-question: What about reporting and analytics requiring cross-service data?

For cross-service queries and reporting, we avoid direct joins across databases. Instead, we use:

  • Materialized Views: Precomputed aggregates stored in dedicated read-only databases or data warehouses.
  • Data Warehouses: ETL processes that periodically extract data from operational databases into centralized analytical stores (like Amazon Redshift or Google BigQuery).
  • API Composition: For simple queries, we might call multiple services and combine results at the API gateway level (though this has performance implications).

Sub-question: When might a shared database still be appropriate?

A shared database could be considered in these scenarios:

  • Small Applications: Very small applications where the overhead of separating databases isn't justified.
  • Tightly Coupled Services: Services that are truly inseparable and always deployed together.
  • Legacy System Migration: As a transitional step before fully decomposing monolithic databases.
  • Regulatory Requirements: Situations where regulations mandate certain data relationships remain in a single database.

However, even in these cases, we should aim to eventually move toward separate databases as the system evolves.

Sub-question: How do you manage database schema migrations?

Each microservice handles its own database schema migrations independently:

  • Version Control: Migrations are stored in version control alongside the service code.
  • Automated Deployment: Migrations run automatically as part of the deployment process, often using tools like Flyway or Liquibase.
  • Backward Compatibility: Careful attention to backward compatibility during schema changes to avoid breaking dependent services.
  • Rollback Plans: Having rollback strategies in case migrations fail.

In conclusion, while shared databases offer simplicity for certain operations, the long-term benefits of separate databases in microservices far outweigh these advantages. The key is implementing robust patterns for handling distributed data consistency while maintaining service autonomy.
