HTTP Status Codes in the 500 Series

The 500 series indicates server-side errors where the server failed to process a valid request. These should be rare in production but require proper handling.

  • New API endpoint under development
  • Database connection timeout
  • External service outage
  • High load causing queue buildup
  • Scheduled maintenance window
  • Slow database query
  • External API latency
    • Status Code Name Description Typical Causes
    500 Internal Server Error Generic server failure Unhandled exceptions, configuration errors
    501 Not Implemented Feature not yet implemented
    502 Bad Gateway Upstream server failure
    503 Service Unavailable Temporarily overloaded or under maintenance
    504 Gateway Timeout Upstream server didn't respond in time

    Error Handling Best Practices

    1. Never Leak Stack Traces: Return generic messages in production
    2. Log Detailed Errors: Capture full exception details internally
    3. Implement Circuit Breakers: Prevent cascading failures
    4. Use Retry Mechanisms: For transient errors with exponential backoff

    Rails Exception Handling

    # config/application.rb
config.exceptions_app = self.routes

# app/controllers/concerns/error_handler.rb
module ErrorHandler
  extend ActiveSupport::Concern
  
  included do
    rescue_from StandardError, with: :handle_internal_error
    rescue_from ActiveRecord::RecordNotFound, with: :record_not_found
  end
  
  private
  
  def handle_internal_error(exception)
    logger.error "#{exception.class}: #{exception.message}"
    render json: { error: "Server encountered an unexpected error" }, status: :internal_server_error
  end
  
  def record_not_found(exception)
    render json: { error: "Resource not found" }, status: :not_found
  end
end

    Common Subquestions:

    Q: How do you differentiate between 500 and 502 errors?

    500 indicates internal application failure, while 502 signals problems with upstream dependencies. Monitor both separately in monitoring systems.

    Q: Should you retry after receiving 503 Service Unavailable?

    Yes, but implement exponential backoff. Include Retry-After header if provided by server to guide client retries.

    Q: How do you handle 504 Gateway Timeouts in distributed systems?

    Set reasonable timeouts, implement fallback strategies (cached data), and use asynchronous processing for long-running tasks.
