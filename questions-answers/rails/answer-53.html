Adding Indexes to Large Tables Without Downtime

Traditional Approach (With Potential Downtime)

Simple `ADD INDEX` command locks the table during creation:

ALTER TABLE orders ADD INDEX idx_customer_id (customer_id);

Problem: For tables with billions of rows, this can take hours and block writes.

Solution 1: Online Index Creation (Database-Specific)

PostgreSQL (v11+):

CREATE INDEX CONCURRENTLY idx_orders_customer ON orders(customer_id);

How it works: Builds index without locking reads/writes, but requires double disk space temporarily.

MySQL (InnoDB):

ALTER TABLE orders ADD INDEX idx_customer_id (customer_id) ALGORITHM=INPLACE;

Note: Still causes brief metadata lock - test thoroughly in staging.

Solution 2: Shadow Table Technique

  1. Create new table with desired index: 
    CREATE TABLE orders_new LIKE orders;
ALTER TABLE orders_new ADD INDEX idx_customer_id (customer_id);
  2. Populate with data (can run concurrently): 
    INSERT INTO orders_new SELECT * FROM orders;
  3. Swap tables atomically: 
    RENAME TABLE orders TO orders_old, orders_new TO orders;
  4. Drop old table after verification

Solution 3: Partitioning Strategy

For time-series data, add index to partitions individually:

-- Create partitioned table
CREATE TABLE orders_partitioned (
  id INT PRIMARY KEY,
  customer_id INT,
  created_at DATETIME
) PARTITION BY RANGE (YEAR(created_at));

-- Add index to each partition
ALTER TABLE orders_partitioned_2023 ADD INDEX idx_customer_id (customer_id);
ALTER TABLE orders_partitioned_2024 ADD INDEX idx_customer_id (customer_id);

Solution 4: Incremental Index Building

Use specialized tools for zero-downtime indexing:

  • pt-online-schema-change (Percona): Modifies table structure without locking
  • gh-ost (GitHub): Swaps tables with minimal locking
  • pg_repack (PostgreSQL): Rebuilds tables/indexes online

No-Downtime Implementation Checklist

  • Test in staging with production-sized dataset
  • Monitor disk space (index building requires ~2x storage)
  • Set up read replicas to offload traffic
  • Implement circuit breakers around affected queries
  • Have rollback plan ready (keep original table accessible)

Recommendation Based on Scenario

Scenario Best Solution
PostgreSQL database CONCURRENTLY index creation
MySQL with InnoDB ALGORITHM=INPLACE + shadow table fallback
Time-partitioned data Partition-wise indexing
Critical systems gh-ost/pt-online-schema-change
