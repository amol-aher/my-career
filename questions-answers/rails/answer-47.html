Rails Environment Configuration Differences

Rails uses different environment configurations to optimize behavior for development, test, and production scenarios. Understanding these differences is critical for maintaining application stability and performance.

Key Configuration Areas:

  1. Asset Pipeline: Compilation, minification, and serving of JavaScript/CSS assets
  2. Database Settings: Connection pools, query caching, and replication configurations
  3. Logging: Verbosity levels and destinations
  4. Cache Stores: In-memory, file-based, or distributed cache configurations
  5. Error Handling: Detailed error pages vs. generic error pages
  6. Thread Safety: Number of threads and worker processes

Sub-question: What are typical development environment settings?

Development environments prioritize ease of debugging and rapid iteration:

  • Asset Pipeline: Compiles assets on-the-fly without minification
  • Database: Configured for easy local setup (often SQLite)
  • Logging: Verbose debug-level logs to console
  • Error Pages: Detailed exception traces with interactive consoles
  • Cache: Disabled or using file store for simplicity
  • Concurrency: Single-threaded WEBrick server
# config/environments/development.rb
config.cache_classes = false
config.eager_load = false
config.consider_all_requests_local = true
config.action_controller.perform_caching = false
config.active_support.deprecation = :log
config.assets.debug = true

Sub-question: What about production environment settings?

Production environments focus on performance, security, and reliability:

  • Asset Pipeline: Precompiled assets with fingerprinting for caching
  • Database: Optimized connection pools and potentially read replicas
  • Logging: Structured logging to external services (Sentry, Logstash)
  • Error Pages: Generic error pages to avoid exposing sensitive information
  • Cache: High-performance caches (Redis, Memcached)
  • Concurrency: Multi-process servers (Puma, Unicorn) with multiple workers
  • Security: HTTPS enforcement, content security policies
# config/environments/production.rb
config.cache_classes = true
config.eager_load = true
config.consider_all_requests_local = false
config.action_controller.perform_caching = true
config.log_level = :info
config.public_file_server.enabled = ENV['RAILS_SERVE_STATIC_FILES'].present?
config.force_ssl = true

Sub-question: How do test environments differ?

Test environments are optimized for automated testing:

  • Database: Often uses in-memory SQLite for speed
  • Assets: Typically disabled or stubbed out
  • Logging: Minimal logging to reduce noise
  • Concurrency: May run tests in parallel
  • Cache: Usually disabled to ensure consistent test results
# config/environments/test.rb
config.cache_classes = true
config.eager_load = false
config.consider_all_requests_local = true
config.action_controller.perform_caching = false
config.active_support.test_order = :random
config.active_support.deprecation = :stderr

Sub-question: How to manage environment-specific secrets?

Secrets management varies by environment:

  • Development/Test: Often stored in plaintext in configuration files
  • Production: Should never be committed to version control
  • Best Practices:
    • Use environment variables for secrets
    • Leverage tools like dotenv for local development
    • Use encrypted credentials for production secrets
    • Consider secret management services (AWS Secrets Manager, HashiCorp Vault)
