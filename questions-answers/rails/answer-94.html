Largest Scale Application I've Worked On — Architecture and Learnings

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

A representative large-scale Rails-based system I led: traffic profile, architecture components, scaling, resilience, and lessons learned.

Overview & scale

Representative system: consumer web and mobile product with microservices for core domains. Key stats (example ranges):

  • Monthly active users: ~3–5 million
  • Peak RPS on API tier: ~500–1,000 requests/sec (spiky, regional)
  • Background jobs: hundreds of thousands/day processed via Sidekiq with multiple worker pools
  • Data size: TBs in object storage, hundreds of GBs in relational DBs, trillions of analytical events

Core architecture

  • API layer: multiple Rails apps (monolith slices & microservices) behind an API Gateway / ALB and CloudFront for edge caching.
  • Data layer: Aurora (primary + read replicas), Redis clusters (ElastiCache) for caching and Sidekiq backend, S3 for assets, and Kafka for event streaming.
  • Compute: EKS for microservices and ECS/Fargate for some worker fleets; Autoscaling at multiple layers.
  • Observability: centralized logging (ELK/Opensearch), metrics (Prometheus/Grafana + CloudWatch), distributed tracing (OpenTelemetry) and SLO-based alerting.

Operational practices

  • CI/CD via GitHub Actions and ArgoCD for GitOps-based deploys to clusters.
  • Rollback capability via immutable images and quick redeploy.
  • Feature flags for progressive rollouts and kill switches for risky features.
  • Dedicated platform team for shared infra and developer self-service (templates, CI images).

Scaling & performance tactics

  • Shard read traffic to replicas and cache hot items with Redis + CDN.
  • Use queue partitioning and separate worker classes for latency-sensitive jobs.
  • Pre-warm caches during deploys and use canary releases monitored by synthetic checks.

Challenges & lessons learned

  • Operational complexity — invest in automation and runbooks early.
  • Observability is essential — correlate logs/traces with user sessions using correlation IDs.
  • Gradual decomposition of monolith to bounded contexts helped reduce deployment blast radius.
  • Design for eventual consistency — embrace idempotency and sagas for multi-step operations.

Subquestions you should expect

  1. How to handle data migrations?
    Use non-blocking migrations, backfills, and dual-write strategies. Test migration performance in staging with production-sized datasets.
  2. How to ensure availability?
    Multi-AZ, read replicas, autoscaling, circuit breakers, and chaos testing to validate assumptions.
