Rails Callbacks: Understanding and Usage

Callback Types by Execution Phase

// Model lifecycle callbacks
class User < ApplicationRecord
  before_validation :normalize_email
  after_commit :send_welcome_email, on: :create
  
  private
  
  def normalize_email
    self.email = email.downcase.strip
  end
  
  def send_welcome_email
    WelcomeMailer.deliver(self)
  end
end

Before Actions

  • before_validation: Modify attributes before validation runs
  • before_save: Final chance to modify record before saving
  • before_create: Only called when creating new records
  • before_update: Only called when updating existing records

After Actions

  • after_validation: Run after validations pass
  • after_save: Called after save/create/update
  • after_create: Only after successful creation
  • after_update: Only after successful update
  • after_destroy: After record deletion

Common Callback Examples

1. Data Normalization

// Normalize phone numbers
before_save :format_phone_number

private

def format_phone_number
  self.phone = phone.gsub(/\D/, '') if phone.present?
end

2. Audit Logging

// Log changes to audit trail
after_save :log_changes

private

def log_changes
  AuditLog.create!(
    user_id: current_user.id,
    action: "#{self.class.name} #{action_name}",
    changes: previous_changes
  )
end

3. File Attachment Cleanup

// Remove old attachments
before_destroy :remove_attachments

private

def remove_attachments
  avatar.purge if avatar.attached?
end

Callback Anti-Patterns

1. Callback Chains Creating Dependencies

Callbacks that trigger other callbacks can create circular dependencies:

// Problematic chain
class Order < ApplicationRecord
  belongs_to :user
  after_save :update_user_stats
  after_save :send_invoice
  
  private
  
  def update_user_stats
    user.update_last_purchase_date!
  end
  
  def send_invoice
    InvoiceMailer.deliver(self)
  end
end

2. Side Effects in Callbacks

Callbacks performing non-trivial work violate SRP:

// Bad practice
before_save :process_payment

private

def process_payment
  PaymentGateway.charge!(amount)
  send_confirmation_email
end

3. Unpredictable Callback Ordering

Order matters but isn't guaranteed:

// Risky ordering
class Product < ApplicationRecord
  before_save :calculate_tax
  before_save :apply_discount
  
  private
  
  def calculate_tax
    # Tax calculation logic
  end
  
  def apply_discount
    # Discount application logic
  end
end

Best Practices for Callback Usage

  • Keep Them Simple: One responsibility per callback method
  • Use Service Objects: Move complex logic out of models
  • Explicit Ordering: Use `prepend` instead of relying on implicit order
  • Conditional Execution: Check conditions before proceeding
  • Test Thoroughly: Cover edge cases and callback interactions

Modern Alternatives

  • Service Objects: Encapsulate business logic outside models
  • ActiveSupport::Concern: Share callback patterns between models
  • Custom Concerns: Reusable modules for common callbacks
  • Form Objects: Handle complex form processing without callbacks
