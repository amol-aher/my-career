Rate Limiting and Throttling API Requests — Strategies and Implementations

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

How to implement rate limiting at different layers: edge (CDN/API gateway), app (Rack::Attack), and per-user quotas; algorithms and best practices.

Why rate limit

  • Protect backend from abuse and DoS.
  • Enforce fair use and tiered quotas for customers.
  • Prevent downstream API overload and maintain SLOs.

Algorithms

  • Fixed window: simple but can burst at window edges.
  • Sliding window: smoother than fixed windows.
  • Leaky bucket / token bucket: supports smoothing and burst control; token bucket is widely used.

Implementation options

  • Edge / CDN: Use CloudFront + WAF or API Gateway throttling to block bad actors early.
  • Application: Rack::Attack with Redis counters for per-IP or per-api-key limits.
  • Distributed rate limiting: Use Redis with Lua scripts or use Consul/Envoy rate limiting service for multi-node accuracy.
# simple Rack::Attack throttle
Rack::Attack.throttle('req/ip', limit: 100, period: 60) do |req|
  req.ip
end

Quotas and billing

Keep track of usage metrics and enforce daily/monthly quotas. Return 429 Too Many Requests with Retry-After and X-RateLimit-* headers.

Best practices

  • Differentiate by consumer (API key, user id) instead of only IP to support NAT-ed users.
  • Graceful degradation and soft-limits for premium customers.
  • Expose rate limit headers so clients can back off gracefully.
  • Monitor and tune limits; provide an appeals/override process for false positives.

Subquestions you should expect

  1. How to prevent spoofing IPs?
    Use API keys/auth and base limits on authenticated identity; use trusted proxies and X-Forwarded-For carefully.
  2. How to handle distributed counters?
    Use Redis with atomic increment and TTL or a token-bucket implementation with Lua scripts to ensure atomicity.
