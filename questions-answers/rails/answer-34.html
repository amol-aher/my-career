HTTP Status Codes in the 400 Series

The 400 series indicates client-side errors where the request contains bad syntax or cannot be fulfilled. These are crucial for providing meaningful feedback to API consumers.

Status Code Name Description Typical Usage
400 Bad Request Malformed request syntax or invalid parameters Missing required parameters, invalid JSON
401 Unauthorized Authentication required but failed or missing Missing/invalid token, expired session
403 Forbidden Authenticated but lacks permission Insufficient privileges, IP blocked
404 Not Found Requested resource doesn't exist Invalid endpoint, deleted resource
405 Method Not Allowed HTTP method not supported for resource Using POST on read-only endpoint
406 Not Acceptable Client requested unsupported content type Requesting XML when only JSON available
409 Conflict Request conflicts with current state Concurrent updates, duplicate creation
422 Unprocessable Entity Semantically valid but syntactically incorrect Validation failures, business rule violations

Best Practices for 400 Series Responses

  1. Provide Detailed Error Messages: Include field-specific validation errors
  2. Consistent Response Structure: Standardize error payload format across APIs
  3. Human-readable Descriptions: Avoid cryptic messages in production
  4. Include Request IDs: Help debugging with unique identifiers

Implementation Examples

# Bad Request (400)
render json: { error: "Missing required parameter: email" }, status: :bad_request

# Unauthorized (401)
render json: { error: "Authentication required" }, status: :unauthorized

# Forbidden (403)
render json: { error: "Insufficient privileges" }, status: :forbidden

# Unprocessable Entity (422)
render json: @user.errors.full_messages, status: :unprocessable_entity

Common Subquestions:

Q: When should you use 422 vs 400?

Use 400 for malformed requests (missing headers, invalid JSON), 422 for semantically invalid but well-formed requests (validation errors).

Q: How do you handle concurrent update conflicts?

Return 409 Conflict with retry-after guidance. Implement optimistic locking with ETags or version numbers.

Q: Should you ever return 200 OK for errors?

No. Always use appropriate status codes even for successful operations with warnings. Reserve 200 for truly successful responses.
