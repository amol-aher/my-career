Single Table Inheritance (STI) in Rails

Single Table Inheritance (STI) is a design pattern in Rails where multiple subclasses share a single database table. Each subclass is represented by a distinct value in a type column, allowing different classes to be stored in the same table while behaving as separate entities.

Basic Implementation

To implement STI, follow these steps:

# app/models/payment.rb
class Payment < ApplicationRecord
  self.inheritance_column = :payment_type # Optional, defaults to 'type'
end

# app/models/credit_card_payment.rb
class CreditCardPayment < Payment
  # Specific credit card payment logic
end

# app/models/paypal_payment.rb
class PayPalPayment < Payment
  # Specific PayPal payment logic
end

The database table would have a structure like:

CREATE TABLE payments (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  amount DECIMAL(10,2),
  payment_type VARCHAR(255), -- Stores class names ('CreditCardPayment', 'PayPalPayment')
  credit_card_number VARCHAR(19),
  paypal_account_id VARCHAR(255),
  created_at DATETIME,
  updated_at DATETIME
);

Key Features of STI

  • Type Column: A string column (typically named type) stores the class name of each record
  • Shared Structure: All subclasses inherit the same database schema
  • Polymorphic Behavior: Records can be instantiated as different subclasses based on the type column
  • Flexible Schema: Subclasses can have optional fields that only apply to specific types

Comparison with Polymorphic Associations

Feature Single Table Inheritance (STI) Polymorphic Associations
Structure All data in a single table with a type discriminator Separate tables linked through foreign keys
Implementation One model class hierarchy sharing a table Multiple independent models linked by associations
Query Performance Fast queries with simple type filtering Joins required between tables
Schema Flexibility Fixed schema with nullable columns for unused fields Independent schemas for each model
Use Case Similar objects with minor variations (e.g., payment methods) Radically different objects (e.g., comments on posts vs products)

When to Use STI

  • Similar Objects: When objects share most attributes but have a few differences
  • Simple Hierarchies: Small inheritance hierarchies (2-5 subclasses)
  • Performance-Critical: When join performance is a concern
  • Shared Business Logic: When common functionality can be abstracted in a base class

When to Avoid STI

  • Many Attributes: When subclasses have vastly different attributes
  • Complex Queries: When queries become overly complex due to many nullable fields
  • Large Number of Types: When the number of subclasses grows beyond manageable levels
  • Strict Data Integrity: When null constraints are important for optional fields

Advanced STI Techniques

Conditional Scopes

Create scopes to easily fetch specific subclasses:

class Payment < ApplicationRecord
  scope :credit_cards, -> { where(payment_type: 'CreditCardPayment') }
  scope :paypal, -> { where(payment_type: 'PayPalPayment') }
end

Polymorphic Interface Methods

Define methods that behave differently based on the subclass:

class Payment < ApplicationRecord
  def process
    case payment_type
    when 'CreditCardPayment' then process_credit_card
    when 'PayPalPayment' then process_paypal
    else super
    end
  end
end

Subquestions and Detailed Answers

How does STI handle validations and callbacks?

STI handles validations and callbacks as follows:

  • Shared Callbacks: Defined in the base class apply to all subclasses
  • Specific Callbacks: Subclasses can override base class callbacks
  • Validation Context: Validations can be made type-specific using conditional logic
    • class Payment < ApplicationRecord
  validates :amount, presence: true
  
  validate :specific_validation, if: :credit_card_payment?
  
  def credit_card_payment?
    payment_type == 'CreditCardPayment'
  end
end

Can STI be combined with other design patterns?

Yes, STI can be effectively combined with:

  • Decorators/Presenters: To handle view-specific logic for different types
  • Service Objects: For complex business logic that varies by type
  • Concerns: To modularize shared functionality between types
    • # Using concerns with STI
module Billable
  extend ActiveSupport::Concern
  
  included do
    validates :amount, numericality: true
  end
end

class Payment < ApplicationRecord
  include Billable
end

How does STI affect database migrations?

Migration considerations:

  • Add Columns Carefully: Add new columns to existing tables with caution
  • Default Values: Provide sensible defaults for new fields added to existing records
  • Backfill Data: Use migrations to populate type columns for existing data
    • # Example migration to add STI
class AddPaymentTypeToPayments < ActiveRecord::Migration[6.1]
  def up
    add_column :payments, :payment_type, :string
    
    Payment.reset_column_information
    
    Payment.find_each do |payment|
      payment.update(payment_type: 'GenericPayment')
    end
  end
end

What are the performance implications of STI?

Performance considerations:

  • Read Performance: Fast reads with simple type filtering
  • Write Performance: Slower writes due to larger table size and potential contention
  • Indexing: Crucial to index the type column for efficient querying
  • Query Complexity: Complex queries with many conditions may suffer performance degradation
  • Scaling: May become unwieldy with hundreds of types

How can STI be refactored to polymorphic associations?

To refactor STI to polymorphic associations:

# Original STI structure
# payments table with payment_type column

# Refactored polymorphic structure
# payments table (base)
# credit_card_payments table
# paypal_payments table

# Models
class Payment < ApplicationRecord
  has_one :credit_card_payment, dependent: :destroy
  has_one :paypal_payment, dependent: :destroy
end

class CreditCardPayment < ApplicationRecord
  belongs_to :payment
end

class PayPalPayment < ApplicationRecord
  belongs_to :payment
end

This approach offers better separation of concerns but requires more complex queries when accessing shared attributes.
