CSRF (Cross-Site Request Forgery) — What it is and Rails Mitigations

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Definition, attack vectors, and detailed Rails-specific mitigations including examples and API considerations.

What is CSRF?

Cross-Site Request Forgery is an attack where a victim's browser is tricked into making authenticated requests to a target site where the victim is logged in. The attacker leverages the browser's automatic credential handling (cookies, HTTP auth) to perform actions on behalf of the user.

  • Typical vector: Attacker hosts a malicious page that submits a form or issues an XHR/fetch to the victim site while the victim has an active session.
  • Important note: CSRF relies on the presence of credentials the browser attaches automatically (cookies, basic auth), so token-based Authorization headers are not vulnerable in the same way.

How Rails mitigates CSRF by default

Rails uses an authenticity token pattern by default for state-changing requests (non-GET). Key elements:

  • Authenticity token: A per-session (or per-form) token embedded in server-rendered forms (form_with, form_for) and verified on the server.
  • protect_from_forgery: Rails controllers include protect_from_forgery with: :exception in ApplicationController by default for HTML apps.
  • CSRF header: For AJAX, Rails UJS sends the token in X-CSRF-Token header automatically.
  • SameSite cookies: Modern Rails sets session cookies with SameSite=Lax by default which mitigates some cross-site POST vectors.
# application_controller.rb
class ApplicationController < ActionController::Base
  protect_from_forgery with: :exception
end

How the authenticity token works (mechanics)

Rails embeds a hidden input with the token in forms. On submit, the token is sent and compared to the server-side stored value (session or HMAC). If missing/invalid, the request is rejected.

  • Token generation: secure random or HMAC-based token tied to session.
  • Validation: server checks that incoming token matches expected token for the session or signed value.

API-only apps & CSRF differences

If you're building an API consumed by SPAs or mobile apps, different patterns apply:

  • Token-based auth (Authorization header): Using Bearer tokens in headers prevents CSRF since browsers won't add Authorization headers automatically across sites.
  • Cookie-based sessions for SPA: If you use cookies, you must implement CSRF protections: include CSRF token fetching endpoint and send token in header for state-changing requests, and use SameSite cookies.
  • Disable CSRF where appropriate: You can skip CSRF checks for JSON API endpoints if they strictly require Authorization headers, e.g., skip_before_action :verify_authenticity_token, if: -> { request.format.json? } — but do this only when you fully understand implications.

Additional mitigations and best practices

  • Use SameSite cookie attribute (Lax/Strict) to limit cookie sending on cross-site requests.
  • Require CSRF tokens for state-changing requests and send them in custom headers for AJAX.
  • Implement Content Security Policy (CSP) to limit where scripts can be loaded from; CSP doesn't prevent CSRF but reduces XSS which can expose tokens.
  • Prefer Authorization header for APIs and avoid relying on cookies for authentication in cross-origin contexts.
  • Log and monitor failed CSRF attempts to detect attack patterns.

Example: SPA + Rails CSRF flow

  1. Browser requests an initial HTML or calls an endpoint /csrf-token to fetch the token.
  2. SPA stores the token in memory (not localStorage) and includes it in X-CSRF-Token header for mutating requests.
  3. Server validates token and processes the request.
# Controller providing token
class CsrfController < ActionController::API
  def token
    render json: { csrf: form_authenticity_token }
  end
end

Subquestions you should expect

  1. Is SameSite enough?
    SameSite helps but doesn't solve all CSRF scenarios (older browsers, cross-site POSTs using target="_blank", etc.). Use it in combination with tokens and proper headers.
  2. Why not store JWT in cookies?
    Storing JWT in cookies exposes you to CSRF; if you must use cookies store short-lived cookies with CSRF tokens, or use HttpOnly cookies with backend rotation and double-submit tokens.
  3. How to test CSRF protections?
    Write request tests that omit or tamper tokens and expect rejection; run integration tests that simulate malicious cross-site requests.
