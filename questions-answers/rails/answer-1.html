REST API Book Controller Implementation

This example demonstrates a standard implementation of a RESTful controller for managing books in a Rails application.

Controller Code

class BooksController < ApplicationController
  before_action :set_book, only: [:show, :update, :destroy]

  # GET /books
  def index
    @books = Book.all
    render json: @books
  end

  # GET /books/:id
  def show
    render json: @book
  end

  # POST /books
  def create
    @book = Book.new(book_params)

    if @book.save
      render json: @book, status: :created
    else
      render json: @book.errors, status: :unprocessable_entity
    end
  end

  # PATCH/PUT /books/:id
  def update
    if @book.update(book_params)
      render json: @book
    else
      render json: @book.errors, status: :unprocessable_entity
    end
  end

  # DELETE /books/:id
  def destroy
    @book.destroy
    head :no_content
  end

  private

  def set_book
    @book = Book.find(params[:id])
  end

  def book_params
    params.require(:book).permit(:title, :author, :isbn, :published_date, :genre)
  end
end

Key Components Explained

  1. Inheritance: Inherits from ApplicationController to gain access to common functionality like rendering JSON responses.
  2. Before Action: set_book method runs before show, update, and destroy actions to load the book record once.
  3. CRUD Actions:
    • index: Returns all books as JSON
    • show: Returns single book details
    • create: Creates new book with validation handling
    • update: Updates existing book with error handling
    • destroy: Deletes book and returns empty response
  4. Strong Parameters: book_params method whitelists permitted attributes to prevent mass assignment vulnerabilities.
  5. Error Handling: Uses Rails' built-in error handling for validation failures (returns HTTP 422 Unprocessable Entity).

Potential Enhancements

  • Add pagination using gems like Kaminari or Pagy for large datasets
  • Implement authentication/authorization (e.g., Devise + Pundit)
  • Add caching strategies for frequently accessed data
  • Include rate limiting to prevent abuse
  • Use versioning for API changes (e.g., namespace controllers)

Testing Considerations

For comprehensive testing, consider:

  • RSpec tests covering happy paths and edge cases
  • Request specs testing full HTTP interactions
  • FactoryBot for creating test data
  • Shoulda Matchers for common validations
