Deadlocks in Multithreaded Rails Applications — Explanation and Prevention

Prepared by: Senior Software Engineer & System Architect — Rails / AWS / SQL / Vue.js

Date: 2025-09-10 (UTC)

Overview

Deadlocks can occur at DB level (row locks) or application level (Ruby threads & mutexes). This file explains causes, detection, and mitigation strategies.

Types of deadlocks

  • Database deadlocks: Two transactions wait on locks held by each other (e.g., Tx A holds row 1 and waits for row 2; Tx B holds row 2 and waits for row 1).
  • Application-level deadlocks: Ruby threads waiting on mutexes in inconsistent order causing cyclic waits.
  • Connection pool deadlocks: All DB connections are checked out and threads block waiting for connections while holding other locks or resources.

How DB deadlocks happen in Rails

  • Common when using SELECT ... FOR UPDATE, performing multiple updates in different orders across requests, or long transactions that lock many rows.
  • Different SQL statement order across code paths is a frequent cause.

How to detect deadlocks

  • Database logs (Postgres detects deadlock and aborts one transaction; look for deadlock messages in the DB logs).
  • Application monitoring: threads stuck, connection pool exhaustion, increasing latency for acquiring locks.
  • Use APM/tracing to find long-running transactions and lock waits.

Preventing and mitigating deadlocks

  • Consistent lock ordering: Always acquire locks in the same order across code paths.
  • Keep transactions short: Avoid complex logic inside transactions; move non-essential work outside transaction boundaries.
  • Use SELECT FOR UPDATE sparingly: Consider optimistic locking (lock_version) or retry loops on serialization failures.
  • Set reasonable statement_timeout / lock_timeout: Fail fast and retry rather than block indefinitely.
  • Monitor connection pool: Ensure pool size >= threads and long-running jobs don't hold connections unnecessarily.
  • Retry strategies: On serialization errors or deadlock errors, implement idempotent retries with backoff.

Example: avoid deadlock with consistent order

# BAD: may deadlock if two threads lock in opposite order
tx1: lock account A, then lock account B
tx2: lock account B, then lock account A

# GOOD: always lock by id order
ids = [a.id, b.id].sort
accounts = Account.where(id: ids).order(:id).lock
# process accounts in sorted order

Subquestions you should expect

  1. How to size DB connection pools?
    Match pool size to concurrency (threads per process * processes) but be mindful of DB capacity. Use separate DB user pools for heavy background workers if necessary.
  2. What about optimistic locking?
    Optimistic locking is great for low-conflict scenarios and avoids DB-level locks; use lock_version and handle conflicts with retries.
